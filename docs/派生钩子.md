# 派生钩子：外部控制有头会话的派生

jcode 在多种流程中打开新的终端窗口：集群智能体派生（`swarm spawn` 且 `spawn_mode=visible`）、新终端恢复、自研会话、重启恢复以及 jade 中继启动。默认情况下 jcode 检测已安装的终端模拟器（kitty、wezterm、alacritty、gnome-terminal 等）并打开一个新的操作系统窗口。

**派生钩子（spawn hook）** 让外部程序接管这次派生，由它决定会话出现在*哪里、以何种方式*：tmux 窗格、kitty 标签页、zellij 窗格、herd 等包装应用中的标签页、特定的显示器/工作区等。

## 配置

```toml
# ~/.jcode/config.toml
[terminal]
spawn_hook = "tmux new-window"
```

或按环境变量配置：

```bash
export JCODE_SPAWN_HOOK="tmux new-window"
# 空值禁用配置文件中的钩子：
export JCODE_SPAWN_HOOK=
```

环境变量总是优先于配置文件。

## 契约

当发生有头派生且配置了钩子时，jcode 运行：

```
<spawn_hook> <jcode-binary> <args...>
```

- 钩子命令按 shell 风格解析（引号和反斜杠转义可用），但直接执行，不经过 shell。
- jcode 二进制和完整参数列表作为额外 argv 项追加（熟悉的 `$TERMINAL -e <cmd>` 约定）。
- 钩子的工作目录是会话工作目录。
- 钩子进程被分离；jcode 不等待它。
- 如果钩子启动失败（二进制缺失、解析错误），jcode 记录警告并回退到内置终端检测。

### 元数据环境变量

钩子（以及内置回退派生的任何终端）会收到：

| 变量 | 含义 |
| --- | --- |
| `JCODE_SPAWN_KIND` | 派生原因：`swarm-agent`、`resume`、`selfdev`、`restart`、`jade-relay` |
| `JCODE_SPAWN_SESSION_ID` | 窗口将运行的 jcode 会话 |
| `JCODE_SPAWN_TITLE` | 建议的窗口/标签页标题（包含会话图标 + 名称） |
| `JCODE_SPAWN_CWD` | 会话工作目录 |
| `JCODE_SPAWN_PROGRAM` | 要执行的 jcode 二进制路径 |
| `JCODE_SPAWN_COMMAND` | 完整命令行（shell 转义），供接受单个 shell 字符串的钩子使用 |
| `JCODE_SPAWN_SWARM_ID` | （集群派生）智能体加入的集群 |
| `JCODE_SPAWN_COORDINATOR_SESSION_ID` | （集群派生）请求该派生的协调者会话 |
| `JCODE_FRESH_SPAWN` | 当派生是新窗口交接时为 `1` |

### 客户端终端环境（多终端路由）

jcode 服务器进程是长驻的：它在启动时捕获一次标识终端的 env 变量（`ZELLIJ_SESSION_NAME`、`TMUX`、`DISPLAY`、`KITTY_WINDOW_ID` 等）。当你之后打开一个*新的*终端/tmux/zellij 会话并连接一个客户端到同一服务器时，服务器的副本已经过期，因此服务器运行的派生钩子会错误地指向*旧*终端。

为解决此问题（见 issue #405），每个连接的客户端都会快照自己的终端标识 env 并发送给服务器。当派生钩子运行时，服务器重新导出请求客户端的值，使钩子跟随用户实际连接的终端：

- 原生变量（如 `ZELLIJ_SESSION_NAME`）被覆盖为客户端的值，因此直接读取它的钩子会指向正确的会话。
- 同时导出一个 `JCODE_CLIENT_<NAME>` 别名（如 `JCODE_CLIENT_ZELLIJ_SESSION_NAME`、`JCODE_CLIENT_TMUX`、`JCODE_CLIENT_DISPLAY`），使钩子可以显式区分客户端的终端与服务器的终端。

覆盖的键包括终端复用器（zellij、tmux、screen）、终端模拟器（kitty、wezterm、ghostty、alacritty、iTerm、Windows Terminal、handterm）和显示服务器（`DISPLAY`、`WAYLAND_DISPLAY`）。只转发客户端实际设置的变量。

## 示例

当 jcode 检测到请求客户端位于 tmux 内部时，其内置启动器会自动在针对请求 `TMUX_PANE` 的右侧窗格中打开有头派生。这覆盖 `/split`、`/fork`、新终端恢复、自研和可见智能体派生。`JCODE_TERMINAL` 可以显式选择终端模拟器，而配置的 `spawn_hook` 仍然具有完全优先级。

### tmux：每个智能体一个窗口

```toml
[terminal]
spawn_hook = "tmux new-window"
```

当你想覆盖自动窗格行为时使用钩子。例如，`tmux new-window <jcode> --resume ses_x` 在当前 tmux 服务器的新窗口中运行该命令。要显式保留右侧窗格行为：

```toml
[terminal]
spawn_hook = "tmux split-window -h"
```

### kitty：每个智能体一个标签页（远程控制）

```toml
[terminal]
spawn_hook = "kitty @ --to unix:/tmp/kitty.sock launch --type=tab --"
```

### 自定义路由脚本

要完全控制（位置、标题、集群与恢复路由），把钩子指向一个脚本：

```toml
[terminal]
spawn_hook = "~/bin/jcode-spawn-router"
```

```bash
#!/usr/bin/env bash
# ~/bin/jcode-spawn-router
# argv: 要运行的 jcode 命令（"$@"）。Env: JCODE_SPAWN_* 元数据。

case "$JCODE_SPAWN_KIND" in
  swarm-agent)
    # 集群工作者作为 tmux 窗格放在以集群命名的窗口中。
    tmux new-window -n "swarm:${JCODE_SPAWN_SWARM_ID:0:8}" "$@" 2>/dev/null \
      || tmux split-window "$@"
    ;;
  *)
    # 其他一切作为普通终端窗口。
    kitty --title "$JCODE_SPAWN_TITLE" -e "$@" &
    ;;
esac
```

启动后未启动任何东西即以非零退出的钩子**不会**触发内置回退（jcode 只在钩子进程无法启动时回退），因此路由脚本应像上面的示例一样自己处理回退。

### 接受单个 shell 字符串的启动器

一些启动器想要一个 shell 命令字符串而不是 argv。使用 `$JCODE_SPAWN_COMMAND`：

```bash
#!/usr/bin/env bash
zellij action new-pane -- bash -lc "$JCODE_SPAWN_COMMAND"
```

## 编程式发现

包装 jcode 的程序（如 herd 风格的会话管理器）可以在它们启动的 `jcode` 服务器进程环境中设置 `JCODE_SPAWN_HOOK`。服务器执行的每一次有头派生（包括协调者通过套接字协议请求的集群智能体）都将通过包装器的钩子路由。

## 聚焦钩子

当 jcode 想把现有会话窗口带到前台时（例如启动自研窗口后），它通常在 X11 上做一次尽力而为的 wmctrl/xdotool 标题搜索。这在 Wayland 或复用器内部不可用，而且拥有布局的包装器也应该拥有聚焦：

```toml
[terminal]
spawn_hook = "tmux new-window"
focus_hook = "~/bin/jcode-focus"   # env: JCODE_FOCUS_SESSION_ID, JCODE_FOCUS_TITLE
```

```bash
#!/usr/bin/env bash
# ~/bin/jcode-focus
tmux select-window -t "$(tmux list-windows -F '#{window_id} #{window_name}' \
  | grep -F "$JCODE_FOCUS_TITLE" | head -1 | cut -d' ' -f1)"
```

环境变量覆盖：`JCODE_FOCUS_HOOK`（空值禁用配置文件中的钩子）。如果钩子启动失败，jcode 回退到内置聚焦路径。
