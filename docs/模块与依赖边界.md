# 模块与依赖边界

本仓库是**单仓库多 crate**布局：业务代码全部位于 `crates/`，根 `src/` 只剩组合外壳
（`main.rs`、`lib.rs`、`cli/`）。本文说明分层结构、crate 归属规则、依赖方向门禁，
以及让编译变快的边界拆分方法。

## 一、当前分层（52 个 crate）

```
第一层  jcode（根包：组合外壳，src/ 仅 main/lib/cli）
          │
第二层  jcode-tui（TUI 主体 + 12 个 jcode-tui-* 子 crate）
          │
第三层  jcode-app-core（agent / 工具 / 服务器 / 环境模式 / 网关行为）
          │
第四层  jcode-base（配置 / 认证 / provider 装配 / 会话 / 存储编排 / 提示词）
          │
底层    jcode-core（最小原语：console / env / fs / id / output_style）
```

横向支撑：

| 类别 | 数量 | 成员 |
|---|---:|---|
| 契约类型 crate | 10 | `jcode-auth-types`、`jcode-background-types`、`jcode-config-types`、`jcode-memory-types`、`jcode-message-types`、`jcode-selfdev-types`、`jcode-session-types`、`jcode-task-types`、`jcode-tool-types`、`jcode-usage-types` |
| Provider crate | 9 | `jcode-provider-core`、`jcode-provider-env`、`jcode-provider-metadata`，以及 anthropic / openai / openrouter 三组「格式 crate + `*-runtime` crate」 |
| TUI 子 crate | 12 | `jcode-tui-anim`、`-core`、`-markdown`、`-mermaid`、`-messages`、`-permissions`、`-render`、`-session-picker`、`-style`、`-usage-overlay`、`-visual-debug`、`-workspace` |
| 其他叶子 | 21 | 协议、计划、集群、组件、工具核心、终端、渲染核心、存储、日志、模糊匹配、嵌入、构建支持等 |

> 名字在本仓库 `crates/` 下不存在的 `jcode-*`，一律视为**目标名**或**已删除的名字**。
> 本 fork 移除的能力（桌面端、PDF、浏览器、遥测、云同步等）已连带删掉对应 crate。

## 二、归属规则

### 类型 crate 拥有稳定的数据契约

`*-types` crate 只放：

- 被多个 crate 或协议层使用的纯数据结构；
- 与数据契约绑定的序列化形态与小型纯助手方法。

**不得**含文件系统、网络、进程、TUI、provider 客户端、全局状态或存储访问；
依赖限于 `serde` / `chrono` 与其他类型 crate。

### 领域行为归 crates 中的运行时模块

出现以下需求时，行为留在运行时 crate（`jcode-base` / `jcode-app-core` / `jcode-tui`）：

- 访问 `crate::storage`、`config`、`logging`、`server` 或派生进程；
- provider HTTP 客户端与认证管理器；
- Tokio 运行时、后台任务、通道、全局缓存、文件锁、PID 注册表；
- TUI 渲染与 crossterm/ratatui 状态。

若类型的内在方法需要这些 API，要么留在一起，要么把**行为和依赖一起**迁移；
不要只搬结构体而在原处留下非法的固有实现。

### `jcode-core` 只放真正共享的原语

跨领域原语、被许多 crate 使用的极小助手、以及暂时无处安放的 DTO。
一旦某类 DTO 成簇增长，就拆成聚焦的领域类型 crate——`jcode-core` 扇出高，
把高变更 DTO 放进去会适得其反。

### 拆分决策规则

只有当拆分至少带来一项编译收益时才拆：

- 常见行为改动不再触碰稳定类型定义；
- 类型专属变更可通过「小类型 crate + 聚焦依赖者」检查；
- 重型依赖远离 DTO crate；
- 下游能用小契约而不依赖大 crate。

反之（新 crate 增加依赖、扩大重建扇出、或迫使频繁跨 crate 编辑）就不要为整齐而拆。

### 迁移期间的再导出策略

1. 把类型移到目标 crate；
2. 旧路径保留 `pub use` 以稳住调用点；
3. 验证聚焦测试与自研构建/重载；
4. 下游能直接依赖领域 crate 后，再删掉过时的再导出。

## 三、依赖方向门禁

```bash
python3 scripts/check_dependency_boundaries.py
python3 scripts/check_wildcard_reexport_budget.py
```

守卫规则：

- 下层不得依赖上层（TUI 更不得出现在类型/协议层之下）。
- `jcode-*-types` 不得直接依赖 `jcode`、`jcode-core`、provider crate、TUI crate
  或协议/运行时重型 crate；只允许外部轻量库与其他类型 crate。
- 需要新内部依赖时，先判断这个依赖本身是否应该成为类型 crate。
- 通配再导出有预算上限（`scripts/wildcard_reexport_budget.json`），避免 `pub use whole_crate::*`
  兼容梯子重新长出。

## 四、迁移检查清单

对每次类型/纯助手迁移：

1. **分类**：是稳定契约还是运行时行为？有固有方法吗？那些方法需要仅运行时 API 吗？行为能否在不增加扇出的前提下一起搬？
2. **兼容**：serde 表示是否不变（默认值、`skip`、`rename`、枚举判别式）？字段可见性是否仍合适？旧路径能否保留再导出？
3. **crate 健康**：目标 crate 的依赖策略是否允许？新依赖是否仅限 `serde`/`chrono`/兄弟类型 crate？是否仍无环？
4. **验证**：有聚焦测试过滤器吗？`cargo check --profile selfdev -p <type-crate> -p jcode --bin jcode` 通过吗？
   `cargo fmt` 通过吗？自研构建与重载在干净 HEAD 上通过吗？

### 测试过滤器的坑

宽泛过滤器会选中无关的有状态/时序敏感/基准测试，不要把它们当必需门：

| 过滤器 | 误选内容 |
|---|---|
| `side_panel` | 固定 UI/布局与延迟基准 |
| `usage` | 应用显示测试 |
| `session::` | 实时挂接服务器测试与选择器行为 |
| `ambient` | 带配置与调度状态的 TUI/助手集成测试 |

只 DTO 的提取在精确测试与编译检查通过后即可推进，不必等宽泛过滤器全绿。

## 五、编译速度：方法与实测

### 5.1 关键路径

```
jcode-base  →  jcode-app-core  →  jcode-tui  →  jcode lib  →  jcode bin
（约 10 万+ 行）  （约 10 万行）      （约 10 万+ 行）
```

瓶颈是这几支大 crate 的 **rustc 前端串行化**，不是链接器选择，也不是第三方冷编译。
因此方向是**加宽依赖 DAG**（拆成并行域 crate），而不是继续抽微型类型 crate。

### 5.2 实测（2026-04-30，`dev_cargo.sh check --profile selfdev`）

| 场景 | 观察 | 解读 |
|---|---:|---|
| 近期仅文档提交后的首次检查 | 约 65.8 s | 缓存/环境状态主导，当作热身噪声基线 |
| 触碰行为模块 | 约 6.2 s | 依赖已构建时，单纯行为编辑相对便宜 |
| 触碰 `jcode-core` 中的类型 | 约 65 s | `jcode-core` 扇出高，改它会让大量下游失效 |

结论：**把稳定、低变更的契约移出大 crate 有益；把高变更 DTO 塞进高扇出 crate 有害。**

### 5.3 拆分优先级

1. 从 `jcode-base` 拆：认证、会话、记忆、provider 实现（重型依赖如云 SDK 隔离在叶子）。
2. 从 `jcode-app-core` 拆：server、agent、工具注册表、后台/集群/自研服务。
3. 从 `jcode-tui` 拆：先明确客户端 API / 视图模型边界，再考虑把可复用客户端状态逻辑移出终端渲染 crate。

### 5.4 其他有效手段

- **消灭 glob 再导出梯子**：新代码不依赖整层 prelude 式再导出，依赖方向在 import 与 manifest 中可见。
- **把内联测试移出热点 crate**：内联 `#[cfg(test)]` 会把「大生产 crate + 大测试体」编成一个 rustc 单元。
- **减少前端宏开销**：不做 `dyn` 的 trait 用原生 `async fn` 替代 `async_trait`；只在对象安全的插件边界保留 boxed future。

### 5.5 反目标

不要为了快构建而默认砍功能；不要拆微型 crate（除非形成真实失效/并行边界）；
不要把高变更行为移进底层类型 crate；不要一次性大重写。

### 5.6 每次边界改动后的验证

```bash
python3 scripts/check_dependency_boundaries.py
cargo check --profile selfdev -p jcode --bin jcode
scripts/check_guardrails.sh
```

需要重测编译时间时，用 `scripts/dev_cargo.sh check --profile selfdev -p jcode --bin jcode`
配合触碰代表性文件（如 `crates/jcode-tui/src/tui/app/input.rs`）测量增量。

## 六、"足够好"的标准

- 每个类型 crate 有清晰领域与最小依赖集；
- `jcode-core` 只含真正原语或有文档的临时模块；
- 没有哪个文件同时混着大 DTO 块、持久化、运行时编排与渲染；
- 每个领域有聚焦验证命令；
- 每次结构变更后自研构建/重载干净可用。
