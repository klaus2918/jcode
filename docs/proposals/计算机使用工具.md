# 提案：macOS 计算机使用的原生 `computer` 工具

## 摘要

添加一个原生工具 **`computer`**，让智能体通过一个 `action` 分发的接口观察和控制 macOS GUI——截图、辅助功能（AX）树、鼠标/键盘输入、窗口/应用管理以及剪贴板。

这与现有 **`browser`** 工具（`crates/jcode-app-core/src/tool/browser.rs`）保持一致：一个注册的工具，`action: String` 选择子操作，带可选类型化参数。它给 jcode 一个闭环控制（*看屏幕 → 决策 → 行动*），而不依赖浏览器或外部自动化工具。

## 动机

- 智能体已经能驱动浏览器；它不能驱动原生 macOS 应用、系统 UI 或浏览器沙箱之外的任何东西。
- "计算机使用"智能体恰好需要三个原语：**读取屏幕**、**读取 UI 结构**、**合成输入**。macOS 通过 Accessibility / Quartz Event Services / ScreenCaptureKit 技术栈提供全部三者。
- 单个、边界清晰的工具让工具表面保持小巧，并把权限故事放在一个地方。

## 架构

```
crates/jcode-macos-control/        (新) cfg(target_os = "macos") 平台 crate
  └─ AX (accessibility-sys)、CGEvent (core-graphics)、
     CoreFoundation (core-foundation)、截图 (ScreenCaptureKit / CGDisplay)、
     应用/窗口控制 (objc2 + objc2-app-kit)、剪贴板 (objc2 NSPasteboard)

crates/jcode-app-core/src/tool/computer.rs   (新) ComputerTool
  └─ 薄分发层：解析输入 -> 调用 jcode-macos-control -> ToolOutput
  └─ 在 crates/jcode-app-core/src/tool/mod.rs 的 base_tools() 中注册
```

- 所有原生 API 都通过现有 Rust 绑定（`objc2`、`accessibility-sys`、`core-graphics`、`core-foundation`）访问——**无 Swift/ObjC 构建步骤**。
- 在非 macOS 目标上工具仍然注册，但每个动作都返回干净的 `unsupported on this platform` 错误，因此工具列表在各操作系统间保持稳定。
- `screenshot` 通过 `ToolOutput::with_image`（base64）返回图像，与今天 `browser` 返回截图的方式一致。

## 权限（重要部分）

macOS 将此分散在**四个** TCC 权限中。编程式*请求*支持因权限而异：

| 权限 | 用途 | 编程式请求 |
|---|---|---|
| **辅助功能** | 驱动其他应用的 UI、注入 `CGEvent` 输入 | ⚠️ 仅提示 + 深链；用户必须手动切换 |
| **屏幕录制** | 截图 / 某些应用的 `get_ui_tree` | ✅ `CGRequestScreenCaptureAccess()` |
| **输入监控** | 读取全局输入流 | ✅ `IOHIDRequestAccess(...)` |
| **自动化**（Apple Events） | 脚本化协作应用 | ✅ 首次发送时按目标应用提示 |

**辅助功能是无法自动授予的那一个**（Apple 的反恶意软件边界），而输入注入需要它。通过 `request_permissions` 动作暴露的最佳可达流程：

1. `AXIsProcessTrustedWithOptions([kAXTrustedCheckOptionPrompt: true])`——显示系统对话框*并自动把 jcode 加入辅助功能列表*（关闭状态）。
2. 深链到精确窗格：
   `open "x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility"`。
3. 轮询 `AXIsProcessTrusted()` 直到授予，然后报告就绪。

因此体验变成**一次提示 + 一次开关**，而不是"去设置里找"——但对辅助功能永远不会零接触。

`check_permissions` 报告全部四项的当前状态，这样智能体可以在尝试控制之前精确告知用户缺少什么。

## 动作

`action`（必填）选择操作。下面的参数是可选的，并按动作验证。

**权限**
- `check_permissions` → 辅助功能 / 屏幕录制 / 输入监控状态
- `request_permissions` → 上述提示 + 深链流程

**观察**
- `screenshot` — `{ display?, window_id?, region? }` → 图像
- `get_ui_tree` — `{ pid? | frontmost, max_depth? }` → 序列化的 AX 树（role、title、value、position、size、actions）
- `find_element` — `{ role?, title?, value?, pid? }` → 匹配的元素及其标识符
- `element_at` — `{ x, y }` → 该点下的元素

**鼠标**
- `move` — `{ x, y }`
- `click` / `double_click` / `right_click` — `{ x?, y? }`（省略时用当前位置）
- `drag` — `{ from: [x,y], to: [x,y] }`
- `scroll` — `{ x?, y?, dx, dy }`

**键盘**
- `type` — `{ text }`
- `key` — `{ keys: "cmd+shift+4" }`（组合键）
- `key_down` / `key_up` — `{ key }`

**语义 AX（可用时优先于原始输入）**
- `press` — `{ element }`（AXPress）
- `set_value` — `{ element, value }`
- `get_value` — `{ element }`
- `perform_action` — `{ element, ax_action }`
- `select_menu` — `{ app, path: ["File", "Export…"] }`

**窗口 / 应用**
- `list_apps`、`activate_app` `{ app }`
- `list_windows` `{ pid? }`、`focus_window` `{ window }`
- `move_window` `{ window, x, y }`、`resize_window` `{ window, w, h }`
- `minimize_window` / `close_window` `{ window }`

**剪贴板**
- `get_clipboard`、`set_clipboard` `{ text }`

> 元素标识符：`find_element` / `get_ui_tree` 返回足够稳定的句柄（例如 `pid` + AX 路径或会话作用域的元素 id），语义动作可以接受，这样智能体在可能时按结构行动而不是按像素坐标。

## 安全

计算机使用是高风险半径，因此：

- 像其他强大工具一样**权限门控**；如果缺少辅助功能/屏幕录制，早期以清晰消息拒绝。
- 变更动作上的 **`dry_run` 参数**——解析并报告目标而不行动。
- 破坏性坐标点击的**截图辅助确认**（返回被瞄准的区域/元素）。
- v1 中**不捕获全局输入**（我们合成输入但不记录用户的击键），默认避开输入监控，除非未来功能需要它。
- 在元素可解析的地方**优先使用语义 AX 动作**而非盲目坐标输入——更健壮、更可审计。

## 实施计划

1. `jcode-macos-control` crate：权限、截图、AX 读取、AX 动作、CGEvent 输入、窗口/应用控制、剪贴板。对纯逻辑部分（输入解析、组合键解析、树序列化）做单元测试。
2. `tool/computer.rs` 中的 `ComputerTool`：输入结构 + `action` 分发 + schema + 描述；在 `tool/mod.rs` 的 `base_tools()` 中注册 `"computer"`。
3. 默认关闭 / 门控发布 + `docs/` 中的文档。
4. 后续：同一工具表面背后的 Windows/Linux 后端。

## 开放问题

- 元素句柄格式——`pid`+AX 路径 vs 不透明会话作用域 id 缓存？
- `request_permissions` 应该阻塞并轮询，还是立即返回状态让智能体重新检查？
- 默认启用：opt-in 标志 vs 总是注册但门控？
