# 跨设备工作树与构建同步（提案）

状态：提案（仅设计，未实现）

## 问题

用户在多台机器上开发 jcode（及其他仓库），例如 MacBook（aarch64-darwin）和 Linux 笔记本。在单台机器上，`selfdev build` + reload 意味着每个本地 jcode 实例都运行新版本，多个智能体可以共享一个工作树，因为服务器调解编辑并跟踪冲突（`FileTouchService`、`file_activity.rs`）。

跨机器拆分时，这会破坏：

- Linux 笔记本上的 `selfdev build` 不会更新 MacBook 的 jcode，反之亦然。
- 没有共享工作树，因此一台机器上的更改对另一台机器上的智能体/会话不可见，直到手动推送/拉取。

目标：让多台机器表现得像一个逻辑工作树 + 一个逻辑构建通道，就像多个智能体在单台机器上已经共享一个工作树一样。

## 现有构建块（已在代码中验证）

| 构建块 | 位置 | 为什么重要 |
| --- | --- | --- |
| 与架构无关的版本身份 | `jcode-build-support/src/source_state.rs`（`SourceState::version_label`、`fingerprint`） | Fingerprint 哈希完整提交哈希 + 状态 + `diff --binary HEAD` + 未跟踪内容。两台机器上的相同源树产生相同标签，即使二进制按架构不同。 |
| 更新二进制自动重载 | `server/util.rs::server_has_newer_binary`、`reload_exec_target` | 基于 mtime 的通道扫描。对等端触发的本地构建发布到 `builds/current` 会以零改动触发现有重载流程。 |
| 拉取 → 构建 → 安装 → 执行 | `session_rebuild.rs` | 已经实现接收端的流水线形状。 |
| 网络门，相同协议 | `jcode-base/src/gateway.rs`（WS + :7643 上的普通 HTTP） | 远程客户端说与 Unix socket 客户端相同的换行 JSON 协议。普通 HTTP 处理器（`/pair`、`/health`）是 `/peer/*` 端点的自然位置。 |
| NAT 友好的设备事件总线 | `server/jade_relay.rs` | 设备 id、心跳、长轮询命令事件。机器无法直接互相到达时也能工作。 |
| 服务器端工具执行 | 服务器架构 | 工具（bash、edit）在服务器进程中运行；远程客户端附加到另一台机器的服务器会获得完整的多智能体单工作树行为，包括冲突警告。 |
| 远程构建先例 | `scripts/remote_build.sh` | rsync + ssh + 同步回模式。 |

### 已知差距：跨机器仓库身份

`repo_scope_key` / `worktree_scope_key` 哈希 git 公共目录 / 工作树的*本地规范路径*。它们永远不会跨机器匹配（`/Users/jeremy/...` vs `/home/jeremy/...`）。跨设备功能必须用可移植的东西作为仓库键：规范化的 origin URL，或配置中的显式仓库名（`[sync] repo_id = "jcode"`），回退到 origin URL 哈希。

## 设计张力

1. **二进制不能共享**跨 darwin-aarch64 和 linux-x86_64。"处处同一版本"必须意味着*相同源状态，每台机器各自构建*，以 `version_label` 作为跨机器等价性检查。
2. **并非所有写入都由服务器调解。** 工具编辑流经服务器，但 `bash`、编辑器和 `cargo` 不可见地变更工作树。因此跨设备同步需要字节级捕获机制（git plumbing 快照和/或 fs watcher），而不仅仅是工具事件转发。
3. **笔记本会离线。** 纯实时同步（mutagen/syncthing 风格）冲突语义差。基于 git 的收敛（每设备同步 ref、合并）诚实地处理离线分歧。

## 机制：在不碰 HEAD 的情况下运送工作树状态

为了原子地捕获可能脏的工作树而不移动用户的 HEAD 或 index：

```
GIT_INDEX_FILE=$tmp git add -A          # 跟踪 + 未跟踪进入临时 index
tree=$(GIT_INDEX_FILE=$tmp git write-tree)
commit=$(git commit-tree $tree -p HEAD -m "jcode sync: <device> <fingerprint>")
git push origin $commit:refs/jcode/sync/<device>
```

- 原子、内容寻址、包含未跟踪文件、排除 gitignore 的。
- 接收方抓取该 ref，应用它（checkout 进工作树或物化 diff），然后验证 `current_source_state().fingerprint` 与 beacon 的 fingerprint 匹配，保证字节精确复现。
- 发送方的工作树/index/HEAD 永不移动。

## 分阶段计划

### Phase B - selfdev 构建对等（先做；消除所述痛点）

在机器 X 上成功 `selfdev build` + 发布后：

1. 计算 `SourceState`（构建流水线已经做了）。
2. 把工作树快照到 `refs/jcode/sync/<device>`（上述机制）并推送到共享 git 远程。干净树可以跳过快照并使用现有提交。
3. 宣布**版本 beacon** `{repo_id, version_label, fingerprint, full_hash, sync_ref, device, timestamp}`：
   - 快速路径：通过 Tailscale 向对等网关 HTTP POST（`/peer/version-beacon`）。
   - 回退：jade relay 设备事件（通过 NAT 工作）。
   - 慢路径：对等端轮询 git 远程上的同步 ref。

机器 Y 的服务器运行一个小型对等同步任务（与 `jade_relay::spawn_if_configured` 形状相同）：

1. 接收 beacon；如果 `version_label` 匹配它已运行的或最近应用的版本则忽略（**回显抑制**，防止构建乒乓）。
2. 策略门，默认保守：
   - 工作树干净且本地 HEAD 是 beacon 提交的祖先
     → 自动应用：抓取、前进、通过 selfdev 构建队列（本机架构）构建、发布。现有的 `server_has_newer_binary()` 轮询随后自动重载。
   - 否则 → 不覆盖。在 TUI/状态中显示：
     `peer build available: <label> from <device> (blocked: local changes)`
     带一键接受。
3. 发布后，Y 的 `version_label` 等于 X 的。跨设备对等可通过比较标签验证（例如在 `selfdev status` ��� beacon ack 中）。

配置草图：

```toml
[sync]
enabled = true
repo_id = "jcode"                  # 可移植仓库身份
peers = ["macbook.tail-net.ts.net:7643"]
auto_apply = "clean-ff-only"       # off | clean-ff-only | always-notify
```

### Phase A - 中心附加（双方在线时一个权威工作树）

`jcode attach <host>`：TUI 通过现有网关 WS 连接到对等机器的服务器。因为工具在服务器端执行，附加的客户端完全参与那台机器的工作树，包括冲突跟踪。

工作项：

- 客户端传输：WS 流替代 Unix socket（服务器端已有桥；需要客户端对应物）。
- 可信个人设备的配对/认证 UX（DeviceRegistry 已存在）。
- 审计假设会话文件系统的客户端本地磁盘读取，例如 `jcode-tui/src/tui/ui_file_diff.rs:270`（对被 diff 文件的 `std::fs::read_to_string`）。这些需要服务器 RPC（`read_file` 控制请求）或优雅降级。

### Phase C - 真正的工作树联邦（长期）

把 Phase B 的快照和 Phase A 的对等推广为连续双向同步：

- **数据面：** 节流自动快照到每设备同步 ref，由 (a) 服务器调解的工具编辑、(b) 针对 bash/编辑器/cargo 写入的 fs watcher、(c) 定时器触发。对等端直接抓取 ref（ssh/Tailscale）或通过共享远程。
- **收敛：** 如果本地 HEAD/状态是祖先 → 快进应用。如果分歧 → 保留两个快照，把仓库标记为"分裂"，让 harness 派智能体执行合并（服务器管理同机冲突的跨设备类比）。
- **协调面：** 通过对等链路联邦 `FileTouchService` 事件，这样两台机器上的智能体都看到"另一个智能体编辑了第 40-60 行"的跨设备警告。可选为热文件添加咨询性写租约。

## 考虑的替代方案

- **工作树的 Syncthing/mutagen：** 简单，但字节级冲突（`.sync-conflict` 文件）、跨多文件编辑无原子性，目标目录 / 构建产物需要仔细排除。Git plumbing 快照给出原子、内容寻址、可合并的状态，使用 git 用户已经理解的语义。
- **总在一台机器上构建 + 复制二进制：** 被架构不匹配破坏；从 linux 交叉编译 darwin（反之亦然）不值得工具链成本，因为两台机器都有可用的本地工具链。
- **NFS/SSHFS 共享工作树：** 惩罚离线使用和 IDE/文件 watcher 性能；对笔记本不可行。

## 建议的实施顺序

1. Phase B beacon + 接收器，`auto_apply = "clean-ff-only"`，仅 git 远程轮询（无新端口），`selfdev status` 显示对等状态。
2. 添加网关 `/peer/version-beacon` 快速路径 + 阻塞情况的 TUI 通知。
3. Phase A `jcode attach`（WS 客户端传输 + 配对 + 文件读取 RPC）。
4. Phase C 联邦，复用 beacon 快照机制和 A 的对等链路。
