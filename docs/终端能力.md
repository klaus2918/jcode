## 图例

- **真彩色**：支持 `\e[38;2;R;G;Bm` / `\e[48;2;R;G;Bm` SGR 序列，1600 万色
- **256 色**：支持 `\e[38;5;Nm` / `\e[48;5;Nm` 索引色
- **Unicode/Emoji**：完整 = 正确字素聚类、正确双宽、emoji ZWJ 序列；部分 = 基本多字节但宽度错误或序列缺失
- **Kitty 键盘协议**：支持 `CSI > flags u` 渐进增强键盘协议
- **括号粘贴**：支持 `\e[?2004h` 把粘贴内容包在开始/结束标记中
- **鼠标捕获**：支持 SGR 1006 鼠标上报（`\e[?1006h`）
- **备用屏幕**：支持 `\e[?1049h` 备用屏幕缓冲区

## 导致白块或陈旧内容的已知渲染问题

### 1. 背景色溢出 / "白块"

**根因**：TUI 在单元格上设置背景色，但终端下一帧未能正确清除或重绘该单元格时，单元格保留旧内容或回退到默认背景（浅色主题下常为白色）。

**受影响的终端和场景：**

- **所有终端**：如果应用在通过 SGR 先设置正确背景色之前写入 `\e[K`（清除到行尾），被清除的区域继承终端的默认背景，而不是应用的预期颜色。这是深色主题 TUI 中白/浅色块的头号原因。

- **tmux**：tmux 模拟自己的屏幕缓冲区。如果内部应用使用 BCE（背景色清除）而 tmux 的 `default-terminal` 没有正确声明 BCE 支持，被清除的区域渲染成错误背景。修复：确保使用 `tmux-256color` terminfo 且与外部终端能力匹配。

- **Windows Terminal（ConPTY）**：ConPTY 有时错误合并快速 SGR+清除序列，导致调整大小或快速重绘后行边界 1-2 个单元格保留旧背景色。

- **VS Code 终端（xterm.js）**：Canvas 渲染器在终端快速交替普通与备用屏幕缓冲区时可能留下"幽灵"单元格，尤其在调整大小事件期间。

### 2. Emoji / 双宽字符错位

**根因**：终端和应用对字符占用多少列意见不一。应用认为 emoji 是 2 列宽（按 Unicode `East_Asian_Width`），终端却渲染为 1 列（或相反），导致该行后续每个单元格都偏移。

**受影响的终端：**

- **macOS Terminal.app**：特别严重。许多 emoji 渲染为 1 格宽，而应用（使用 libc `wcwidth` 或 Unicode 表）假设 2 格。这使整行失步，留下显示为空白/白块的"幻影"单元格。

- **tmux**：tmux 有自己的内部 `wcwidth` 实现。如果它与外部终端对字符宽度的判断不一致（近期 Unicode 版本新增的 emoji 常见），光标定位失败，单元格出现重复或空白。

- **screen**：比 tmux 更糟。其 Unicode 宽度表过时多年。大多数 emoji 和许多 CJK 字符会破坏行布局。

- **Alacritty**：总体良好，但 PUA（私用区）码点的 Nerd Font 字形默认为 1 格宽。如果应用假设 2 格，会发生错位。

### 3. 调整大小后的陈旧内容

**根因**：终端窗口调整大小时，应用收到 `SIGWINCH` 必须重绘。如果重绘是部分的，或终端的行重排逻辑与应用假设冲突，旧内容保持可见。

**受影响的终端：**

- **Konsole**：调整大小时重排激进——它重排软换行行，这可能与期望每行独立的 TUI 应用冲突。这导致瞬时的"双重渲染"伪影。

- **tmux**：调整大小使 tmux 重排自己的缓冲区，然后把 `SIGWINCH` 中继给内部应用。存在竞争：如果应用在 tmux 完成重排之前重绘，旧内容会出现 1-2 帧。

- **VS Code 终端**：xterm.js 的调整大小处理器可能滞后于实际视口大小，导致应用按错误尺寸绘制 1-2 帧。

### 4. 备用屏幕缓冲区切换伪影

**根因**：进入或离开备用屏幕（`\e[?1049h` / `\e[?1049l`）时，一些终端不完全清空缓冲区，或恢复错误的已保存状态。

**受影响的场景：**

- **Warp**：Warp 的块架构不使用传统备用屏幕。依赖 `\e[?1049h` 的 TUI 应用可能发现输出与 Warp 的 shell 集成 UI 元素混杂。

- **tmux + 嵌套会话**：嵌套 tmux 会话（或 screen 里的 tmux）可能丢失哪个备用屏幕缓冲区活动的追踪，把外部复用器的状态栏叠在内部应用内容上。

- **macOS Terminal.app**：在较旧 macOS 版本（pre-Ventura）上，从备用屏幕恢复时偶尔光标保持不可见直到用户输入。

### 5. 光标可见性问题

**根因**：`\e[?25l`（隐藏光标）和 `\e[?25h`（显示光标）并不总是可靠配对，尤其当应用崩溃或被 SIGKILL 杀死时。

**受影响的终端：**

- **所有终端**：如果 TUI 应用未恢复光标就崩溃，它保持隐藏。大多数现代终端（kitty、WezTerm、iTerm2）在 shell 提示符处自动恢复，但 GNOME 终端和 Terminal.app 可能保持光标隐藏直到 `reset` 或 `tput cnorm`。

- **tmux**：如果内部窗格的应用隐藏光标后用户切换窗格，光标可见性状态可能在窗格间泄漏（较新 tmux 已修复，但 3.3 及更早仍可观察到）。

### 6. SGR 重置范围问题

**根因**：`\e[0m`（SGR 重置）应重置所有属性，但一些终端对下划线样式、下划线颜色或删除线的处理不一致。

- **GNOME 终端（VTE）**：较旧 VTE 版本在 SGR 0 时不重置下划线颜色，导致彩色下划线跨行持续。
- **Konsole**：历史 bug，`\e[0m` 不重置上划线属性。
- **screen**：`\e[0m` 不能可靠重置 256 色前景/背景，后续文本留下陈旧颜色。

### 7. Kitty 键盘协议回退问题

**根因**：启用 kitty 键盘协议但退出时不正确禁用（或崩溃）的应用把终端留在增强键盘模式。后续 shell 输入可能产生乱码转义序列。

- **Kitty、Alacritty、WezTerm、Ghostty**：应用退出时不调用 `CSI < u` 都会受影响。Kitty 本身在检测到 shell 提示符时自动重置。Alacritty 和 WezTerm 不自动重置——用户必须运行 `reset`。

### 8. tmux 特有的透传限制

tmux 是 TUI 应用中渲染问题最常见的来源，因为它插入完整的 VT100 模拟层：

- **转义序列过滤**：tmux 剥离它不认识的任何转义序列。这破坏 kitty 键盘协议、kitty 图形协议、iTerm2 行内图像，以及某些扩展 SGR 属性（例如 `CSI 4:3 m` 卷曲下划线需要 tmux 3.4+）。
- **延迟透传**：即使设置 `set -g allow-passthrough on`，DCS 透传也会增加延迟并可能拆分长序列。
- **TERM 不匹配**：如果内部 `TERM` 与 tmux 声明的能力不匹配（例如应用看到 `xterm-256color` 但 tmux 只传递 `screen-256color`），颜色/能力协商静默失败。
- **剪贴板**：OSC 52 剪贴板支持有效但必须显式启用（`set -g set-clipboard on`）。

## 对 TUI 开发者的建议

1. **清除前总是先设置 BGC**：在任何 `\e[K`、`\e[J` 或 `\e[2J` 之前，通过 SGR 设置预期背景色。绝不假设终端的默认背景与你的主题匹配。

2. **用 `COLORTERM` 检测真彩色**：检查 `COLORTERM=truecolor` 或 `COLORTERM=24bit`，而不是解析 terminfo，后者对 RGB 支持不可靠。

3. **防御性处理 emoji 宽度**：使用 Unicode 15.1+ 宽度表并接受一些终端会不一致。考虑在网格对齐的 TUI 布局中避免 emoji，或用显式空格填充。

4. **SIGWINCH 时全量重绘**：不要在调整大小时增量修补屏幕。清空一切并从头重绘。

5. **退出时总是恢复终端状态**：使用清理处理器（即使对 SIGTERM/SIGINT），它：恢复光标可见性、离开备用屏幕、禁用鼠标捕获、禁用括号粘贴、重置 kitty 键盘协议并发出 SGR 重置。

6. **在 tmux 下测试**：如果用户可能在 tmux 内运行，在那里显式测试。许多渲染错误只在复用器下出现。

7. **对 Terminal.app 和 screen 优雅降级**：它们仍是常用终端中能力最低的。检测它们（通过 `TERM_PROGRAM` 或 `TERM`）并回退到 256 色模式和 ASCII 安全 UI 元素。
