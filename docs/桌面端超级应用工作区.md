# 桌面端超级应用工作区方向

状态：提案
更新：2026-04-25

本文把 Jcode Desktop 的产品方向从单一聊天式应用细化为一个 **Niri 式智能体工作区超级应用**。

应用最终应承载多种表面：

- 智能体会话
- 任务/活动视图
- 代码/文件表面
- diff
- 终端或命令输出表面
- 设置/认证/工具/调试表面

目标不是克隆一个通用窗口管理器。目标是给 Jcode 用户一个快速、键盘驱动、空间化的环境，在一个自定义桌面应用内监督多个智能体会话和相关开发工具。

- [桌面端代码库架构](桌面端代码库架构.md)
- [多会话客户端架构](多会话客户端架构.md)

## 产品论点

Jcode Desktop 应是一个**本地 AI 开发超级应用**：

```text
一个原生应用
  多个会话
  多种表面
  快速空间导航
  强键盘工作流
  智能体优先的活动可见性
  自定义渲染和布局
```

关键 UX 更接近：

- Niri / 可滚动平铺工作区
- 类 Vim 键盘导航
- 命令面板
- 智能体任务控制中心

而不是：

- 单一聊天窗口
- 传统 IDE 克隆
- web 应用外壳
- 通用桌面窗口管理器

## 为什么 Niri 式

Niri 对 Jcode 有用的想法不是合成器实现，而是心智模型：

- 表面按空间排列
- 焦点可预测地移动
- 用户用键盘优先命令导航
- 新工作出现在结构化位置
- 布局足够持久以建立肌肉记忆
- 许多并行任务可以被监控而不丢失上下文

Jcode Desktop 可以把这种工作流带给没有 Niri 式环境的 macOS 用户，同时在 Linux 上仍然工作良好。

## 工作区模型

桌面应用应围绕这些概念构建：

```text
Workspace（工作区）
  -> Rows / Workspaces / Lanes（行 / 工作区 / 通道）
    -> Columns（列）
      -> Surfaces（表面）
```

术语可以调整，但核心模型应支持：

- 多个智能体会话可见或快速可达
- 用 `h/j/k/l` 式移动做空间导航
- 在会话旁边打开相关表面
- 在列/通道之间移动表面
- 临时缩放/聚焦一个表面
- 按项目/工作区保留布局

建议的初始术语：

| 术语 | 含义 |
|---|---|
| Workspace（工作区） | 项目/仓库级桌面环境 |
| Lane（通道） | 垂直分组或 Niri 式工作区行 |
| Column（列） | 水平焦点/导航单元 |
| Surface（表面） | 可见应用面板：会话、文件/代码视图、diff、活动、设置、调试等 |
| Session surface（会话表面） | 附着到服务器拥有的 Jcode 会话的表面 |
| Tool surface（工具表面） | 文件/代码/diff/活动/设置/调试等 |

## 表面类型

应用从一开始就应围绕通用表面注册表构建。

```rust
enum SurfaceKind {
    AgentSession,
    Activity,
    WorkspaceFiles,
    CodeView,
    Diff,
    TerminalOutput,
    Settings,
    Debug,
    Extension,
}
```

一个表面应有：

```rust
struct SurfaceState {
    id: SurfaceId,
    kind: SurfaceKind,
    title: String,
    workspace_id: WorkspaceId,
    lane_id: LaneId,
    column_id: ColumnId,
    focus_state: FocusState,
    local_state: SurfaceLocalState,
}
```

表面模型应独立于渲染器，以便支持：

- 一个窗口多个表面
- 以后多个窗口
- 以后弹出表面
- 会话表面和非会话工具表面使用同一导航模型

## 智能体会话作为一等表面

智能体会话应是一种表面类型，而不是整个应用。

```text
AgentSessionSurface
  - 记录时间线
  - 组合器
  - 内联工具卡片
  - 会话状态
  - 会话本地队列/中断
```

这允许这样的布局：

```text
[Session A] [Session B] [Diff     ]
[Activity ] [Files    ] [CodeView ]
```

或者：

```text
Lane 1: 主任务
  Column 1: 协调者会话
  Column 2: 实现智能体会话
  Column 3: diff/编辑器

Lane 2: 审阅
  Column 1: 变更文件
  Column 2: 笔记/会话
```

## 导航模型

应用应有受 Vim 启发的模态/命令式键盘模型，但适配 macOS 和桌面预期。

### 重要 macOS 约束

不要依赖普通 `Cmd+H` 做左导航。

在 macOS 上：

- `Cmd+H` 隐藏应用
- `Cmd+M` 最小化
- `Cmd+Q` 退出
- `Cmd+W` 按应用惯例关闭当前窗口/表面
- `Cmd+,` 打开设置

覆盖这些会让应用对 Mac 用户显得不友好。

### 推荐的导航方式

使用以下之一或两者：

1. **Leader/命令模式**
   - 按 leader 键，然后 `h/j/k/l`。
   - 示例：焦点不在文本输入时用 `Space h`、`Space j`、`Space k`、`Space l`。
   - 或者用 `Cmd+K h/j/k/l` 作为命令和弦。

2. **直接高级快捷键**
   - macOS 上用 `Cmd+Option+H/J/K/L` 做焦点移动。
   - Linux 上用 `Ctrl+Alt+H/J/K/L` 或 `Super+Alt+H/J/K/L`。

Leader 模型更安全，因为它避免 macOS 保留快捷键，并与 Vim 肌肉记忆配合良好。

### 建议的初始键位

```text
焦点移动：
  leader h      焦点左移
  leader j      焦点下移 / 下一个通道
  leader k      焦点上移 / 上一个通道
  leader l      焦点右移

表面移动：
  leader H      表面左移
  leader J      表面下移
  leader K      表面上移
  leader L      表面右移

工作区/会话：
  leader n      新智能体会话
  leader s      会话切换器
  leader a      活动中心
  leader e      编辑器/文件表面
  leader d      diff 表面
  leader /      命令面板
  leader z      缩放聚焦表面
  leader x      关闭聚焦表面

智能体控制：
  leader Enter  按模式聚焦组合器 / 提交
  leader Esc    取消/停止聚焦的智能体运行，有风险时需确认
```

确切的 leader 键应可配置。合理默认：

- 焦点不在文本输入时用 `Space`
- 用 `Cmd+K` 作为通用命令和弦
- 用 `Ctrl+Space` 作为偏好显式模式进入的用户的替代

## 输入模式

应用应区分导航模式和文本输入模式。

```text
导航模式
  - hjkl 控制焦点/布局
  - 按键触发命令
  - 按设置，打字可以打开命令面板或聚焦组合器

文本输入模式
  - 按键编辑组合器/编辑器/输入
  - Escape 返回导航模式
  - 平台快捷键仍然有效：复制/粘贴/全选
```

一旦应用有文本输入表面，这至关重要。没有显式输入模式，全局 Vim 式按键会与文本输入冲突。

## 布局行为

第一个实现不需要完整 Niri 行为。它应从可以演进的更简单模型开始。

### MVP 布局

```text
单个应用窗口
  左侧边栏：工作区/会话
  中央表面网格：带聚焦表面的列
  右侧活动/检查器面板（可选）
```

MVP 导航：

- 聚焦下一个/上一个表面
- 在列之间左右移动焦点
- 在右侧打开新会话
- 关闭表面
- 缩放聚焦表面
- 活动面板切换

### 之后的布局

Niri 式可滚动布局：

- 每个通道的水平列
- 垂直通道/工作区移动
- 平滑动画焦点移动
- 持久表面位置
- 按工作区恢复布局
- 用鼠标拖动表面，但键盘仍为主
- 把表面弹出为原生窗口
- 把弹出表面停靠回工作区

## 表面生命周期

表面命令应在表面类型间保持一致。

```text
new-surface(kind)
close-surface(id)
focus-surface(direction)
move-surface(direction)
zoom-surface(id)
split-surface(kind, direction)
pop-out-surface(id)
dock-surface(id)
```

智能体会话特定命令变成 `AgentSession` 表面上的特化动作：

```text
send-message
cancel-run
soft-interrupt
background-tool
resume-session
fork-session
```

非会话表面以后可以添加特化命令，而不改变通用表面生命周期命令。

## 可选未来表面

现在不要预规划任何大型嵌入应用。工作区模型应保持足够通用以承载未来表面类型，但实现计划应聚焦智能体会话、活动、文件、diff 和命令路由。

如果以后考虑大型嵌入表面，它应经过自己的设计决策，而不是被初始桌面架构假定。

## 内置代码编辑器方向

内置编辑器是大型系统，在工作区/会话工作流强大之前应保持可选。

建议级别：

### 级别 1：文件查看器和外部编辑器

MVP 友好：

- 文件树 / 变更文件
- 只读文件预览
- 在外部编辑器中打开
- 外部打开 diff
- 复制路径/片段

### 级别 2：轻量代码查看器/diff 编辑器

有用且现实：

- 语法高亮文件视图
- 文件内搜索
- 内联 diff 查看器
- 以后接受/拒绝生成的变更
- 简单文本选择/复制

### 级别 3：真正代码编辑器

大但以后可行：

- rope 文本缓冲
- 可能的多光标
- 撤销/重做
- 语法高亮
- LSP 集成
- 诊断
- 补全
- 文件保存/重载冲突处理
- 大文件性能

### 建议

从级别 1 开始，然后级别 2。在智能体工作区、记录、活动和 diff 工作流变得出色之前，不要构建完整编辑器。

架构应通用地支持文件/代码表面，但不应过早承诺完整编辑器实现。

## 活动作为持久表面

对于超级应用，活动不应只是小面板。

活动应是一种表面类型，可以：

- 固定到侧面
- 作为完整表面打开
- 按工作区/会话/工具类型过滤
- 用相同表面命令导航
- 用于跳转到相关会话/工具输出

这很重要，因为 Jcode 用户可能并发运行许多智能体/任务。

## 命令面板作为通用路由器

命令面板应成为访问一切事物的通用方式：

- 会话
- 表面
- 文件
- 命令
- 设置
- 工具
- 文件和代码视图
- 后台任务
- 调试视图

它应由 `jcode-client-core` 中的共享命令注册表支撑，而不是每个 UI 单独硬编码。

## 数据模型补充

`jcode-client-core` 应包含工作区布局状态模型：

```rust
struct WorkspaceLayoutState {
    workspaces: Vec<WorkspaceNode>,
    active_workspace: WorkspaceId,
    active_surface: Option<SurfaceId>,
}

struct WorkspaceNode {
    id: WorkspaceId,
    name: String,
    lanes: Vec<LaneNode>,
}

struct LaneNode {
    id: LaneId,
    columns: Vec<ColumnNode>,
}

struct ColumnNode {
    id: ColumnId,
    surfaces: Vec<SurfaceId>,
    active_surface_index: usize,
}
```

表面本地数据应按类型分离：

```rust
enum SurfaceLocalState {
    AgentSession(AgentSessionSurfaceState),
    Activity(ActivitySurfaceState),
    WorkspaceFiles(WorkspaceFilesSurfaceState),
    CodeView(CodeViewSurfaceState),
    Diff(DiffSurfaceState),
    TerminalOutput(TerminalOutputSurfaceState),
    Settings(SettingsSurfaceState),
    Debug(DebugSurfaceState),
    Extension(ExtensionSurfaceState),
}
```

这保留核心规则：

> 会话是服务器拥有的运行时状态。表面是客户端拥有的 UI 状态。

## 渲染器影响

Niri 式超级应用增加自定义 UI 引擎的重要性。

UI 引擎必须支持：

- 嵌套拆分/列/通道布局
- 以后动画或平滑焦点移动
- 虚拟化表面
- 焦点环和活动表面指示器
- 不浪费空间的表面装饰/标题栏
- 缩放/聚焦模式
- 以后拖动重排
- 用于无障碍/调试的稳定 ID
- 廉价的离屏/非活动表面表示

不要时刻保持每个表面完全渲染。非活动表面应保留状态，但除非可见或预热，避免昂贵的布局/文本/渲染工作。

## 建议的第一个超级应用里程碑

更新早期假数据桌面原型，以证明超级应用模型，而不只是一个记录。

### 里程碑：假数据空间工作区

成功标准：

- Linux 上一个原生窗口
- 自定义 `wgpu` 渲染
- 带多个假智能体会话表面的工作区布局
- 用 leader + `h/j/k/l` 做焦点移动
- 打开/关闭/移动/缩放假表面
- 带假运行任务的活动表面
- 命令面板可以创建会话/活动/文件/diff/调试占位表面
- 记录表面独立虚拟化
- 调试 HUD 显示每表面布局/渲染统计
- 空闲 CPU 保持接近零

此阶段可选的非会话表面可以是占位符。重要的是证明工作区模型可以承载多种表面类型，而不承诺特定未来应用。

## 产品护栏

因为"超级应用"可能爆炸式扩张，保持这些护栏：

1. 智能体会话和活动是核心产品。
2. 非会话表面是支撑工具，不是第一个里程碑。
3. 外部集成应先于嵌入实现。
4. 键盘导航必须在鼠标拖动布局打磨之前工作。
5. 表面架构必须从第一天起就是通用的。
6. 在 diff/审阅工作流出色之前，不要构建大型嵌入应用。
7. 保持服务器作为会话和智能体的事实来源。

## 总结决策

Jcode Desktop 应成为一个**键盘驱动、Niri 式智能体工作区超级应用**。

初始桌面应用应证明：

- 多个会话表面
- 空间导航
- 通用表面生命周期
- 命令面板路由
- 活动可见性
- 多个可见表面下的性能

然后可以添加额外的文件/diff/工具表面，而不改变基本应用模型。
