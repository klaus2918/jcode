# 远程交接（设计草图）

状态：探索中。这里的内容都尚未实现。

## 想法

会话目前固定在其 `jcode` 服务器所在的机器上。远程交接意味着：**在需要时甚至可以在回合中途，把活动会话从一台主机移到另一台主机**，而不丢失记录、工具状态或用户的注意力。

三个动机故事：

1. **笔记本 → 桌面。** 电池快没电了，构建需要 8 核。`/handoff desktop` 把会话移到 `arch-linux-desktop`，本地 TUI 通过 SSH 重新挂接。
2. **桌面 → 笔记本。** 离开办公桌；隔夜运行应该继续在桌面上执行，但我想在笔记本上观看和控制。
3. **任何主机 → 手机/网页。** 同一个会话，瘦客户端，通过中继。

这实际上是人们混淆的两个不同原语：

- **迁移（Migration）**：会话的所有权转移到另一台主机（工作区、进程也一起转移）。
- **挂接（Attach）**：所有权留在原地，由远程客户端驱动（这更接近 `allow_session_takeover` 已经在做的事情，只是通过非本地传输）。

大部分价值在挂接。迁移是困难且较少见的那种。

## 已有什么

| 组件 | 位置 | 备注 |
| --- | --- | --- |
| 客户端间的会话接管 | `server/client_session.rs`（`allow_session_takeover`） | 处理所有者冲突、客户端实例身份、本地历史启发式。已经是正确的决策面。 |
| SSH ControlMaster 配置 | `app-core/src/ssh_remote.rs` | 命名主机、已验证的后台控制套接字、无头复用。 |
| Unix 套接字协议 | `server/socket.rs`、`client_api.rs` | 行分隔的 JSON `Request`/`ServerEvent`。形态上传输无关，代码上不是。 |
| 重载交接 | `server/reload.rs`、`restart_snapshot.rs` | 已经能在进程切换时序列化活动服务器状态。这就是迁移，只是少了网络。 |
| 中继 | `server/jade_relay.rs` | 到远程控制平面的长轮询桥；手机/网页路径。 |
| 工具框架 API | `jcode-harness-api{,-server}` | 第二个、更结构化的客户端界面。 |

重要的观察：**重载已经解决了迁移的状态传输一半**，**接管已经解决了挂接的所有权一半**。远程交接主要是把这两者通过一个不是本地套接字的传输打通。

## 设计

### 第 0 层：传输抽象

今天的客户端拨号 `socket_path()`。引入一个 `SessionTransport`，有三个实现：

- `Local(UnixStream)` —— 今天的路径，零行为变化。
- `Ssh(profile)` —— `ssh -S <control-socket> <target> jcode serve --stdio`，在 stdin/stdout 上分帧。复用现有的已验证 ControlMaster，因此没有新的认证面，jcode 中也不需要处理凭据。
- `Relay` —— 现有的 jade 中继分帧，用于无法 SSH 进入的主机。

这一层之上的所有东西继续使用相同的 `Request`/`ServerEvent` JSON。这是让其余一切变便宜的唯——个变更。

### 第 1 层：远程挂接

`/attach desktop` 或在会话选择器中挑选远程主机：

1. 解析 SSH 配置，确保控制主控存活（`is_control_master_alive`，否则 `spawn_control_master_terminal`）。
2. 打开传输，`Subscribe { target_session_id, allow_session_takeover: true, .. }`。
3. 远程服务器运行现有的接管决策。同样的冲突日志，同样的拒绝情形。远程客户端只是另一个客户端实例。
4. 记录回填使用现有的 `client_has_local_history` 路径，因此不会在慢速链路上重发整个会话。

需要显式设计的失败模式：回合中途断链。远程服务器应继续执行该回合（客户端断开时它已经这样做了），客户端应重新连接并从最后收到的事件 id 重放。这要求事件 id 在每个会话内单调，而今天并不能明确保证。无论是否做交接，都值得修复。

### 第 2 层：迁移

`/handoff desktop --move`。序列：

1. **目标端预检**：jcode 存在且版本兼容、工作区路径存在、git 远程/提交匹配、提供商凭据可用。大声拒绝而不是半途迁移。版本偏差是现实世界最可能的失败。
2. **静默**：完成或检查点当前回合。复用 `turn_streaming_mpsc.rs` 中的优雅关闭工具交接逻辑（`allow_reload_handoff`），它已经知道如何中断 bash 工具并记录可恢复的结果。
3. **快照**：复用 `restart_snapshot` 序列化会话状态，然后通过传输运送记录 + 快照 + 待处理队列。
4. **收养**：目标端收养会话，验证它可以渲染，然后将源端**退役**为墓碑，重定向任何本地重新挂接的客户端。
5. 源端保留只读副本 N 天。迁移时绝不删除。

v1 的非目标：移动正在运行的后台 bash 进程、打开的文件句柄或未提交的工作树状态。未提交的更改应通过*提交*（仓库已经偏好边做边提交）或带 diff 预览的显式 rsync 步骤处理，而不是静默处理。

### 所有权模型

任何时刻恰好一台主机拥有一个会话。写入会话记录的带心跳租约就足够了：

- 所有者每隔几秒续租。
- 潜在所有者只能在租约过期后夺取，或通过显式的 `--force`（会记录夺取行为）。
- 要避免的是脑裂；两台服务器追加同一个记录比短暂拒绝糟糕得多。

## UX

- `/remote add desktop` —— 现有的 ssh 配置流程。
- `/remote list` —— 主机、可达性、各自拥有的会话。
- `/attach desktop:<session>` —— 从这里驱动远程会话。
- `/handoff desktop` —— 把当前会话移到那里，然后远程重新挂接，让用户视野永不空白。这是关键细节：交接应该*看起来*什么都没发生，只多了一行状态变化。
- 当会话不在本地时，标题栏显示 `● desktop`，并带往返延迟。

## 未决问题

1. 远程工具权限提示是在客户端弹出还是由主机决定？我认为主机拥有策略，客户端只渲染提示。否则被攻破的客户端会提权。
2. 延迟：SSH 上每次接近击键的交互都没问题（局域网毫秒级，广域网可容忍），但流式渲染路径假定事件投递廉价。可能需要在传输层做合并。
3. 集群协调者是否跨主机？自然的扩展（在强力机器上派生工作者），但它会放大所有权问题。以后再说。
4. 信任边界：SSH 免费给了我们认证/授权。中继没有，在它承载完整会话控制之前需要一个真正的方案。

## 建议的第一个切片

只做第 0 层 + 第 1 层挂接，SSH 传输，不做迁移。这本身就有实际用处（从笔记本驱动桌面），复用现有的接管逻辑，并迫使完成其余一切所依赖的传输抽象和重连/重放修复。
