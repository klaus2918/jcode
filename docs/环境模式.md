# 环境模式

环境模式是一种**主动、常驻**的智能体模式：无需用户提示即自主工作，像大脑在睡眠中巩固记忆那样
照料记忆图谱、识别有用工作并代表用户行动，同时始终处于资源限制之内。

本文合并原「环境模式」与相关安全约束说明，并标注当前实现状态。
安全细节见 [安全系统](安全系统.md)，记忆细节见 [记忆系统](记忆系统.md)。

## 一、做什么

环境模式作为后台循环运行，一次遍历里同时做三件事（不是独立阶段）：

1. **园艺**：合并、修剪并强化记忆图谱；
2. **侦察**：分析最近会话、git 历史与记忆，理解用户关心什么；
3. **工作**：主动完成用户会乐意看到的任务。

关键设计决策：

- **同时只有一个实例**，无并行；
- **订阅优先**：默认用 OAuth（OpenAI/Anthropic），未显式配置绝不使用 API 密钥；
- **用户优先**：交互式会话始终优先于环境工作；
- **强模型**：用所选 provider 最强的可用模型（弱模型会做错误的主动工作而惹恼用户）；
- **自我调度**：智能体决定下次何时唤醒，受自适应资源限制约束。

```
调度层（事件触发器 / 定时器 / 资源计算器 / 持久化调度队列）
   → 资源门控（可以运行吗？）
   → 环境智能体（检查队列 → 侦察 → 园艺 → 工作 → schedule_ambient）
   → 输出（合并后的记忆图谱 / 提交与变更 / 信息组件）
```

## 二、环境周期

```
定时器/事件触发 → 资源计算器检查用量余量
   ├─ 超预算：延迟并重算间隔
   └─ 可运行：派生环境智能体
        → 检查调度队列（有待处理项则先做）
        → 加载记忆图谱
        → 园艺遍历：查重复→合并强化；查矛盾→解决；查衰退→修剪或重验证；对照代码库验证过期事实
        → 侦察遍历（同时）：分析最近会话中错过的提取、检查 git 历史、识别主动工作机会
        → 工作遍历：执行主动任务、存储新记忆
        → end_ambient_cycle(summary, schedule)
```

## 三、环境智能体工具

### `end_ambient_cycle`（必需）

每个周期**必须**以此结束；系统用它生成通知与信息组件展示。

| 字段 | 必需 | 说明 |
|---|:--:|---|
| `summary` | 是 | 已完成工作的可读摘要 |
| `memories_modified` | 是 | 创建/合并/修剪/更新的记忆数 |
| `compactions` | 是 | 本周期内上下文压缩次数 |
| `proactive_work` | 否 | 主动代码变更描述 |
| `next_schedule` | 否 | 下次唤醒时间 + 上下文（省略则回退系统默认） |

### `schedule_ambient`

周期中途也能调用，排队未来工作：`{ wake_in_minutes | wake_at, context, priority }`。

### 其他

- `todos`：智能体用它规划本周期（提供"计划了什么 vs 实际做了什么"的可视性，
  周期被中断时知道还剩什么）；
- `request_permission`：来自[安全系统](安全系统.md)，用于任何需要许可的行动。

## 四、意外停止的处理

模型可能因输出长度限制、API 错误或随机停止而中断：

1. 若回合结束时未调用 `end_ambient_cycle` → 注入**续接消息**
   （"你未调用 end_ambient_cycle 就意外停止了。若已完成请调用它并附摘要与下次调度；
   若未完成请继续。"）；
2. 第二次停止仍未调用 → 生成标记为 `incomplete` 的部分会话记录，压缩计数取系统指标，
   按 `max_interval_minutes` 调度默认唤醒，并记警告日志；
3. 若 `end_ambient_cycle` 里既无 `schedule_ambient` 也无 `next_schedule` →
   按配置调度默认唤醒并记警告（智能体应始终调度下次唤醒）。

## 五、系统提示词（每周期动态构建，含真实数据）

提示词包含：当前状态（上次周期、关机/空闲时长、活动会话数、周期预算）、
调度队列内容、最近会话列表（id/状态/时长/主题/提取状态）、
记忆图谱健康（总数、低置信度、未解决矛盾、缺嵌入、重复候选、上次合并时间）、
用户反馈历史、资源预算（provider、窗口剩余令牌、重置时间、用户使用率、本周期限额），
以及指令段：先用 todos 规划；优先级为「先做队列项 → 园艺 → 侦察主动工作」；
园艺优先做高价值维护（先重复与矛盾、再修剪，预算有余才验证过期事实）；
主动工作要保守（糟糕的惊喜比没有惊喜更糟），代码变更必须放 worktree 分支并经
`request_permission` 创建 PR；结束时必须调用 `end_ambient_cycle` 并调度下次唤醒。

## 六、资源自适应

### 用量跟踪

每次 API 调用（用户或环境）都记录 `UsageRecord{timestamp, source(User|Ambient),
tokens_input, tokens_output, provider}`。

### 速率限制发现

优先从响应头学习（`x-ratelimit-limit-requests`、`-remaining-requests`、`-limit-tokens`、
`-remaining-tokens`、`-reset-requests`）；响应头不可用时回退到保守默认值，
并根据是否发生限流错误调整。

### 自适应间隔

```
window_remaining = reset_time - now
user_rate        = 滚动平均(usage_log, source=User, 最近 1 小时)
user_projected   = user_rate * window_remaining
ambient_budget   = (tokens_remaining - user_projected) * 0.8      # 预留 20% 缓冲
tokens_per_cycle = 滚动平均(最近 5 个周期)
cycles_available = ambient_budget / tokens_per_cycle
interval         = window_remaining / cycles_available            # 无余量则等重置
interval         = clamp(interval, min_interval, max_interval)
```

行为规则：

| 条件 | 行为 |
|---|---|
| 用户正在会话中活跃 | 暂停环境，或把间隔乘以 3–5 倍 |
| 用户已空闲数小时 | 更频繁运行 |
| 命中速率限制 | 指数退避（间隔翻倍） |
| 连续 N 个周期无错误 | 逐渐缩短间隔 |
| 无响应头可用 | 从 30 分钟开始，按错误调整 |
| 接近窗口结束且预算有余 | 挤入额外周期 |
| 预算消耗超过 80% | 回退到最大间隔 |

### 两层调度

智能体层**提议**（`schedule_ambient` 给出"15 分钟后唤醒，上下文：检查 CI"），
系统层**约束**（结合用户/环境用量、速率限制、窗口剩余、活动会话算出最终值与定时器）。
因此：智能体说 10 分钟后但系统认为 30 分钟前不安全 → 推迟；说 6 小时后但预算闲置 → 提前；
用户开始交互 → 暂停；接近限流 → 指数退避。

### 事件触发器（仍受资源门控）

| 事件 | 优先级 | 理由 |
|---|---|---|
| 会话崩溃 | 高 | 可能错过记忆提取 |
| 会话关闭 | 普通 | 可能有未提取记忆 |
| git 推送 | 低 | 代码库变更，事实可能过期 |
| 用户空闲超阈值 | 低 | 做环境工作的好时机 |
| 显式 `jcode ambient trigger` | 立即 | 用户请求 |

### 调度队列

持久化项 `ScheduledItem{id, scheduled_for, context, priority, created_by_session, created_at}`。
规则：环境唤醒时首先检查；按优先级再按时间排序；过期项仍执行；预算超限可延迟但不丢弃；
同一时刻只有一个环境智能体（新触发器排队等待）。

## 七、provider 与模型选择

优先级链：OpenAI OAuth → Anthropic OAuth → （仅在配置显式选择加入时）API 密钥 / OpenRouter
→ 都不可用则禁用环境模式。

理由：OpenAI 与 Anthropic 有独立限流池，环境不会与交互会话抢配额；订阅制无按令牌成本；
按令牌付费的 provider **默认关闭**以避免静默烧钱。

| provider | 模型 |
|---|---|
| OpenAI OAuth | 最强可用 |
| Anthropic OAuth | 最强可用 |
| OpenRouter / API 密钥（选择加入） | 最强可用 / 可配置 |

规则：订阅允许使用（受自适应限流约束）；按令牌付费默认关闭、可配每日预算上限；
用户活跃时暂停或降到最低；命中限流积极退避；交互使用 Anthropic 时环境优先用 OpenAI（反之亦然）。

## 八、主动工作

上下文来自记忆（用户偏好与优先级）、最近会话（用户之前在做什么）、git 历史（活跃分支与最近变更）；
推断"用户最关心什么、有什么工作即将到来、什么会正面惊喜用户"；
行动范围为写/修测试、小规模重构、更新过期文档、修明显问题、清理 TODO（**不做未经请求的大型重构**）。

安全约束（见 [安全系统](安全系统.md)）：

- 所有行动都经分级（自动允许 / 需要许可）；
- **绝不直接推送到 main/master**，提交到独立分支（默认前缀 `ambient/`）；
- 代码变更需 worktree + PR，始终经过审阅；
- 变更小而聚焦；
- 每周期生成会话记录摘要；
- 尊重 `.gitignore` 与敏感文件；
- 用户可在 TUI 中看到环境工作与待处理许可请求。

## 九、信息组件

```
╭─ 环境 ─────────────────────────────╮
│ ● 运行中（园艺 + 侦察）            │
│ 队列：2 项（下一项：检查 CI）      │
│ 上次：12 分钟前——修剪 3、合并 1    │
│ 下次：约 18 分钟（自适应）          │
│ 预算：██████░░░░ 剩余 58%          │
╰───────────────────────────────────╯
```

字段：状态（`idle` / `running` / `scheduled` / `paused (rate limited)`）、队列数量与下一项预览、
上次周期时间与摘要、下次唤醒估计、预算条（用户用量 + 环境用量 + 剩余余量三段）。

## 十、配置

```toml
[ambient]
enabled = false                 # 默认关闭
# provider / model             # 默认按优先级链自动选择
allow_api_keys = false          # 默认仅 OAuth
# api_daily_budget = 100000     # 使用 API 密钥时的每日令牌预算
min_interval_minutes = 5
max_interval_minutes = 120
pause_on_active_session = true
proactive_work = true
work_branch_prefix = "ambient/"
visible = true                  # 是否在终端窗口中显示环境周期
```

按项目配置（项目级 `.jcode/config.toml`）：可整体 `enabled = false`，
或限制为仅园艺（`proactive_work = false`）。

## 十一、存储与上下文管理

```
~/.jcode/ambient/
├── state.json                  # 当前状态（状态、上次运行等）
├── queue.json                  # 调度队列（重启后持久）
├── usage.json                  # 自适应计算用的用量历史
├── transcripts/                # 每周期会话记录（安全系统的摘要来源）
└── logs/ambient-YYYY-MM-DD.log
```

上下文窗口管理：与交互式会话相同的压缩策略（**使用率达 80% 时压缩**），无特殊处理。

## 十二、通过记忆学习用户反馈

环境模式复用记忆系统本身学习用户的批准/拒绝模式，无需单独反馈机制：
用户拒绝主动变更 → 存入"用户拒绝了某类工作"的记忆；批准 → 存入正向记忆；
这些记忆随时间强化，自然影响后续优先级。之所以可行，是因为环境在决定做什么之前已经侦察过记忆。

## 十三、崩溃安全与恢复

原则：

- **原子写入**：图谱与状态先写临时文件再原子重命名，写入中途崩溃不会损坏数据；
- **增量检查点**：园艺到一半崩溃不应重做已完成部分（"最后处理"标记跟踪周期内进度）；
- **持久队列**：调度队列与许可请求在磁盘上，重启后存活；
- **中断的会话记录**标记为 `interrupted` 而非 `completed`。

重启后恢复：

1. **不重放错过的周期**——只跑一个检查当前状态的周期；
2. 距上次运行很久时自然产生积压（待提取的崩溃会话、待验证的过期记忆），智能体总是检查当前状态；
3. **过期的调度项仍然执行**（上下文仍有效，只是晚了）；
4. **恢复而非重启**：发现被中断的周期时从检查点继续。

## 十四、冷启动

首次运行时没有用量历史与反馈记忆，引导策略：从保守开始（仅园艺）→ 建立用量基线
（最初几周期只观察并跟踪用量模式）→ 积累 N 个成功且被认可的周期后逐步解锁主动工作；
用户也可配置跳过预热。

## 十五、CLI

```bash
jcode ambient status      # 查看状态
jcode ambient log         # 最近活动日志
jcode ambient trigger     # 手动触发一个周期
jcode ambient stop        # 停止环境模式
```
