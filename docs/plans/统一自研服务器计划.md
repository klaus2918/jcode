# 统一自研开发 / 普通服务器计划

> 状态：**已实现。**
>
> 本文保留为历史设计/发布计划。当前架构使用单个共享服务器，自研开发作为会话本地 canary 能力处理，而不是独立的专用守护进程/socket。
> 下面任何对 `/tmp/jcode-selfdev.sock`、`canary-wrapper` 或 `JCODE_SELFDEV_MODE` 的引用描述的是合并前架构或过渡步骤，而不是当前运行时设计。

## 目标

通过移除专用自研开发守护进程/socket 对并**把自研开发作为普通共享服务器上的会话能力**处理，减少 RAM 使用。

今天，普通会话和自研开发会话可能最终拥有独立的常驻服务器进程，这重复了：

- Tokio 运行时开销
- 分配器堆/碎片足迹
- MCP 池状态
- 嵌入/模型生命周期机制
- 事件缓冲、注册表、会话 map、集群 map
- 一般服务器基线 RSS

## 当前架构

### 普通模式
- 主 socket：运行时 `jcode.sock`
- 调试 socket：运行时 `jcode-debug.sock`
- 启动路径：`jcode` -> 默认客户端流程 -> 需要时派生 `jcode serve`

### 自研开发模式
- 主 socket：`/tmp/jcode-selfdev.sock`
- 调试 socket：`/tmp/jcode-selfdev-debug.sock`
- 启动路径：
  - 仓库自动检测或 `jcode self-dev`
  - `cli/selfdev.rs::run_self_dev()`
  - exec 进 `canary-wrapper`
  - wrapper 确保自研开发服务器存在于专用 socket
  - wrapper 针对该 socket 启动 TUI 客户端

## 代码检查的关键发现

运行时已经支持**每会话自研开发状态**：

- 协议 `Subscribe { working_dir, selfdev }`
- 服务器订阅处理可以只把该会话标记为 canary/self-dev
- `selfdev` 工具可用性已由 `session.is_canary` 门控
- 提示词添加已由 `session.is_canary` 门控
- clear/resume/headless 流程已按会话保留或推断 canary 状态

这意味着剩余的主要拆分不是会话模型，而是**启动 / 重载 / wrapper 管道**。

## 目标架构

### 一个共享服务器
- 主 socket：运行时 `jcode.sock`
- 调试 socket：运行时 `jcode-debug.sock`
- 自研开发会话与普通会话连接同一服务器

### 自研开发成为会话本地
客户端在以下任一为真时是自研开发：
- 显式 `jcode self-dev`
- 当前工作目录是 jcode 仓库（自动检测）
- 恢复的会话已是 canary

该客户端连接共享服务器并发送：
- `working_dir`
- `selfdev: true`

服务器然后：
- 把会话标记为 canary
- 为该会话注册 selfdev 工具
- 只对该会话包含 selfdev 提示词添加

### 调试 socket
有一个共享服务器，就有一个共享调试 socket。

后果：
- 无专用自研开发调试 socket
- 调试工具从同一服务器看到普通和自研开发会话
- 自研开发敏感动作仍由目标会话 canary 状态门控

## 重要策略决策

如果自研开发会话触发重载，它重载**共享服务器**。
这意味着所有客户端重新连接。

这是 RAM 节省最干净的设计。

重载选择的二进制应取决于**触发会话**，而不是服务器全局自研开发模式标志：

- 普通会话重载 -> stable / 启动器候选
- canary 会话重载 -> 仓库 / canary 候选

## 实现阶段

### 阶段 1 - 共享服务器路径上的客户端侧自研开发
**目标：** 阻止仓库自动检测强制独立的自研开发守护进程。

变更：
- 不把仓库启动自动改道进 `canary-wrapper`
- 引入仅客户端的自研开发信号（与服务器自研开发 env 分开）
- 继续使用普通服务器派生/连接路径
- 继续发送 `Subscribe { selfdev: true }`
- 阻止共享服务器子进程继承仅客户端的自研开发 env
- 停止服务器自研开发检测基于当前工作目录推断自研开发

预期结果：
- 在仓库内打开 jcode 默认使用共享服务器路径
- 会话仍成为 canary/self-dev
- 显式 `jcode self-dev` 命令可以暂时仍使用旧版 wrapper

### 阶段 2 - 把显式 `jcode self-dev` 移到共享服务器路径
**目标：** 让显式自研开发命令使用相同的共享服务器流程。

变更：
- 简化 `cli/selfdev.rs::run_self_dev()`
- 保留可选的 `cargo build --release`
- 设置仅客户端自研开发模式
- 通过普通客户端/服务器启动路径连接
- 标准用法中移除对 `canary-wrapper` 的需求

预期结果：
- 自动检测的自研开发和显式 `jcode self-dev` 共享一个服务器

### 阶段 3 - 会话定向重载选择
**目标：** 从重载/更新行为中移除服务器全局自研开发假设。

变更：
- 在重载处理中包含触发会话上下文
- 基于触发会话 canary 状态选择服务器 exec 目标
- 始终在共享服务器上运行重载监视器，但通过会话状态/请求策略授权

预期结果：
- 一个共享服务器仍能重载到正确的二进制

### 阶段 4 - 移除专用自研开发 socket 假设
**目标：** 完全退役独立 socket 模型。

变更：
- 弃用 `/tmp/jcode-selfdev.sock` 和 `/tmp/jcode-selfdev-debug.sock`
- 更新通过独立 socket 探测自研开发的文档、测试和脚本
- 简化调试/测试工具以使用共享调试 socket

## 风险 / 权衡

### 共享重载影响
自研开发触发的重载影响共享服务器上的所有客户端。
这是主要行为变化，也是 RAM 节省的关键权衡。

### 旧版工具假设
一些脚本和测试当前偏好自研开发调试 socket 路径，需要更新。

### 分散的基于 env 的逻辑
启动、热重载和服务器行为中有多个 `JCODE_SELFDEV_MODE` 检查；这些需要分离为：
- 客户端自研开发请求
- 服务器自研开发模式（旧版 / 兼容）
- 会话 canary 能力
