# 编译性能计划

本文档跟踪让 jcode 的自研开发 / 重构循环快得多的计划，同时不牺牲全功能构建。

另见：

- [`编译期隔离重构.md`](../编译期隔离重构.md)
- [`重构路线图.md`](../重构路线图.md)
- [`模块化架构RFC.md`](../模块化架构RFC.md)

## 目标

- 为正常使用和自研开发重载保留全功能构建。
- 让常见的自研开发编辑显著更便宜地编译。
- 减少定制需要重新编译的频率。
- 每个阶段后度量改进，停止没有回报的折腾。

## 当前基线（2026-03-24）

在当前树上本地测量：

- 热 `cargo check --quiet`：**约 8.5s**
- 热 `scripts/dev_cargo.sh build --release -p jcode --bin jcode --quiet`：**约 47.3s**

本次审计的额外观察：

- 之前一次偏热的 `cargo check` 运行落在 **约 12.3s**。
- 一次没那么热的 `cargo check --timings` 运行落在 **约 23.8s**。
- 之前的本地默认 `clang + mold` 设置在本机发布链接期间失败。
- `clang + lld` 在这里能成功链接发布版 `jcode` 二进制。

## 近期目标

对于不触碰广泛共享接口的常见自研开发编辑：

- 热 `cargo check`：**< 5s**
- 热 `cargo build` / 面向重载的构建：**< 20–30s**

对于共享/核心编辑，即使达不到同样的快路径，我们仍应努力显著低于今天的基线。

## 什么最重要（排序）

1. **工作区 / crate 边界**
   - Rust 在 crate 边界缓存最好。
   - 重型未触碰子系统应在完整构建中保持编译并可复用。
2. **好的边界设计**
   - 高变更逻辑不应存在于宽扇出 crate 或不稳定的共享类型中。
3. **`sccache`**
   - 对重复本地构建和 CI 是实际收益。
4. **快速、可靠的链接器配置**
   - 对 `cargo build` 和发布/自研开发重载构建尤其重要。
5. **重型子系统隔离**
   - 嵌入、提供商实现和大型 TUI/渲染代码应停止搅动无关构建。
6. **内循环的更窄构建目标**
   - 不需要时避免重建额外的 bin/目标。
7. **减少完全不需要重新编译的需求**
   - Issue #32 的定制记录和扩展点应让许多变更由配置/钩子/技能/数据驱动，而不是源码驱动。

## 执行计划

### 阶段 1 — 战术性构建速度胜利

- 为本地贡献者保持 `.cargo/config.toml` 保守。
- 使用 `scripts/dev_cargo.sh` 进行本地自研开发构建：
  - 已安装时自动启用 `sccache`
  - 在 Linux x86_64 上优先 `clang + lld`
  - 为 `jcode` 自研开发构建/重载路径使用专用 Cargo `selfdev` profile
  - 仍可通过 `JCODE_FAST_LINKER=mold` 选择 `mold`
- 通过该包装脚本路由重构影子构建。

### 阶段 2 — 度量和可重复性

标准自研开发检查点现在位于 `scripts/bench_selfdev_checkpoints.sh` 之后，它运行：
- 冷 `cargo check`
- 热触摸文件 `cargo check`
- 冷自研开发 `jcode` 构建
- 热触摸文件自研开发 `jcode` 构建

在捕获重构的可比较前后数字时使用它。

- 为冷/热 `check` 和 `build` 计时添加有文档的命令。
- 判断 ROI 时优先触摸文件计时（例如 `scripts/bench_compile.sh check --touch src/server.rs`）而不是无操作热缓存重跑。
- 每个结构阶段后跟踪计时增量。

### 阶段 3 — 工作区边界设计

精炼的分层目标、依赖规则和迁移指南位于 [`docs/模块化架构RFC.md`](../模块化架构RFC.md)。下面的 crate 列表是面向编译性能的目的地草图，应视为与该 RFC 兼容，而不是唯一可接受的最终打包。

提议的目的地布局：

- `jcode-core`
  - 协议、ID、消息类型、配置原语、共享工具类型
- `jcode-server`
  - 服务器生命周期、重载、套接字、集群、守护进程行为
- `jcode-agent`
  - 智能体轮次循环、工具编排、流处理
- `jcode-provider`
  - 提供商特质、共享提供商类型、路由/目录支持
- `jcode-embedding`
  - 嵌入模型集成和相关重型推理依赖
- `jcode-tui`
  - TUI 渲染、部件、状态归约、终端 UI 支持
- `jcode-tui-core`
  - 与根耦合最小的低级 TUI 辅助，包括流缓冲区和键绑定解析
- `jcode-selfdev`
  - 定制记录、迁移逻辑、自研开发产品化
- `jcode-build-support`
  - 自研开发构建命令、源码状态指纹、二进制渠道路径/清单

### 阶段 4 — 首次 crate 拆分

从杠杆最高的缓存边界开始：

1. `jcode-embedding`
2. 提供商支持 / 提供商实现拆分
3. 新扩展点工作落地后的自研开发/定制系统
4. 沿已在抽取的接缝进行服务器 / 智能体拆分

## 下一个边界评估

下一个明显的重型依赖边界不如已经落地的那些清晰安全/本地化：

- 提供商支持仍然高价值，但 `src/provider/mod.rs` 和相关实现足够广泛，下一次拆分应该精心设计而不是仓促进行。
- 未来的 `jcode-provider-core` / 提供商实现拆分仍然是最有前景的下一步编译速度动作，但它需要先进行边界设计，这样高变更的共享类型不会创建新的失效热点。

当前提供商边界立场：

- **已完成：** `jcode-provider-metadata` 用于稳定的登录/profile 目录数据和纯选择逻辑。
- **已完成：** `jcode-provider-core` 用于共享 HTTP 客户端加路由/成本/核心提供商值类型。
- **已完成：** `jcode-provider-openrouter` 用于 OpenRouter 特定目录/缓存/排名/模型规格支持。

- **已完成：** `jcode-provider-core::openai_schema` 用于纯 OpenAI schema 适配 / 严格规范化辅助。

## 根 crate 分解策略（2026-05-29）

之前的拆分创建了许多根从中重新导出的 `*-types` / `*-core` crate，但 `scripts/analyze_root_crate.py` 显示 **336K 根 crate 行中的 334K 仍然真正在根中**：重型逻辑留在薄门面之后。分析器（随本节提交）给出了完成这项工作所需的目标地图。随时运行它：

```bash
python3 scripts/analyze_root_crate.py          # 排序模块 + 阻塞 + 循环 + 反馈弧
python3 scripts/analyze_root_crate.py --full    # 完整反馈弧集列表
python3 scripts/analyze_root_crate.py --json     # 机器可读
```

### 核心问题：一个巨大的依赖循环

仅库模块图（排除测试代码）有一个单一的 **42 个模块的强连通分量 / 约 310K 行（crate 的 92%）**：`tui, server, provider, tool, cli, auth, agent, session, …`。当它们互相引用时，你不能把 `tui`/`server`/`provider` 剥离成独立 crate。这是*结构性*阻塞，也是"直接把大目录移出去"永远行不通的原因。

### 好消息：循环是浅的

42 模块循环只由 **46 条共 178 个引用的反向边** 维持，而且大多数是单引用的"偶然"耦合。打破这个小反馈弧集把图变成 DAG，之后模块自底向上剥离。最便宜优先（来自分析器）：

- **1 引用边（约 24 条）：** 例如 `agent -> tui`（一个 `write_generated_image_side_panel_page` 调用）、`tool -> tui`（一个 `tui::image::display_image` 导入）、`config -> auth`、`config -> tool`、`telemetry -> cli`、`bus -> provider`、`browser -> provider`。每条都是可以移到共享低级 crate 或反转到特质/回调后的单次调用/导入。
- **中等权重边：** `usage -> auth`（4）、`tool -> provider`（5）、`tool -> server`（5）、`sidecar -> provider`（7）、`agent -> tool`（9）、`import -> tui`（9）、`usage -> provider`（9）。
- **重型结构接缝（精心设计）：** `agent -> provider`（20）、`cli -> tui`（21）、`auth -> provider`（39）。这些是值得特质接缝的真正架构耦合。

### 执行顺序（自底向上，DAG 优先）

1. **基线指标。** 记录最大当前单元和完整构建墙时间的峰值 rustc RSS（`scripts/bench_compile.sh`），这样每次抽取的内存/编译收益都可测量。
2. **先打破便宜的反向边。** 通过把共享原语下移到现有低级 crate（`jcode-core`、`jcode-tui-*`）或反转到小特质之后，消除 1-2 引用耦合（图像辅助、单次配置查找、telemetry/cli）。重跑分析器；观察 SCC 缩小。
3. **抽取已干净的叶子。** 分析器标记"现在可抽取"的模块（无根内阻塞）：`background`、`prompt`、`safety`、`transport`、`replay`、`browser`、`perf`，加上许多 <400 loc 的叶子。这些不需要打破循环，立即缩小根 crate。
4. **处理重型接缝**（`auth↔provider`、`cli↔tui`、`agent↔provider`），在便宜边消失后用深思熟虑的特质边界。
5. **提升大子系统**（`tool` 29K、`provider` 35K、`server` 38K，然后 `tui` 125K），一旦它们不再在循环中。`tui` 最后走：几乎没有什么依赖它（DAG 的汇），所以一旦它自己的出站依赖成为 crate，它就能干净地提升并移除最大的单一编译单元。

### 为什么这直接减少编译内存

rustc 在代码生成峰值时把整个 crate 的 IR 保存在内存中，所以峰值 RSS 随最大编译单元的大小缩放。今天那个单元是 336K 行的根 crate（约 2.5-3 GiB/进程）。每个移入自己 crate 的模块都会缩小最大单元，降低每进程峰值 RSS，这正是让更多并行任务在没有 OOM 的情况下运行的原因（补充上面的内存自适应任务数）。它还锐化了增量缓存：编辑一个文件重建一个小 crate，而不是整个巨石。

## 结果：阶段 A/B/C（2026-05-29）和停止决定

巨石根 crate 被物理拆分为严格向下 DAG 的独立编译 crate。每个都是自己的 rustc 单元，所以每个都独立类型检查/代码生成，全局每进程内存峰值是各单元的最大值（不是总和）。

```
jcode（根：cli + bin）        依赖
  -> jcode-tui（tui + video_export）  依赖
       -> jcode-app-core（server/tool/agent SCC + 叶子）  依赖
            -> jcode-base（provider/auth/config/session/message/memory 基础）
```

每个 rustc 峰值的 `VmHWM` 地面真值（selfdev profile，单任务，`/tmp/peakrss2.sh`）：

| 单元 | 峰值 VmHWM | 注意 |
| --- | --- | --- |
| 巨石（之前） | **3.18 GiB** | OOM 杀死 15 GB/无交换机器的单元 |
| jcode-base | 1.126 GiB | 地板：底部 crate，内部依赖最少 |
| jcode-app-core | 1.176 GiB | base + 0.050 |
| jcode-tui | 1.280 GiB | app-core + 0.104（98K loc 只加 +0.104） |
| jcode（根 cli） | 0.664 GiB | 薄壳，cli 迭代的快速增量 |

**结果：最大单一编译单元 3.18 -> 1.28 GiB（-60%）。** 没有单元超过约 1.3 GiB，所以内存自适应任务限制器可以调度并行 rustc 任务而不会 OOM。提交：`4dd91a9c`（阶段 A）、`4aec863e`（阶段 B）、`f649daeb`（测试导入）、`85c96735`（阶段 C jcode-tui）、`2591c0e5`（test-support 特性恢复跨 crate `#[cfg(test)]` 辅助）。完整 `cargo check --workspace --all-targets` 干净。

### 为什么我们停在这里（上面的停止条件）

`jcode-tui`（当前 1.280 GiB 最大值）的进一步拆分经过分析并故意**不做**：

- **可行但低价值。** 渲染层已经依赖 106 方法的 `TuiState` 特质（`ui::draw(frame, app: &dyn TuiState)`），而不是具体 `App`；从渲染模块到 `app` 的生产反向边基本为零（`ui_input.rs` 中使用两个纯辅助/常量的一次），所以存在干净的 `app` vs `render` 切割。
- **但峰值是地板约束的，不是 tui 约束的。** `jcode-base` 单独已经是 1.126 GiB，因为每个 crate 都继承相同的外部依赖单态化（serde/tokio/reqwest/ratatui）。tui 的整个 98K loc 只比 app-core 多 +0.104，所以把它拆成约 49K 两半只会省约 30-50 MB，**无法**达到由基础地板结构性固定的"<1.13 GiB"目标。
- **它增加真正的维护成本：** 分割 1535 行的 `mod.rs` 胶水（视图模型类型 `DisplayMessage`/`ToolCall`/`ProcessingStatus`/`TuiState` 本身），并把每个特性转发链（jemalloc/embeddings/pdf/test-support）再扩展一跳。

根据停止条件，一旦约束峰值是共享基础地板，仅凭编译内存理由继续高变更重构就不合理。剩余杠杆（降低地板本身）是 profile 级（codegen-units/debuginfo）或依赖级（修剪/特性门控重型外部依赖），而不是进一步雕刻 crate。

## 结果：增量重建修复（2026-05-29）

结构拆分后，用 `cargo --timings` 和 `CARGO_LOG=...fingerprint` 归因内循环墙时间。两个非结构性缺陷对真实自研开发迭代的影响远大于任何剩余的 crate 大小效应：

1. **调整并行任务内存预算的大小**（`scripts/dev_cargo.sh`，提交 `83857b13`）。自适应限制器预算 2048 MiB/rustc，为旧的 2.5-3 GiB 巨石校准。最大单元现在约 1.28 GiB，那个过时数字把空闲的 15 GiB/8 核机器限制在 6 个任务。降到 1536 MiB/任务，让空闲机器使用所有核（受压机器获得一个任务：约 9 GiB 可用时 4 -> 5），同时保持 OOM 安全（悲观的 8 任务并发 RSS 约 6.7 GiB）。

2. **阻止 git 活动强制全树重编译**（`crates/jcode-build-meta/build.rs`，提交 `8d87b2c0`）。这是主导的内循环税。`jcode-build-meta` 嵌入每个 crate 通过 `env!("JCODE_*")` 消费的版本/git 元数据。它 (a) 声明 `.git/HEAD` + `.git/index` 为 `rerun-if-changed` 输入，并且 (b) 每次重跑自动递增持久补丁计数器。Cargo 在声明的输入比输出新时标记构建脚本脏、重跑它，然后通过 `StaleDepFingerprint` 强制重编译所有依赖者；计数器保证输出每次实际变化。净效果：任何 `git add`/`git status`/提交/并发智能体 git 操作都使整个图失效（base -> app-core -> tui -> cli）。

   修复：从已提交的 git 状态确定性派生开发补丁号（`base.patch + 自 base 标签以来的提交数`，HEAD 的纯函数），并删除 `.git/*` 重跑触发，保留 `Cargo.toml` + `JCODE_RELEASE_BUILD`/`JCODE_BUILD_SEMVER`/`JCODE_BUILD_GIT_*` env 触发，这样发布/分发构建仍嵌入精确元数据。

   测得（selfdev，热，本机）：

   | 场景 | 之前 | 之后 |
   | --- | --- | --- |
   | `git/index` 触摸后的构建（提交、`git add`、并行智能体） | 约 18-25s | **0.65s** |
   | `git/HEAD` 触摸后的构建 | 约 18s | **0.87s** |
   | 真实代码编辑后的构建（`jcode-base/src/lib.rs`） | 约 20s | 约 20s（正确不变） |

   开发 `--version` git 哈希在下一次真实重建前可能滞后于会话内最新提交；这是外观性的，发布构建（清理/覆盖）自动刷新。

"为什么一切刚重新编译？"的诊断配方：
`CARGO_LOG=cargo::core::compiler::fingerprint=info <cargo build> 2>&1 | grep -iE 'stale|dirty'`。
查找 `StaleItem(ChangedFile { reference: <build-script output>, stale: <some input> })` —— 它指明 mtime 超过构建脚本输出的确切 `rerun-if-changed` 输入。

### sccache：仅非增量

`sccache` 不能缓存增量编译单元。jcode 的所有常见 profile（`selfdev`、`dev`、`release`、`test`）都设置 `incremental = true`，所以在内循环中 sccache 产生 **0% 命中率**（跨 272 次真实编译和干净工作区/依赖重建测得），同时仍添加每个 rustc 的包装开销和误导性的"已启用"状态。

`dev_cargo.sh` 现在自动决定：

- **增量构建**（selfdev/dev/release/test，或 `CARGO_INCREMENTAL=1`）：跳过 sccache（`sccache_status=skipped-incremental`），因为它永远不会命中。
- **非增量构建**（`release-lto`，或 `CARGO_INCREMENTAL=0`）：启用 sccache，它真正产生缓存命中（CI、分发构建）。

覆盖：

```bash
JCODE_SCCACHE=on   scripts/dev_cargo.sh build --profile selfdev ...   # 强制启用
JCODE_SCCACHE=off  scripts/dev_cargo.sh build --profile release-lto ... # 强制禁用
CARGO_INCREMENTAL=0 scripts/dev_cargo.sh build --profile selfdev ...   # 使其可缓存
```

- 2026-05-29：使 sccache 增量感知。本机验证：`--print-setup` 对 `--profile selfdev` 报告 `skipped-incremental`，对 `--profile release-lto` 报告 `enabled`；`JCODE_SCCACHE=on` 和 `CARGO_INCREMENTAL=0` 都为 selfdev 重新启用它。旧的总是启用 sccache 下干净的 `jcode-azure-auth` 重建显示 `0/54` 缓存命中，确认之前浪费的开销。

### 远程构建主机快速失败 / 快速恢复

当 `JCODE_REMOTE_CARGO=1`（通常在 `~/.config/jcode/remote-build.env` 中设置）时，`dev_cargo.sh` 通过 `scripts/remote_build.sh` 把构建卸载到 `JCODE_REMOTE_HOST`。预检设计为在主机在线时远程构建"即插即用"，而不在离线时付出慢超时：

- 在 SSH 预检之前运行便宜的 `bash` `/dev/tcp` 可达性探针，因此离线主机在约 **1s** 内故障转移到本地 cargo，而不是等待完整 SSH `ConnectTimeout`（以前每次构建约 5s）。
- 最近失败后，后续构建使用更短的恢复探针超时（默认 **0.3s**），让停机期间的重复构建保持便宜。
- 恢复在**下一次构建**检测到：在线主机在几毫秒内回答 TCP 探针，所以立即恢复远程构建，没有冷却。
- SSH 配置使用 `ProxyJump`/`ProxyCommand` 时自动跳过探针（直接 TCP 探针到最终主机会误导），回退到正常 SSH 预检。

可调项（全部可选）：

```bash
JCODE_REMOTE_TCP_TIMEOUT=1            # 首次探针 TCP 超时（秒，可为小数）
JCODE_REMOTE_RECOVERY_TCP_TIMEOUT=0.3 # 主机最近离线时的探针超时
JCODE_REMOTE_DOWN_TTL=300             # 使用恢复超��的时间
JCODE_REMOTE_TCP_PROBE=0              # 禁用预探针；仅用 SSH 预检
JCODE_REMOTE_CARGO=0                  # 为一条命令完全禁用远程构建
```

- 2026-05-29：添加上述 TCP 预探针 + 恢复超时逻辑。本机验证（远程主机离线）：热自研开发编辑构建预检从首次构建的约 **5.0s** 降到约 **1.0s**，后续构建约 **0.3s**，而在线主机仍在下次构建重连（单元测试中 TCP 探针约 10ms 回答）。函数级单元测试覆盖可达/不可达探针、最近失败窗口和 `desktop-tailscale` 端点解析。

### 目标目录清理（`scripts/clean_target.sh`）

`target/` 目录跨 profile（dev/selfdev/release）和交叉编译缓存（`*-apple-darwin`、`*-pc-windows-*`、`linux-compat`）无界增长。本机达到约 84GB。臃肿的目标目录不直接减慢编译，但会耗尽磁盘并在空间不足时强制完整重建。

`scripts/clean_target.sh` **在并行构建运行时安全地**回收空间：

- 绝不触碰有活跃 `rustc`/`cargo` 进程（通过 `/proc/<pid>/cmdline` 扫描）���在近期活动窗口内写入（默认 20min，`JCODE_CLEAN_ACTIVE_WINDOW_MIN`）的 `target/<profile>` 目录。
- 默认模式只移除交叉编译/兼容缓存（按需重新生成）并报告将释放的内容。
- `--aggressive` 额外对过期 profile 运行 `cargo clean --profile <p>`（仍受活跃进程 / 近期写入保护约束）。

```bash

```

### 内存自适应 cargo 任务数

8 核/15 GiB 开发机器上最大的日常痛苦是**内存压力**：几个自研开发智能体同时构建，`.cargo/config.toml` 固定静态 `jobs = 6`。大型根 `jcode` crate 上的 rustc 峰值约 2.5-3 GiB RSS，所以 6 个并发 rustc 进程（跨一个或几个构建）在无交换机器上超调 RAM，`earlyoom` 杀死构建。静态任务数在两个方向都错：机器空闲时浪费核，忙碌时过度订阅内存。

`scripts/dev_cargo.sh`（`selfdev build` 使用的路径）现在每次运行时根据**当前可用**内存调整任务数：

- `select_build_jobs()` 读取 `MemAvailable` 并除以��任务内存预算（默认 **2048 MiB**，`JCODE_BUILD_MIB_PER_JOB`），然后钳制在 `[1, nproc]`。
- 它导出覆盖 `.cargo/config.toml` 中 `build.jobs` 的 `CARGO_BUILD_JOBS`。
- 空闲机器仍使用每个核；受压时新构建自节流（例如并行智能体构建期间约 5.9 GiB 可用时选择 **2 个任务**）。
- 显式 `JCODE_BUILD_JOBS` / `CARGO_BUILD_JOBS` 总是优先；无效值警告并回退到自适应调整。非 Linux 主机保持 cargo/`.cargo` 默认。

提交的 `.cargo/config.toml` 静态回退也从 `6` 降到 `4`，用于绕过包装脚本的直接 `cargo` 调用（对约 15 GiB 上的单次构建仍内存安全，但不再假设接近满核数）。

```bash
JCODE_BUILD_JOBS=2            # 为一条命令硬覆盖任务数
JCODE_BUILD_MIB_PER_JOB=2048  # 每个 rustc 任务的内存预算（默认）
scripts/dev_cargo.sh --print-setup   # 显示 build_jobs_status + cargo_build_jobs
```

- 2026-05-29：添加自适应调整。通过 `--print-setup` 和存根 cargo 测试台验证覆盖优先、无效输入落入自适应、预算极端钳制到 `[1, nproc]`，并且选择的 `CARGO_BUILD_JOBS` 导出到子 cargo 进程。真实的 `dev_cargo.sh check -p jcode-logging` 构建成功。

对于编译计时，优先可重复的触摸文件测量而不是无操作热缓存重跑：

```bash
scripts/bench_compile.sh check --runs 3 --touch src/server.rs
scripts/bench_compile.sh check --runs 3 --touch src/tool/read.rs
scripts/bench_compile.sh release-jcode --runs 3
scripts/bench_compile.sh selfdev-jcode --runs 3
scripts/bench_compile.sh build -- --package jcode --bin jcode
scripts/bench_selfdev_checkpoints.sh --touch src/server.rs --runs 3
```

`bench_compile.sh` 现在支持：

- `--runs <n>` 重复计时，带 min/median/avg/max 汇总
- `--touch <path>` 每次计时运行前模拟本地编辑
- `--json` 可脚本化输出
- `-- <extra cargo args>` 缩小测量的目标/包/bin/特性

`bench_selfdev_checkpoints.sh` 在该基础之上构建，为冷/热 check + build 比较产生单一标准自研开发检查点包。

- 热 `build` / 面向重载的构建时间是否实质性改善？

## 结果：前端并行、链接器、基础拆分和测试构建（2026-06-08）

这一轮聚焦在 crate DAG 已经就位后的热自研开发编辑循环。下面的每个声明都有测量支撑；负面结果与胜利一样刻意记录，这样我们不会重试它们。

### 剖析：热时间实际花在哪里

`jcode-base` 上的 `-Ztime-passes`（selfdev profile，单线程，干净单元）：

| pass | 仅 lib | lib + tests |
| --- | --- | --- |
| macro_expand | 0.5s | 1.5s |
| type_check | 5.3s | 6.5s |
| MIR_borrow_check | 7.2s | 9.7s |
| monomorphization collect | 5.1s | 6.8s |
| codegen_crate | 2.9s | 8-12s |
| LLVM_passes | 2.8s | 3-4s |
| **总计** | **约 24s** | **约 30-33s** |

要点：巨石的普通 `build`/`check` **约 80% 是单线程前端**（类型检查 + 借用检查 + 单态化收集）。代码生成只在**测试**构建中占主导（所有 `#[test]` 主体变成真实代码）。

### 胜利 1 — nightly 并行前端（`-Zthreads`）

因为瓶颈是前端，`rustc -Zthreads`（nightly）是单一最高杠杆。本机测得（Intel Ultra 7，8 逻辑核，selfdev profile）：

- `jcode-base` 干净重编译：**25.3s -> 12.7s**（`-Zthreads=4`）
- base 编辑全链重建端到端：**约 16s -> 约 10s**
- 8 核机器上超过 4 线程收益递减。

随 `scripts/dev_cargo.sh`（`configure_parallel_frontend`）发布：安装 nightly 工具链时对 `selfdev` profile 自动启用，隔离到 `target/selfdev`，这样不会搅动 rust-analyzer 的 `target/debug` 缓存。控制：`JCODE_PARALLEL_FRONTEND`、`JCODE_FRONTEND_THREADS`、`JCODE_DEV_TOOLCHAIN`。

### 胜利 2 — bin 链接优先 mold 而不是 lld

`jcode` 二进制约 **300 MB** `.text`（静态链接 aws-sdk、`tract` ML、ratatui、syntect、多个 rustls 副本……）。在重链接 bin 的热重建上（几乎每次增量构建）：

- lld：约 2.9s
- **mold：约 2.0s**

把 `dev_cargo.sh` 自动检测翻转为 mold 优先（lld 保持回退）。每次增量构建省约 0.8s。注意：更改链接器会更改 RUSTFLAGS，所以这落地后的首次构建做一次性完整重编译。（仅 dev/selfdev 路径；`release-lto` 链接保持不变——历史上 `clang + mold` 在这台机器上有发布链接问题。）

### 负面 — cranelift 代码生成后端

在 lib 和 test 构建上尝试 `-Zcodegen-backend=cranelift`。两者都**更慢**（lib 25.3s -> cranelift 更慢；base `--tests` 32.5s LLVM vs 34.2s cranelift）。瓶颈是前端，不是代码生成，所以 cranelift 更快代码生成的权衡在这里输了。**不要启用 cranelift。**

### 负面 — 把 provider/auth 拆出 `jcode-base`

假设：provider+auth 占 base 变更的约 70%；把它们拉进兄弟 crate 应该阻止提供商编辑重编译 base-core。

做了完整分析和完整执行：

- 映射模块��赖图；provider/auth 循环是 6 模块 SCC（`auth, provider, provider_catalog, subscription_catalog, usage, live_tests`）。
- 计算精确的传递切割：**17 个模块 / 114 个文件 / 约 75k LOC** 必须上移（provider、auth、usage、memory、memory_agent、compaction、sidecar、skill、goal、gmail、catalogs），留下**零剩余反向边**的**约 28k-LOC base-core**（已验证）。
- 在 worktree 中执行：创建 `jcode-provider-stack`，移动所有 114 个文件，重接 `app-core` 重新导出它。**完整构建通过，二进制运行，测试通过。**

然后测量，受控，低负载：

| 布局 | provider 编辑重建 |
| --- | --- |
| 未拆分（base 103k） | 约 10.4s |
| 拆分（provider-stack 75k + base-core 28k） | 约 10.1s |

**没有胜利。** `--timings` 分解显示原因：感谢 rmeta 流水线，`app-core` 在 `base` 完成**之前**就开始编译（base 在关键路径上只有约 2s，之后 app-core 接上）。而 `app-core + tui + bin` 主导链，不受拆分影响。拆分*中间* crate 只是把工作从已经重叠的路径移走。

**决定：回退。** 不为零测量收益发布 114 文件穿越 auth/billing 代码的移动。学到的一般规则：**一旦并行前端和 rmeta 流水线发挥作用，进一步拆分现有巨石收益递减到负**。杠杆是 crate *内容/重量*，不是 crate *数量*。

### 负面 — 把内联 `#[cfg(test)]` 测试移到单独目标

内联测试很大：base 1132 / app-core 830 / tui 1313 个 `#[test]`，约 49k LOC 测试代码。它们给 `cargo test -p jcode-base` 前端增加 **+5.7s（+23%）**，集中在代码生成（测试主体变成真实代码）。

但移出它们**没有帮助**：

1. 在普通 `build`/`check` 上它们已经被 `cfg` 门控掉，花费 **0s**。它们只在真正对该 crate 运行 `cargo test` 时花钱。
2. 把单元测试转换为 `tests/` 集成目标不可行：1132 个 base 测试触达私有内部；集成测试只看 `pub` 项，所以要么让大片 API 公开，要么添加仅测试访问器——破坏封装的大量折腾。
3. 即使拆分出去，`cargo test -p <crate>` 编译整个测试 cfg 单元；你不能便宜地只编译一个测试。那是 cargo 限制，不是结构问题。

**决定：内联单元测试保持原样。** 它们是白盒测试的正确结构，对构建循环零成本。

### 本轮之后的状态

对于普通 `build` 编辑循环，热 provider/base 编辑约 10s，现在是**平衡的串行链**，没有单一主导阶段：

```
provider/base 前端约 3s -> app-core 约 3s -> tui 约 2.7s -> bin 链接约 2s（mold）
```

结构性杠杆（crate 拆分、测试迁移）已耗尽。剩余真实杠杆是**产品级，不是机械级**：

- **依赖/二进制重量**（此处未测试）：300 MB 二进制静态链接完整 aws-sdk、`tract`（ML，用于嵌入）、syntect 等。把最重的栈特性门控在默认关闭的标志之后会削减每次构建的代码生成*和*链接。剩余概率最高的胜利；承诺前先测量。
- **死代码**：根 bin/lib 很大并携带死代码警告；修剪真正未使用的代码是唯一的"免费"结构性胜利。

### 负面 — 开发二进制的 `-C prefer-dynamic`

假设：约 2s 的 bin 链接由把所有东西静态烤进巨大二进制主导；`prefer-dynamic` 应该动态化它并削减链接。

用 `-C prefer-dynamic`（selfdev + nightly threads + mold）构建完整 bin，并在相同条件下背靠背测量增量重链接（触摸 `main.rs`）vs static+mold：

| 链接配置 | 热 bin 重链接 | 二进制大小 |
| --- | --- | --- |
| static + mold | 约 1.8-2.7s | 414 MB |
| prefer-dynamic + mold | 约 1.8-3.0s | 413 MB |

**没有胜利，二进制也没有变小。** `prefer-dynamic` 只动态化构建为 dylib 的 crate（基本上是 Rust std）；工作区 crate 和重型依赖（aws-sdk、tract、ratatui……）仍然是烤进 bin 的 `rlib`，所以链接做同样的工作。动态二进制运行还需要它的 `.so` 文件在 `LD_LIBRARY_PATH` 上，这会给 `selfdev reload` 路径增加脆弱性（reload 把二进制复制到 `~/.jcode/builds/current/`）。零收益的坏交易。

动态链接唯一会帮助的方式是把重型*依赖*栈编译为 dylib——这是产品级"依赖重量"杠杆，不是机械配置变更。

### 最终裁决

所有非产品编译杠杆现在都耗尽并有记录。发布的胜利：nightly 并行前端和 mold。其他一切（更多 crate 拆分、测试迁移、cranelift、prefer-dynamic）都测量并拒绝了。热编辑循环是平衡的约 10s 串行链；唯一剩余杠杆是产品级（修剪静态链接的依赖重量），明确超出范围。

## 增量缓存审计（2026-06-08）

审计增量构建缓存是否最优配置。它是最优的——但发现了一个静默破坏缓存复用的多智能体工作流细节。

### 配置：正确，无需更改

- `selfdev` / `dev` / `test` 都设置 `incremental = true`。✓
- sccache 对增量构建**故意跳过**（`dev_cargo.sh` 中的 `maybe_enable_sccache`）：sccache 不能缓存增量编译单元，所以在我们的增量 profile 上它会为 0% 命中添加包装开销。强制启用需要 `JCODE_SCCACHE=on`（并且要有用需要非增量 profile）。✓
- nightly 并行前端（`-Zthreads=4`）与增量兼容——已验证：真正空闲的无操作重建是 **0.4s**（纯指纹检查），所以 `-Zthreads` 不会打败依赖图缓存。✓

### 真正的问题：共享 worktree mtime 失效

观察到"无操作"重建（不触摸任何东西）花了 **46s** 而不是 0.4s。`CARGO_LOG=cargo::core::compiler::fingerprint=info` 显示原因：

```
stale: changed ".../jcode-provider-core/src/lib.rs"
  source_mtime > fingerprint_mtime   -> StaleDepFingerprint cascades to the whole graph
```

源码内容没有变化——只是它的 **mtime** 变了，因为**另一个智能体在同一个共享 worktree**（`/home/jeremy/jcode`）中在构建之间编辑文件。Cargo 以 mtime 为新鲜度键，所以对低级、高扇出 crate（例如 `jcode-provider-core`、`jcode-base`）的任何并发编辑都会使该 crate 及其下游一切失效，把 0.4s 无操作变成全链重建。

背靠背证明：构建 #2（空闲）= **0.4s**；构建 #3，在兄弟会话触摸 `inline_interactive.rs` / `info_widget_stability.rs` 之后，= **46.6s**。

### 纠正：共享 worktree 模型是有意的，而且它有效

上面的 46s "无操作"**不是缓存 bug**——它是共享构建模型��做本职工作。当几个智能体在**同一个** worktree 工作时，它们共享一个 `target/selfdev` 目录，所以：

- 智能体 A 编辑文件并构建 -> `target/selfdev` 现在包含 A 的变更。
- 智能体 B 构建 -> cargo 正确地只重建 A 触碰的 crate（B 的二进制必须包含 A 的编辑）并复用其他一切。B 在*消费 A 的编译*，这正是目标："一个智能体编译，人人受益。"

把智能体放在单独 worktree 对该目标**更糟**（完全没有共享）。自研开发构建系统用跨会话**去重**强化共享：`build_dedupe_key = worktree_scope : source_fingerprint : command`。如果智能体 B 在 A 已构建相同源码状态时请求构建，B *附加*到 A 进行中的构建，而不是启动第二个。

### 保持共享缓存高效的一条真正规则

`target/selfdev` 指纹**包含 RUSTFLAGS**，`-Zthreads` 和 `-fuse-ld=mold` 都是它的一部分（测得：更改任一强制约 2.5 min 完整重建并留下竞争的工件集）。所以共享缓存只有在 selfdev profile 的**每次**构建使用**相同标志**时保持热：

- `selfdev build` 总是通过注入标准 `-Zthreads=4 + mold` 标志的 `scripts/dev_cargo.sh` 路由。所有使用它的智能体完美共享（空闲无操作约 1s）。✓
- 绕过 `dev_cargo.sh` 的裸 `cargo build --profile selfdev` 使用不同标志 -> 触发完整重建并毒化下一次 `selfdev build` 的共享缓存。**避免它。** 总是通过 `selfdev build` / `dev_cargo.sh` 构建。
- rust-analyzer 使用 `target/debug`（单独目录），所以它**不会**毒化 `target/selfdev`。✓

无需配置变更；缓存本身已经最优。操作规则很简单：每个智能体以相同方式构建。
