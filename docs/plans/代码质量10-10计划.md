# 代码质量 10/10 计划

本文定义 jcode 的质量目标、达到它所需的标准，以及在不破坏产品的情况下实现目标的分阶段执行计划。

## 目标

把 jcode 从当前大约 **7/10 的整体代码质量**提升到持续的 **9+/10 工程标准**，并带一个在日常开发中感觉像"10/10"的务实目标：

- 干净构建
- 清晰模块所有权
- 小而可维护的文件
- 低风险重构
- 强测试
- 压力下行为可预测
- 防止回归的严格 CI 护栏

因为 jcode 是快速移动的产品，"10/10"**不是**"完美"。它意味着：

1. 缺陷更容易预防而不是引入
2. 贡献者能快速理解代码属于哪里
3. 仓库抵抗架构漂移
4. 风险区域测试良好且可观察
5. 质量不依赖记忆或英雄主义

## 当前问题

今天在代码库中观察到的主要问题：

### 1. 超大模块

几个文件对长期可维护性来说大得离谱。当前主要热点：

- `src/provider/openai.rs`
- `src/provider/mod.rs`
- `src/agent.rs`
- `src/server.rs`
- `src/tui/ui.rs`
- `src/tui/info_widget.rs`
- `tests/e2e/main.rs`

这些文件一次做的事情太多，造成审阅、测试和入职摩擦。

### 2. 警告与死代码债务

仓库当前容忍显著的警告预算，而不是瞄准零警告构建。还有多个宽泛的 `allow(dead_code)` 抑制隐藏漂移。

### 3. 失败路径严格性不一致

代码库包含大量 `unwrap`、`expect`、`panic!`、`todo!` 和 `unimplemented!` 用法。有些在测试中有效，但生产代码应更防御性和显式。

### 4. 测试集中

测试很多是好事，但一些测试覆盖集中在超大文件内，尚未提供理想的故障隔离。

### 5. 护栏存在但还不够严格

仓库已有有用的质量基础设施，但应收紧，使质量随时间自动改进。

## "10/10"的完成定义

当代码库达到以下状态时，我们认为此计划成功：

### 构建与 lint 质量

- `cargo check --all-targets --all-features` 干净通过
- `cargo clippy --all-targets --all-features -- -D warnings` 干净通过或非常接近，带狭窄、有理有据的例外
- `cargo fmt --all -- --check` 通过
- 警告数接近零并主动向下棘轮

### 结构质量

- 没有生产文件超过 **1200 LOC** 而无记录的原因
- 大多数生产文件低于 **800 LOC**
- 大多数函数保持在 **100 LOC** 以下，除非复杂性明确有理
- 主要领域有清晰边界和所有权

### 可靠性质量

- e2e 测试按功能拆分，而不是集中在巨型文件中
- 关键状态转换有定向测试
- 重载、流式、工具执行和集群协调有显式失败模式覆盖
- 存在针对内存、socket 生命周期和重连/重载行为的长期可靠性检查

### 安全质量

- 生产 `unwrap` / `expect` 使用显著减少，剩余处有理有据
- 宽泛 `allow(dead_code)` 抑制被消除或缩减为狭窄的本地允许
- 工具、shell、路径和凭据边界显式且已测试

### 贡献者质量

- 贡献者能说出代码属于哪里
- 重构规则已文档化
- CI 使回归难以合并
- 架构文档与现实一致

## 不可协商原则

1. **无大爆炸重写。** 增量重构。
2. **先做保持行为的变更。** 在改变逻辑之前抽取、移动、拆分和测试。
3. **质量必须可强制。** 优先 CI 护栏而非非正式预期。
4. **激进删除死代码。** 更简单的代码是更高质量的代码。
5. **在整个计划中保持产品可发布。**

## 要跟踪的指标

计划期间应反复检查这些指标：

- 警告数
- clippy 违规
- 宽泛 `allow(dead_code)` 抑制数
- 生产 `unwrap` / `expect` 数
- 前 20 大 Rust 文件
- 测试运行时间和 flake 率
- 启动时间、内存和重载可靠性

## 分阶段计划

## 阶段 0：阻止进一步恶化

**目标：** 停止质量变差。

任务：

- 为 clippy 和 all-target/all-feature 构建添加更严格的 CI 检查
- 向下棘轮警告策略
- 记录代码质量标准和文件大小目标
- 为质量计划建立跟踪的待办清单

成功标准：

- 没有新警告不知不觉合并
- 没有随意添加新巨型文件
- 贡献者能在仓库中看到路线图和标准

## 阶段 1：警告与死代码烧尽

**目标：** 恢复构建中的信号质量。

任务：

- 移除未使用变量、方法和陈旧辅助
- 用真正需要处的狭窄作用域 allow 替换宽泛 `#![allow(dead_code)]`
- 删除废弃代码路径
- 减少 TUI、记忆和 provider 模块中的死代码

成功标准：

- 警告数实质减少
- 死代码抑制成为例外而非默认

## 阶段 2：分解最大文件

**目标：** 消除主要可维护性风险。

优先级顺序：

1. `tests/e2e/main.rs`
2. `src/server.rs`
3. `src/agent.rs`
4. `src/provider/mod.rs`
5. `src/provider/openai.rs`
6. `src/tui/ui.rs`
7. `src/tui/info_widget.rs`

方法：

- 先抽取纯辅助函数
- 其次抽取类型和状态机
- 第三抽取领域特定子模块
- 移动期间保持公共接口稳定

成功标准：

- 每个热点文件实质变小
- 功能保持稳定
- 每次拆分期间测试保持绿色

## 阶段 3：强化错误处理

**目标：** 使失败模式显式且可恢复。

任务：

- 减少生产 `unwrap` / `expect`
- 用 `anyhow` / `thiserror` 改进错误上下文
- 分类可重试 vs 面向用户 vs 内部不变量失败
- 为畸形流、重连和工具中断路径添加测试

成功标准：

- 更少易 panic 的生产路径
- 更清晰的日志和更可诊断的失败

## 阶段 4：再平衡测试金字塔

**目标：** 让失败更快、更窄、更可操作。

任务：

- 按功能拆分 e2e 套件
- 为解析、协议和状态转换添加更多单元测试
- 为稳定渲染输出添加快照或黄金测试
- 为序列化、工具解析和补丁/编辑不变量添加属性测试
- 改进测试支持工具和隔离

成功标准：

- 更低的测试维护成本
- 失败快速定位到一个子系统

## 阶段 5：可靠性与性能护栏

**目标：** 让架构质量与运行时质量对齐。

任务：

- 添加或加强内存和压力检查
- 添加重复重载 / 附加 / 分离可靠性测试
- 跟踪启动和空闲资源回归
- 改进重载、socket 和 provider 流式周围的结构化诊断

成功标准：

- 回归在发布前被发现
- 长期运行行为可测量地稳定

## 阶段 6：完成棘轮

**目标：** 让质量自我维持。

任务：

- 从警告预算转向有效零警告构建
- 在可行处强制更严格的 clippy 规则
- 记录模块所有权预期
- 重构落地后审阅并刷新架构文档

成功标准：

- 没有特别清理推动时仓库质量保持高
- 代码库默认抵抗漂移

## 立即执行顺序

第一批具体动作：

1. 落地本质量计划和跟踪的待办清单
2. 收紧 CI 护栏
3. 开始警告/死代码清理
4. 拆分 `tests/e2e/main.rs`
5. 继续进入 `src/server.rs`

## 重构计划的工作规则

- 每一步必须能编译，或因非常明显的临时原因失败
- 优先移动代码而不改变行为
- 尽可能避免在同一提交中混合清理和功能工作
- 触及文件时让它比之前更干净
- 如果添加新的宽泛 allow 抑制，必须在 PR 中记录

## 验证矩阵

计划期间的最低验证：

- `cargo check -q`
- `cargo test -q`
- 触及区域的定向测试
- `scripts/check_warning_budget.sh`
- `cargo fmt --all -- --check`

触及核心编排或 provider 代码时更严格的验证：

- `cargo check --all-targets --all-features`
- `cargo clippy --all-targets --all-features -- -D warnings`
- `cargo test --all-targets --all-features`
- `cargo test --test e2e`

## 所有权

这是活跃的工程计划，不是一次性清理文档。预期：

- 里程碑完成时更新计划
- 待办项保持最新
- 进度在仓库中可见
- 每个完成的阶段留下比以前更强的护栏
