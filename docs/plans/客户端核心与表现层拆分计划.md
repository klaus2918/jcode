# 客户端核心与表现层拆分计划

状态：提案

本文档审计当前 TUI/客户端技术栈，并提议在可复用的 `client-core` 层与 ratatui/crossterm 表现层之间做安全、增量的拆分。

目标是让当前单表面客户端更易维护，同时解锁 [`多会话客户端架构.md`](../多会话客户端架构.md) 中描述的多表面方向。

另见：

- [`重构路线图.md`](../重构路线图.md)
- [`多会话客户端架构.md`](../多会话客户端架构.md)
- [`服务器架构.md`](../服务器架构.md)

## 执行摘要

今天客户端技术栈在功能上是拆分的，但结构上不是：

- `src/tui/app.rs` 拥有一个非常大的 `App` 状态对象，会话状态、传输状态、输入状态、瞬态 UI 状态和运行时句柄混在一起。
- `src/tui/app/*.rs` 表现得像一个分布式 reducer，但变更被表达为直接 `impl App` 方法，而不是类型化动作和 reducer 入口。
- `src/tui/ui.rs` 和 `src/tui/ui_*.rs` 已经大部分是纯表现，但它们仍然依赖非常宽的 `TuiState` trait 和几个进程全局渲染缓存。
- `src/tui/workspace_client.rs` 是进程全局可变状态，这是当前真正的 client-core 拆分和多表面客户端最清晰的阻碍。

最安全的计划是：

1. 先在现有 crate 内定义一个真正的 `client-core` 状态模型。
2. 在不改变行为的前提下，把纯状态和 reducer 移到该边界后面。
3. 把 ratatui 渲染、overlays、markdown、mermaid 和渲染缓存留在表现层。
4. 只有在边界干净之后，才考虑把 `client-core` 移入自己的 crate。

## 当前表现边界

渲染器已经通过 `src/tui/mod.rs::TuiState` 有部分边界。

那个边界有前景，但仍然太宽，因为它目前包含：

- 原始领域/会话访问
- 表面状态访问
- 认证/配置查找
- 渲染特定辅助函数，如 `render_streaming_markdown`
- 一些昂贵的派生计算和缓存行为
- 可变行为，如 `update_cost`

结果是 trait 充当倾倒点而不是窄表现模型。

## 代码中发现的具体痛点

### 1. `App` 太大且语义混杂

`src/tui/app.rs` 中的状态根承载：

- 领域状态
- 表面/控制器状态
- 传输状态
- 运行时句柄
- 表现相邻状态

这阻止了在当前 TUI 运行时之外复用。

### 2. 没有类型化动作/reducer 边界

主要 reducer 是隐式的：

- `local.rs::handle_tick`
- `local.rs::handle_terminal_event`
- `remote/server_events.rs::handle_server_event`
- `remote/input_dispatch.rs::*`
- `state_ui_messages.rs::*`
- `conversation_state.rs::*`

这些应变成命名状态切片上的命名 reducer。

### 3. 工作区状态是进程全局的

- `src/tui/workspace_client.rs`
  - 使用 `static WORKSPACE_STATE: Mutex<Option<WorkspaceClientState>>`

这与以下不兼容：

- 一个进程中的多个客户端实例
- 无全局重置的测试隔离
- 未来多表面客户端
- 干净的 client-core 提取

这个状态必须变成实例拥有的。

### 4. 渲染层仍然依赖全局

`src/tui/ui.rs` 中的示例：

- `LAST_MAX_SCROLL`
- `PINNED_PANE_TOTAL_LINES`
- 提示视口动画状态
- 可见复制目标

这些是表现关注点，但应变成渲染器实例状态，而不是进程全局状态。

### 5. 运行时循环和渲染紧密交织

`terminal.draw(|frame| crate::tui::ui::draw(frame, &self))` 出现在许多控制流路径中：

- `run_shell.rs`
- `turn.rs`
- `remote/reconnect.rs`
- `input.rs`
- `model_context.rs`

这让控制器提取更困难，因为重绘时机耦合到变更路径。

## 提议的拆分

## 第 1 层：`client-core`

拥有客户端行为和状态，但不拥有 ratatui 渲染或终端 I/O。

核心中允许：

- 客户端/会话/表面状态
- 用户意图、服务器事件、bus 事件和 tick 的归约
- 命令解析和路由决策
- 排队和挂起操作状态
- 工作区模型状态
- 功能开关和模式状态
- 为运行时适配器发出的 effects

核心中不允许：

- `ratatui`
- `crossterm` 事件类型
- 直接终端绘制
- 进程全局 UI 缓存
- 部件渲染
- mermaid/图片/markdown 渲染细节

## 第 2 层：表现

拥有所有 ratatui 和渲染时关注点。

包括：

- `src/tui/ui.rs` 和 `src/tui/ui_*.rs`
- `src/tui/info_widget*.rs`
- `src/tui/markdown*.rs`
- `src/tui/mermaid*.rs`
- `src/tui/session_picker*.rs`
- `src/tui/login_picker.rs`
- `src/tui/account_picker*.rs`
- `src/tui/usage_overlay.rs`
- `src/tui/visual_debug.rs`

表现应消费来自核心的窄不可变快照或只读 trait。

## 推荐的 Reducer API

不要从单个巨型 reducer 开始。

从切片 reducer 和一个协调器开始：

- `reduce_tick(state, now) -> Effects`
- `reduce_terminal_intent(state, intent) -> Effects`
- `reduce_server_event(state, event) -> Effects`
- `reduce_bus_event(state, event) -> Effects`
- `reduce_workspace_action(state, action) -> Effects`

建议类型：

- `ClientIntent`
  - 规范化的用户意图，而不是原始 crossterm 键
- `ExternalEvent`
  - 服务器事件、bus 事件、tick、生命周期事件
- `ClientEffect`
  - 供适配器执行的运行时工作

这保持 crossterm 和 ratatui 不进入核心。

## 提议的提取顺序

## Phase 0：文档和命名

- 落地本文档。
- 冻结未来核心切片的命名。
- 暂时不移动代码。

## Phase 1：在当前 crate 内引入状态切片

创建空的或轻填充的模块：

- `src/client_core/mod.rs`
- `src/client_core/state/mod.rs`
- `src/client_core/state/conversation.rs`
- `src/client_core/state/composer.rs`
- `src/client_core/state/turn.rs`
- `src/client_core/state/stream.rs`
- `src/client_core/state/remote.rs`
- `src/client_core/state/workspace.rs`
- `src/client_core/state/surface.rs`
- `src/client_core/state/features.rs`
- `src/client_core/state/notices.rs`

安全规则：

- 先移动类型
- 保持方法体在原地，直到状态干净编译

## Phase 2：提取最容易的纯 reducer

首次提取应该是最少耦合的文件：

1. `state_ui_messages.rs`
2. `conversation_state.rs`
3. `state_ui_input_helpers.rs`
4. `remote/queue_recovery.rs`
5. `state_ui_maintenance.rs`

为什么先做：

- 大部分是状态变更
- 终端/运行时耦合低
- 容易用单元测试覆盖

## Phase 3：把工作区状态移入应用实例

这是最高杠杆的架构修复。

在大型事件循环重构之前做：

1. 用 app/core 内的 `WorkspaceState` 替换 `workspace_client.rs` 全局静态状态
2. 保持相同的命令和行为
3. 调整 `remote/workspace.rs` 对实例拥有的状态操作

为什么现在：

- 移除最清晰的多表面阻碍
- 降低其他一切的未来复杂度

## Phase 4：提取远程事件归约

把 `src/tui/app/remote/server_events.rs` 拆分为：

- 核心归约
  - 状态转换
  - 显示消息变更
  - token 和工具调用记账
  - 状态转换
- 运行时适配器
  - `RemoteEventState` 解析胶水
  - 重绘策略
  - 传输特定缓冲

这是工作区状态之后最重要的 reducer 提取。

## Phase 5：提取规范化终端意图

不要把原始 `crossterm::Event` 放进核心。

改为：

1. 把按键解码保留在 `local.rs`、`remote.rs` 和 `input.rs`
2. 引入规范化意图，例如：
   - `SubmitPrompt`
   - `MoveCursorLeft`
   - `ScrollChatUp`
   - `OpenSessionPicker`
   - `ToggleCopySelection`
   - `NavigateWorkspace(Direction)`
3. 在核心中归约这些意图

## Phase 6：收窄渲染器边界

用以下之一替换当前宽的 `TuiState` 依赖：

- 一个窄得多的 trait，或
- 从核心状态构建的 `PresentationSnapshot`

推��方向：

- 从核心 + 表现拥有的缓存构建 `PresentationSnapshot`

这让昂贵的派生计算不进入临时 trait 方法。

## Phase 7：把运行时适配器移到 effects 后面

一旦 reducer 返回 `ClientEffect`，更新：

- `src/tui/app/local.rs`
- `src/tui/app/remote.rs`
- `src/tui/app/remote/reconnect.rs`
- `src/tui/app/run_shell.rs`

让它们变成薄壳：

- 收集外部事件
- 归约它们
- 运行返回的 effects
- 调度重绘

## Phase 8：可选的 crate 拆分

只有在 ratatui/crossterm 从核心 API 移除之后：

- 创建 `crates/jcode-client-core`
- 把 `src/client_core/*` 移入该 crate
- 把表现留���主 crate 或未来的 `jcode-tui-presentation` crate

不要从 crate 拆分开始。从边界开始。

## 拆分的测试策略

每个提取阶段都应保留现有用户可见行为。

建议检查：

- `src/tui/ui_tests` 和 `src/tui/app/tests.rs` 下的现有 TUI 测试
- 新 `client_core` 切片的聚焦 reducer 测试
- 去全局化 `workspace_client.rs` 后的工作区状态测试
- 使用捕获事件序列的远程 `ServerEvent` 归约测试

## 推荐的首个 PR 序列

如果这项工作立即开始，首个序列应该是：

1. 仅文档
   - 本��划
2. 仅类型移动
   - 引入 `client_core::state::workspace::WorkspaceState`
   - 暂时无行为变更
3. 安全行为移动
   - 让工作区状态实例拥有
4. reducer 移动
   - 提取 `state_ui_messages.rs`
5. reducer 移动
   - 提取 `remote/server_events.rs`

这个顺序在解锁最重要的未来架构工作的同时最小化风险。

## 首次拆分的非目标

不要在第一波中尝试这些：

- 重写渲染器
- 立即删除 `TuiState` 抽象
- 把 mermaid/markdown 渲染移入核心
- 一次重新设计所有 overlays/部件
- 从第一天引入巨大的 Redux 风格通用动作枚举
- 让独立和工作区模式成为独立应用

## 底线

拆分应该是：

- `client-core` = 实例拥有的客户端状态 + reducer + effects
- 表现 = ratatui 部件、布局、绘制、渲染缓存、视觉调试

最安全的首次提取不是渲染变更。它是让工作区状态实例拥有，然后提取现有伪 reducer，从显示消息和远程事件归约开始。
