# 多会话客户端架构（提议）

状态：已提议

本文档描述 jcode UI 架构从当前的**每客户端单会话**模型演进为带内置会话工作区管理的**多会话客户端**模型的提议。

目标是支持所有平台上用户的内置空间/多会话 UI，同时保留当前与 Niri 等工具一起使用的外部窗口工作流。

另见：

- [服务器架构](服务器架构.md)
- [集群架构](集群架构.md)
- [Windows支持](Windows平台.md)

## 摘要

今天，jcode 实际组织如下：

- **服务器**拥有许多会话。
- **每个客户端**通常挂接一个会话。
- **每个终端窗口/进程**通常托管一个客户端。

这给出了实用的映射：

- `session ≈ client ≈ process`

提议的架构把客户端模型改为：

- **服务器**仍然拥有许多会话。
- **许多客户端**可能同时存在。
- **每个客户端可能托管一个或多个会话表面**。

这把映射改为：

- `session = 服务器拥有的运行时`
- `surface = 会话的客户端侧挂接/视图`
- `client = 一个或多个表面的容器`

这保留独立窗口，同时启用内置多会话工作区。

## 目标

- 添加内置多会话工作区 UI。
- 保留当前独立客户端工作流。
- 保留与 Niri 等外部窗口管理器的互操作。
- 使 macOS 和其他平台成为空间多会话使用的一等公民。
- 避免把整个 TUI 栈重复到单独的"独立"和"工作区"应用中。
- 保持服务器作为会话的事实来源。

## 非目标

- 取代操作系统级窗口管理器。
- 为任意应用构建通用终端多路复用器。
- 要求所有用户采用工作区模式。
- 第一版支持来自同一会话的多个交互式挂接的完全并发编辑。

## 当前架构

当前高层模型：

```text
服务器
  ├── 会话 A
  ├── 会话 B
  └── 会话 C

客户端 1 -> 会话 A
客户端 2 -> 会话 B
客户端 3 -> 会话 C
```

实践中，每个客户端通常是自己的终端窗口/进程，因此今天想要空间布局的用户依赖外部窗口管理器。

这在 Linux 上用 Niri 等工具效果很好，但对跨平台内置工作区体验不够可移植。

## 提议架构

### 核心想法

服务器继续拥有会话，但客户端从单会话 UI 演进为**多会话外壳**。

```text
服务器
  ├── 会话 A
  ├── 会话 B
  ├── 会话 C
  └── 会话 D

客户端 1（工作区）
  ├── 表面 A -> 会话 A
  ├── 表面 B -> 会话 B
  └── 表面 C -> 会话 C

客户端 2（独立）
  └── 表面 D -> 会话 D
```

独立窗口变成只托管一个表面的客户端。工作区变成托管许多表面的客户端。

## 术语

### 会话

服务器拥有的运行时，包含：

- 对话历史
- 提供商/模型状态
- 工具执行状态
- 会话持久化
- 后台任务状态
- 记忆提取状态

会话**从根本上**不是窗口或进程。

### 表面（或挂接）

会话的客户端侧交互式或被动视图。

示例：

- 在内置工作区中显示的会话
- 挂接一个会话的独立 jcode 窗口

表面是会话在特定客户端中的 UI 表示。

### 客户端

托管一个或多个表面的 TUI 进程。

示例：

- 当前独立 jcode 窗口
- 未来多会话工作区客户端

## 关键设计规则

架构必须分离：

### 共享会话状态

由服务器拥有：

- 消息
- 流式/工具事件
- 模型/提供商选择
- 持久化元数据
- 后台执行状态
- 服务器端会话生命周期

### 表面本地 UI 状态

由特定客户端表面拥有：

- 输入草稿
- 光标位置
- 滚动位置
- 选择/复制状态
- 本地窗格焦点
- 窗格缩放/全屏状态
- 本地视口和布局放置

这种分离是支持以下内容所必需的：

- 同一会话随时间在不同地方显示
- 把会话弹出到独立窗口
- 把独立会话停靠回工作区
- 同一底层会话的不同本地视图状态

## 客户端模式

同一个客户端二进制应支持两种主要模式。

### 单表面模式

等价于今天的独立客户端：

- 一个客户端
- 一个表面
- 挂接一个会话

这应保持为许多用户的默认/简单心智模型。

### 多表面模式

工作区模式：

- 一个客户端
- 许多表面
- 内置空间导航和会话管理

此模式提供应用内会话管理器和工作区 UI。

## 与外部窗口管理器的互操作

保留与 Niri 及类似工具的互操作是核心需求。

内置工作区不得取代独立客户端。相反，两者都应保持一等公民。

### 所需工作流支持

- 在应用内工作区中挂接会话
- 把会话弹出到自己的独立客户端/窗口
- 可选地把独立会话停靠回工作区
- 允许多个独立客户端与工作区客户端共存

### 结果模型

- 许多客户端可能同时存在
- 每个客户端可能托管一个或多个会话表面
- 服务器仍然拥有底层会话

## 交互属主

对初始实现，一个会话应一次有**一个活动交互式表面**。

这意味着：

- 如果工作区表面被弹出到独立窗口，独立表面成为活动交互属主
- 工作区表面应消失或变成被动
- 停靠逆转该属主

这避免与以下内容的同步问题：

- 多个输入草稿
- 竞争提交
- 光标/焦点冲突
- 同一会话的重复交互属主

未来设计可能允许更丰富的镜像或被动预览，但 v1 应偏好每会话单一活动控制器。

## Niri 式工作区 UX

首选的第一个版本**不是**许多会话同时可见的平铺多窗格仪表盘。

相反，内置工作区应像 Niri 式空间会话管理器那样行为：

- 主视口一次显示**一个全尺寸会话**
- 每个会话占据工作区中的一个全屏逻辑单元格
- 左/右/上/下移动在工作区中移动**镜头**
- 每个工作区行像 Niri 的会话水平条带
- 上/下切换工作区行并恢复该行记住的焦点
- 新会话插入当前工作区行中**聚焦会话的右侧**

概念上：

```text
工作区 +1：[会话 C]
工作区  0：[会话 A] [会话 B]
工作区 -1：[会话 D] [会话 E] [会话 F]
```

这刻意**不是**带假空单元格的固定矩阵。

## 工作区地图 / 信息组件

内置信息组件应充当**工作区地图**，而不是文本密集的状态列表。

### 角色

组件应让用户一目了然：

- 当前是哪个工作区行
- 当前行中哪个会话被聚焦
- 左/右存在什么会话
- 上/下相邻行存在什么会话
- 每个非当前行中上次聚焦的是哪个会话
- 哪些会话在运行、完成、出错、等待或分离

### 布局模型

组件应渲染**水平条带的垂直堆栈**。

- 每行代表一个工作区
- 行中的每个矩形代表一个会话
- 只显示实际存在的会话
- 非当前工作区仍记住其上次聚焦的会话

这比合成网格更好地保留 Niri 心智模型。

### 视觉语言

组件应形状优先、文本最少。

每个会话表示为一个矩形。

建议的编码：

- **空闲** → 暗淡的轮廓矩形
- **聚焦** → 明亮或双轮廓矩形
- **运行中** → 动画矩形边框 / 类似旋转器的周边运动
- **完成** → 绿色矩形
- **等待** → 黄色矩形
- **错误** → 红色矩形
- **分离** → 独特轮廓样式（例如虚线或外部标记）

组件应避免在地图内部放冗长标签。会话名称和完整细节属于主头部/状态区域，而不是地图。

### 示例形状演进

一个会话：

```text
╔══════╗
╚══════╝
```

右侧加一个：

```text
┌──────┐  ╔══════╗
└──────┘  ╚══════╝
```

上移并在那里加一个：

```text
        ╔══════╗
        ╚══════╝

┌──────┐  ┌──────┐
└──────┘  └──────┘
```

真实 TUI 版本应使用颜色和动画，而不是文本标记。

## 客户端侧架构

当前的单一 `App` 对象太单体化，无法干净扩展到许多会话。客户端应拆分为层。

### `ClientShell`

全局进程/UI 状态：

- 终端事件循环
- 工作区布局
- 工作区移动的镜头/视口位置
- 焦点管理
- 键盘模式（普通/插入/命令）
- 表面管理
- 弹出/停靠编排
- 全局命令和通知

### `SessionController`

按会话的实时控制器：

- 订阅/恢复会话
- 提交消息
- 取消当前回合
- 应用模型/会话命令
- 接收并应用服务器事件
- 重连逻辑

### `SessionSurfaceState`

按表面的本地 UI 状态：

- 输入缓冲
- 光标位置
- 滚动状态
- 选择/复制状态
- 侧面板本地视口
- 本地焦点和缩放状态

### 共享会话渲染器

可复用的渲染层，可以把会话表面渲染到任意矩形。这是让独立和工作区模式复用同一 UI 栈的关键步骤。

## 建议的内部模型

```rust
struct ClientShell {
    surfaces: Vec<SessionSurface>,
    focused_surface: Option<SurfaceId>,
    mode: ClientMode,
    layout: LayoutState,
}

struct SessionSurface {
    surface_id: SurfaceId,
    session_id: SessionId,
    controller: SessionController,
    ui: SessionSurfaceState,
}

struct SessionController {
    // v1：每表面专用远程连接
    // v2：多路复用会话句柄
}

struct SessionSurfaceState {
    input: String,
    cursor_pos: usize,
    scroll_offset: usize,
    side_pane_focus: bool,
    zoomed: bool,
}
```

这启用：

- 独立模式 = 单表面客户端
- 工作区模式 = 多表面客户端

## 传输 / 协议策略

### 阶段 1：每个活动表面专用连接

最快实用路径：

- 一个客户端进程
- 每个活动会话表面一个远程连接

优点：

- 最少协议变更
- 复用当前面向会话的客户端行为
- 最容易证明工作区 UX

缺点：

- 每个托管表面更多开销
- 一个进程内重复的连接/重连机制
- 不是最干净的长期抽象

### 阶段 2：多路复用客户端协议

长期架构：

- 一个客户端连接可以订阅许多会话
- 请求和事件显式按 `session_id` 标记

示例：

```rust
Request::SendMessage { session_id, ... }
Request::Cancel { session_id, ... }
ServerEvent::TextDelta { session_id, text }
ServerEvent::Done { session_id, ... }
```

优点：

- 更干净的工作区原生设计
- 更低连接开销
- 对多会话客户端更清晰的事件路由

缺点：

- 更大的协议和服务器重构

建议：不要让 v1 阻塞在协议多路复用上。

## 键位绑定与导航

好的默认工作区绑定集是：

- 用 `Alt+h/j/k/l` 做工作区移动
- 为已在外部 WM 中使用这些绑定的用户提供可配置重映射（例如重映射到 `Super+h/j/k/l`）

客户端应支持模态拆分：

- **普通模式** → 工作区导航和布局操作
- **插入模式** → 聚焦会话接收键入输入

这避免文本输入和空间移动之间的冲突。

## 弹出 / 停靠工作流

### 弹出到独立窗口

1. 用户选择工作区表面。
2. 客户端派生挂接同一会话的独立 jcode 客户端。
3. 独立表面成为活动交互属主。
4. 工作区表面被移除或降级为被动。

### 停靠到工作区

1. 用户请求停靠独立会话。
2. 工作区客户端为该会话创建表面。
3. 工作区表面成为活动交互属主。
4. 独立客户端退出或分离。

## 互操作 API 面

架构应为外部和内部互操作暴露小型控制面。

潜在操作：

- `list_sessions`
- `list_surfaces`
- `workspace_state`
- `focus_session(session_id)`
- `open_session_in_window(session_id)`
- `dock_session(session_id)`
- `undock_session(session_id)`
- `move_session_to_workspace(session_id, position)`

这最初可以通过现有 jcode 控制通道提供，如：

- CLI 命令
- 主服务器协议
- 调试/控制套接字

确切的公共 API 形态不如为这些操作保留干净的内部模型重要。

## 推荐的 UI 方向

对第一个版本，偏好**全屏、镜头式工作区**而非真正的多窗格仪表盘。

原因：

- 更接近 Niri 心智模型
- 保持每个会话全尺寸且完全可读
- 使终端 UI 中会话间平滑移动更可行
- 简化渲染，因为只有当前会话需要完整实时焦点
- 稍后仍允许更丰富的概览模式

这以后可以成长为可选的可调整大小会话表面或更丰富的多可见工作区视图，但第一个版本应优化为流畅的类 Niri 体验。

## 迁移计划

### 阶段 0：渲染器提取

- 从当前 TUI 提取可复用的会话渲染层。
- 不再假设一个 `App` 拥有整个终端表面。

### 阶段 1：表面/控制器拆分

- 把当前单体客户端状态拆分为外壳/控制器/表面层。
- 保持单表面行为不变。

### 阶段 2：工作区模型 + 地图组件

- 引入 Niri 式工作区行模型。
- 添加只渲染矩形的状态工作区地图信息组件。
- 跟踪每工作区行记住的焦点。

### 阶段 3：全屏镜头导航

- 允许一个客户端进程托管多个会话表面。
- 一次显示一个全尺寸会话。
- 在相邻会话/工作区之间移动视口。

### 阶段 4：弹出支持

- 添加在独立客户端中打开托管会话的命令。
- 保留当前 `jcode --resume <session>` 工作流。

### 阶段 5：停靠支持

- 允许独立会话重新挂接到工作区客户端。
- 每会话保持一个交互属主。

### 阶段 6：协议清理

- 评估会话多路复用协议支持。
- 在明显有益时替换每表面专用连接。

## 开放问题

- v1 中应存在被动镜像表面，还是会话一次应只在一个可见位置存在？
- 侧面板状态的哪些部分按会话作用域 vs 按表面作用域？
- 工作区模式应成为新命令（`jcode workspace`）还是普通客户端的运行时模式？
- 停靠/取消停靠应如何暴露：命令面板、斜杠命令、CLI、调试套接字，还是全部？
- 工作区布局状态在启动之间应持久化多少？
- 为平滑动画应预渲染多少离屏会话状态？

## 建议

采用以下设计方向：

1. **把客户端扩展为支持多个会话表面。**
2. **保持服务器作为会话的属主。**
3. **保留独立客户端为一等公民。**
4. **把工作区窗格和独立窗口视为同一会话模型的不同表面。**
5. **从每会话一个活动交互式表面开始。**
6. **把 Niri 式全屏工作区配合只渲染矩形的工作区地图组件作为主要 UX。**
7. **在尝试协议多路复用前，先每个活动表面一个连接地原型化。**

这给 jcode 一个可移植的内置多会话工作区，而不牺牲现有工作流或外部窗口管理器互操作。
