# Jcode 服务器记忆事件处理手册

状态：有效的运维处理手册
更新日期：2026-07-14

本手册回答两个问题：

1. 什么占用了 jcode 服务器的内存？
2. 针对该具体原因，最安全的下一步行动是什么？

目标不是对每个高 RSS 值做出反应。目标是在更改或停止任何东西之前，区分活动应用状态、分配器留存和非堆映射。

## 一条命令的初步诊断

运行：

```bash
jcode debug 'server:memory-incident'
```

这是事件期间的第一个命令。它刻意保持轻量。它不锁定或序列化每个智能体会话记录，因此在数千个会话常驻时仍然有用。

报告包括：

- RSS、PSS、匿名 PSS 和分配器活动字节
- 15 分钟 PSS 增长
- 活动、无头、分离和已连接会话计数
- 常驻会话的状态计数
- 常驻智能体最多的集群
- 严重程度和主要成因分类
- 按顺序排列、针对原因的行动

在更改状态之前，将 JSON 输出保留在事件记录中。

## 离线时间线分析

运行时内存日志默认启用，并按日写入 JSONL 文件：

```text
~/.jcode/logs/memory/
```

分析最新的服务器进程生命周期：

```bash
python scripts/analyze_runtime_memory_log.py --days 1
```

分析器默认选择最新的服务器和客户端进程实例。这很重要，因为跨服务器重载比较 PSS 会产生虚假峰值。仅对显式跨实例取证使用 `--all-instances`。

列出记录的进程生命周期并直接选择重载前的事件：

```bash
python scripts/analyze_runtime_memory_log.py --days 1 --list-instances
python scripts/analyze_runtime_memory_log.py --days 1 --instance <server-instance-id>
```

事后分析优先使用 `--instance`。它保留一个连贯的进程生命周期，不会把高内存服务器与低内存替代品混在一起。

机器可读输出：

```bash
python scripts/analyze_runtime_memory_log.py --days 1 --json > /tmp/jcode-memory-analysis.json
```

## 严重程度阈值

内置事件报告使用这些初始运维阈值：

| 信号 | 警告 | 严重 |
|---|---:|---:|
| PSS | 1 GiB | 2 GiB |
| 15 分钟 PSS 增长 | 256 MiB | 1 GiB |
| 常驻智能体会话 | 128 | 512 |

阈值启动调查。它本身不授权破坏性清理。

## 决策树

### 1. `runaway_live_session_population`（会话数量失控）

证据：

- 活动智能体数量高或快速上升
- 无头或分离会话数量远超已连接客户端
- 分配器活动字节随会话数上升
- 一个或多个集群主导 `top_live_swarms`

行动：

1. 暂停或限制创建会话的生产方。
2. 运行 `jcode debug 'swarm:list'` 并检查最大的活动集群。
3. 从所属协调器使用 `swarm list` 和 `swarm cleanup` 移除其不再需要的工人。
4. 不要盲目销毁会话。先确认活动工作是可丢弃的。
5. 重新运行 `server:memory-incident`。要求活动会话、分配器活动字节和 PSS 一起下降。
6. 只有释放但持有的内存仍然很高时，才运行 `allocator:purge`。

原因：分配器清理无法释放活动的智能体运行时。

### 2. `allocator_retention`（分配器留存）

证据：

- 分配器留存-常驻估计至少 256 MiB
- 留存-常驻内存至少占 PSS 的 25%
- 分配器活动字节明显低于匿名 PSS

行动：

```bash
jcode debug 'server:memory-incident' > /tmp/before.json
jcode debug 'allocator:purge'
jcode debug 'server:memory-incident' > /tmp/after.json
```

PSS 大幅下降确认分配器留存。如果它反复回升，检查分配抖动和分配器衰减，而不是提高内存预算。

### 3. `session_payload_growth`（会话负载增长）

证据：

- 已跟踪的会话记录/提供商缓存/工具/Blob 字节至少解释分配器活动内存的一半
- 一个或多个会话主导 `top_by_json_bytes`

行动：

1. 运行 `jcode debug 'server:memory'` 进行完整的归因遍历。
2. 检查提供商缓存、工具结果、大 Blob 和负载文本。
3. 压缩、摘要、截断或将大型工件移出热路径。
4. 在接受更大的稳态之前，添加或收紧硬上限。

### 4. `unattributed_live_heap`（无法归因的活动堆）

证据：

- 分配器活动字节超过 1 GiB
- 会话数量和分配器留存无法解释堆
- 活动堆归因覆盖率仍低于 50%

行动：

1. 捕获 `server:memory` 和运行时日志分析。
2. 为任何明显缺失的属主添加计数器。
3. 如果归属仍不清晰，使用 `jemalloc-prof` 构建：

```bash
jcode debug 'allocator:profile:on'
jcode debug 'allocator:profile:dump /tmp/jcode-server.heap'
```

普通系统分配器构建无法产生分配栈分析。不要仅凭 RSS 声称堆归属。

### 5. `non_heap_or_mapping_growth`（非堆或映射增长）

证据：

- PSS 高但分配器活动字节不高
- 文件支持、共享内存或线程栈映射在增长

行动：

```bash
cat /proc/<server-pid>/smaps_rollup
pmap -x <server-pid> | sort -k3 -nr | head -40
ps -T -p <server-pid> -o pid,tid,%cpu,time,comm,wchan:32
```

调查分配器之外的模型映射、共享内存、线程创建或大型匿名映射。

## 升级阶梯

先使用最便宜可靠的证据：

1. `server:memory-incident`，通常亚秒且非阻塞
2. 运行时 JSONL 分析器，进程生命周期趋势和事件分类
3. `server:memory`，昂贵的按智能体归因
4. 分配器清理 A/B 测试，仅用于留存
5. jemalloc 堆分析，仅用于无法解释的活动堆
6. OS 映射和 CPU 分析器关联

## 必需的事件记录

保存：

- 服务器 ID、版本、git 哈希和运行时长
- PSS、匿名 PSS、分配器活动和留存-常驻字节
- 活动/无头/已连接会话计数
- 顶部活动集群和状态计数
- 15 分钟增长
- 所选行动及前后测量
- 活动工作是否被保留

## 解决标准

只有以下情况之一成立时，事件才算解决：

- 已识别活动属主被减少，PSS 相应下降
- 分配器清理证明是留存，且复发机制已修正
- 映射增长已被识别并限制
- 堆分析识别了属主，且添加了回归测试或上限
- 高稳态被证明是有意的、已记录文档，并给出显式预算

不要只凭"重启后内存下降"就关闭事件。重启会抹掉证据，且不能识别原因。
