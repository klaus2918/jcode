# 账号流程：可观测性、隐私与支持诊断

六个订阅账号流程的安全日志、审计事件、指标、追踪、告警、脱敏、保留和支持诊断：（1）设备登录，（2）浏览器批准/拒绝，（3）账号状态（`/v1/me`），（4）结账，（5）计费门户，（6）webhooks/撤销。

与 `docs/dev/账号契约一致性测试.md` 配套。客户端表面在本仓库中；后端表面在 `solosystems-backend` 中。

## 永不记录清单（两个仓库，由测试强制）

这些值在任何日志级别下都绝不能出现在日志、遥测、追踪、崩溃报告或支持包中：

- `api_key`（JCODE_API_KEY）——完整或超过 `jc_...last4` 的截断。
- `device_code`、magic-link token、批准 URL 查询参数。
- 遥测中的原始邮箱地址（本地日志可以显示用户已在屏幕上看到的内容；遥测不得携带邮箱；后端审计日志只在审计表中存邮箱，不在应用日志中）。
- Stripe secret：webhook 签名 secret、客户支付详情、完整结账/门户会话 URL（它们嵌入会话 secret）。
- env 文件内容（`jcode-subscription` env 文件）和任何 HTTP 客户端调试日志中的 `Authorization` 头。

强制：SN-03 一致性测试 grep 捕获的登录输出；添加一个 CI grep 遍历 `record_*` 调用点，断言只有脱敏标签流入遥测（所有认证标签已经过 `sanitize_telemetry_label`）。

## 审计事件（后端，持久）

以 `account_id` 为键的追加式审计表，保留 400 天：

| 事件 | 必需字段 |
|---|---|
| `device_auth.requested` | account_id?、email_hash、ip_hash、user_agent 类别、device_code_id（不透明 id，非代码本身） |
| `device_auth.approved` / `denied` | device_code_id、批准者会话 id、原因 |
| `device_auth.expired` | device_code_id |
| `key.issued` | key_id（非 key）、tier |
| `key.revoked` | key_id、行为者（user/portal/admin/system）、原因 |
| `checkout.started` / `completed` / `abandoned` | stripe session id、目标 tier |
| `portal.opened`、`subscription.updated` / `canceled` | stripe id、旧->新 tier/状态 |
| `webhook.received` / `applied` / `rejected` | stripe 事件 id、类型、签名结果、去重结果 |
| `me.tier_changed` | 旧、新、原因（webhook/admin） |

关联要求：每个审计行携带 `account_id`、`request_id`（每个 HTTP 请求）和 `flow_id`（一次设备登录尝试或一次结账尝试）。`device_code_id` 链接流程 1-2；`stripe_event_id` 链接 4-6。客户端今天不发送关联 id；如果添加，只用随机的每次尝试 UUID，绝不把遥测 install id 与 account_id 加入同一事件（保持匿名遥测与账号不可关联）。

## 客户端遥测（本仓库，匿名）

保持当前形态：成功事件带粗粒度 `auth_provider` +
`auth_method`（"jcode-subscription"、"device_code_magic_link"），失败原因限制为 `AuthFailureReason::label` 值。新增：

- 镜像 `auth_success` 的 `auth_failure` 事件（仅原因标签）。
- 轮询循环结果计数器：approved/denied/expired/slow_down/error，加分桶的批准耗时（如 <30s、<2m、<15m）——没有精确到足以与后端日志关联的时间戳。
- **不要**向 `AuthEvent` 添加 `account_id`（`src/cli/login/jcode_device.rs:370` 的现有 TODO 应解决为"后端审计拥有账号关联事件；客户端遥测保持匿名"）。

## 指标与告警（后端）

指标（按流程，适用时按结果和 tier 标记）：

- `device_auth_requests_total`、`device_auth_approvals_total`、
  `device_auth_denials_total`、`device_auth_expiries_total`；
  告警：1 小时内批准率 < 50%，或过期率 > 40%（邮件投递问题），或请求尖峰 > 基线 10 倍（枚举/滥用）。
- `token_poll_requests_total{result}`；`slow_down` 比例 > 20% 时告警
  （客户端行为不当或攻击），意外 5xx 比例 > 1% 时告警。
- `me_requests_total{status}`；401 尖峰（大规模撤销 bug）和
  p99 延迟 > 2s（客户端超时是 5s：`ME_FETCH_TIMEOUT`、
  `crates/jcode-base/src/subscription_api.rs:14`）时告警。
- `webhook_events_total{type, outcome=applied|duplicate|rejected}` 和
  `webhook_apply_lag_seconds`（Stripe `created` -> 状态应用）；
  告警：持续有被拒绝的签名、滞后 p95 > 60s（这是
  RV-01/CK-02 一致性边界）、任何 DLQ 深度 > 0 持续 15 分钟。
- `key_revocations_total{actor}`；系统/管理员批量撤销时告警。

客户端侧（通过现有匿名遥测，在 telemetry-worker 中仪表化）：按版本的登录成功比、`auth_failure_reason` 分布——新发布改变失败构成时做回归告警。

## 追踪

后端：每个请求一个 trace；每个 flow_id 一个父 span，使一次设备登录尝试显示 request -> email send -> approval -> token issue 为��联 span。span 属性限于审计字段集（id 和哈希，绝无 secret/邮箱）。Stripe webhook 处理为每个事件一个 span，带 `stripe_event_id` 和去重决策。

客户端：认证不做分布式追踪（隐私）。登录流程周围的本地日志行只使用每日日志和流程结果。

## 保留

| 数据 | 位置 | 保留 |
|---|---|---|
| 审计事件 | 后端 | 400 天，追加式 |
| 后端应用日志 | 后端 | 30 天 |
| 追踪 | 后端 | 7-14 天 |
| Stripe webhook 负载归档 | 后端（加密） | 90 天 |
| 匿名客户端遥测 | telemetry-worker D1 | 按 TELEMETRY.md；无账号关联 |
| 本地客户端日志 | `~/.jcode/logs/` | 用户所有；必须满足永不记录清单 |
| 支持包 | 按需创建 | 案件结案后删除（<= 90 天） |

## 支持诊断

`jcode doctor` 式账号诊断（扩展现有 provider doctor，`crates/jcode-provider-doctor/`）：打印 auth_base、脱敏 key（`jc_...last4`）、本地存储的账号邮箱、缓存 tier（`subscription_catalog::cached_tier`）、上次 `/v1/me` 状态、env 文件路径和权限。构造上可安全复制（绝无完整 key）。支持向用户索取：脱敏 key id、大致登录时间和 `AuthFailureReason` 标签；后端支持在审计表中按 `key_id`/`email_hash` 关联。任何流程都不要求用户粘贴 key 或链接。

## 每流程一页摘要

1. 设备登录：客户端只记录结果标签；后端用 device_code_id 审计请求/批准/过期；批准/过期率有指标+告警。
2. 浏览器批准/拒绝：仅后端；审计批准者会话，拒绝尖峰告警；页面不得记录 magic token（只记录其哈希）。
3. `/v1/me`：后端请求日志带 account_id + request_id；客户端缓存 tier 且不记录敏感内容；401 尖峰和延迟告警。
4. 结账：通过 Stripe id 审计 started/completed/abandoned；漏斗指标；绝不记录支付详情（Stripe 拥有它们）。
5. 门户：审计 opened 及结果订阅变化；门户 URL 是 secret（绝不记录）。
6. Webhooks/撤销：审计每个事件带签名 + 去重结果；滞后和 DLQ 告警；撤销审计行是支持的事实来源。
