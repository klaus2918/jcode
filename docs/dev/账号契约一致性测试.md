# 账号契约一致性测试与测试向量

jcode 订阅账号契约的可执行一致性设计：设备登录、浏览器批准/拒绝、账号状态（`/v1/me`）、结账、计费门户、webhook 顺序、撤销和混合版本兼容性。

契约的客户端半部分在本仓库中；服务器半部分在私有 `solosystems-backend` 仓库中。本文定义共享测试向量、在两侧执行它们的装置，以及谁拥有什么。

## 依据（当前代码）

- 设备流客户端和线契约：`src/cli/login/jcode_device.rs:1-225`
  - `POST {auth_base}/v1/auth/device {"email"}` ->
    `{device_code, verify_url, expires_in (默认 900), interval (默认 5)}`
  - `POST {auth_base}/v1/auth/token {"device_code"}` ->
    `202`/`428` 待处理，`429` 减速，`200` 已批准
    `{api_key, account_id?, email?, tier?}`，`200 {"status":"pending"}` 旧版
    待处理，错误码 `authorization_pending|pending`、`slow_down`、
    `expired_token|expired|expired_device_code`、`access_denied|denied`，
    且 `404`/`410` 视为已过期。
- 轮询循环计时：`src/cli/login/jcode_device.rs:230-264`
  （`interval.max(1)`，截止时间来自 `expires_in`，`slow_down` 加 5s）。
- 凭据持久化：`src/cli/login/jcode_device.rs:268-304`
  （`JCODE_API_KEY`、`JCODE_ACCOUNT_ID`、`JCODE_ACCOUNT_EMAIL`、`JCODE_TIER`
  写入 jcode-subscription env 文件）。
- 账号状态客户端：`crates/jcode-base/src/subscription_api.rs`
  （`GET /v1/me` -> `SubscriptionMe`，5s 超时，持久化缓存 tier；
  未知/缺失 tier 的闸门如 Plus：
  `crates/jcode-base/src/subscription_catalog.rs:193-204`）。
- 要扩展的现有可执行装置：`src/cli/login/jcode_device/tests.rs:7-46` 中的脚本化本地 HTTP 服务器加状态机测试
  （`poll_state_machine_*`、`poll_for_api_key_*`）。
- 负路径断言的认证失败分类：`crates/jcode-base/src/auth/login_diagnostics.rs`。

## 仓库所有权

| 关注点 | 所有者仓库 | 装置 |
|---|---|---|
| 客户端轮询状态机、持久化、`/v1/me` 解析、tier 闸门 | jcode（本仓库） | 针对脚本化 HTTP 服务器的 Rust 单元/集成测试 |
| 共享线测试向量（JSON fixtures） | jcode，按版本标签镜像到 solosystems-backend | `tests/fixtures/account-contract/`（提议） |
| 邮件投递、批准/拒绝网页、结账会话创建、Stripe webhooks、密钥撤销、`/v1/me` 事实 | solosystems-backend（私有） | 针对真实 handler 重放相同 fixtures 的后端集成测试 |
| 端到端冒烟（在线 staging） | solosystems-backend CI，jcode CI 中由 staging 凭据门控的 opt-in 任务 | 针对 staging `JCODE_API_BASE` 的可脚本化 `jcode login jcode` 流程 |

规则：fixture 变更是契约变更。Fixtures 带版本号（每个向量文件有 `schema_version` 字段）；两个仓库都固定 fixture 集，混合版本矩阵（见下）证明旧客户端在新服务器向量下仍通过，反之亦然。

## Fixture 布局（提议，本仓库）

```
tests/fixtures/account-contract/
  v1/
    device_auth/           # 对 POST /v1/auth/device 的响应
    token_poll/            # 对 POST /v1/auth/token 的脚本化序列
    me/                    # GET /v1/me 响应体
    webhook_order/         # 仅后端，为文档镜像
    manifest.json          # {schema_version, vectors: [...]}
```

每个向量：`{name, request, response_script: [(status, body)...],
expected_outcome, notes}`。Rust 装置反序列化 manifest 并驱动 `spawn_scripted_http_server`，使向量是数据而非代码。

## 1. 设备登录向量

| ID | 脚本 | 预期 |
|---|---|---|
| DL-01 快乐路径 | device 200 完整响应体；token 202、200 已批准 | `TokenApprovedState` 填充；env 文件有全部四个键 |
| DL-02 默认值 | device 200 无 `expires_in`/`interval` | 应用默认 900/5 |
| DL-03 旧版待处理 | token 200 `{"status":"pending"}` 然后批准 | 先分类为待处理，然后批准 |
| DL-04 嵌套错误 | token 400 `{"error":{"code":"authorization_pending"}}` | 待处理 |
| DL-05 扁平 OAuth 错误 | token 400 `{"error":"slow_down"}` | SlowDown，等待 += 5s |
| DL-06 过期 | token 400 `expired_token`（也是 `expired`、`expired_device_code`） | 过期，清晰的重跑消息 |
| DL-07 消失 | token 404 / 410 空响应体 | 过期 |
| DL-08 拒绝 | token 403 `{"error":{"code":"access_denied","message":"..."}}` | 拒绝并浮出服务器消息 |
| DL-09 空 api_key | token 200 `{"api_key":"  "}` | 硬错误，什么都不持久化 |
| DL-10 垃圾 200 | token 200 非 JSON | 解析错误，什么都不持久化 |
| DL-11 意外 5xx | token 500 | 错误包含状态和修剪后的响应体 |
| DL-12 device 拒绝 | device 400/422/429 | 在任何轮询前中止登录 |

## 2. 浏览器批准/拒绝（后端所有，向量镜像）

客户端无法测试网页；后端必须有可执行测试：

- BA-01 批准链接把 device_code 恰好标记为批准一次（幂等）。
- BA-02 拒绝链接在下次轮询时产生带拒绝原因的 `access_denied`。
- BA-03 批准过期代码返回错误页，轮询保持过期。
- BA-04 magic-link token 一次性：第二次点击是 no-op/错误。
- BA-05 来自与邮箱目标不同的账号/会话的批准失败。
- BA-06 `verify_url` 主机必须匹配认证服务源（客户端侧
  负向：拒绝/拒绝自动打开非 HTTPS 或外源 URL；今天
  `maybe_open_browser` 打开服务器发送的任何 URL——添加此检查）。

## 3. 账号状态（`/v1/me`）

| ID | 响应体 | 预期 |
|---|---|---|
| ME-01 完整 | 带用量的活动旗舰 | 解析，tier 缓存 |
| ME-02 最小 | 缺失 `resets_at`，未知 tier `"mystery"` | 容忍；`parsed_tier()` 为 None；闸门回退到 Plus |
| ME-03 401 | `{"error":"invalid_key"}` | 错误浮出；缓存的 tier 不被覆盖（撤销是显式的，见 6） |
| ME-04 5xx/超时 | 延迟 > 5s | `ME_FETCH_TIMEOUT` 触发；离线闸门使用缓存 tier |
| ME-05 状态值 | `active`、`past_due`、`canceled`、`trialing` | 客户端逐字渲染状态；未知值不崩溃 |

## 4. 结账与门户

结账/门户今天仅网页；客户端在 `JCODE_PRICING_URL` 交接（`src/cli/login/jcode_device.rs:355-367`）。一致性：

- CK-01（后端）为已登录设备创建结账会话，把结果订阅链接到设备登录返回的同一个 `account_id`。
- CK-02（后端）完成的结账在 N 秒内更新 `/v1/me` tier；向量断言最终一致性边界（staging 测试建议 N=60）。
- CK-03（客户端）结账后，新的 `/v1/me` 获取无需重新登录即升级缓存 tier（测试：旧缓存值上的 ME-01 带新 tier）。
- CK-04（后端）门户取消流程设置 `status:"canceled"`，同时密钥保持有效直到周期结束；客户端向量 ME-05 覆盖渲染。
- CK-05（客户端）登录后 tier==none/empty 打印定价提示（`login_jcode_device_flow` 尾部）——stderr 文本快照测试。

## 5. Webhook 顺序（后端所有）

Stripe 乱序且至少一次地投递 webhooks。后端测试必须对 webhook handler 重放这些顺序并断言最终状态：

- WH-01 `checkout.session.completed` 然后 `invoice.paid`（正常）。
- WH-02 `invoice.paid` 在 `checkout.session.completed` 之前（重排）。
- WH-03 每个事件的重复投递（幂等键）。
- WH-04 `customer.subscription.deleted` 与同一秒的 `invoice.paid` 竞争：终态按事件 `created` 时间戳获胜，而不是到达顺序。
- WH-05 签名无效 / 陈旧时间戳 -> 400，无状态变化。
- WH-06 未知事件类型 -> 2xx 确认，无状态变化（前向兼容）。

客户端可观察契约：任何 WH 序列安定后，`/v1/me` 反映恰好一个连贯的 `{tier, status}`；`me/` 中镜像的 fixtures 枚举可达的终态，使客户端测试矩阵保持封闭。

## 6. 撤销

- RV-01（后端）门户/管理员撤销使 API key 失效：模型 API 和 `/v1/me` 在有界滞后内返回 401（staging 断言 <= 60s）。
- RV-02（客户端）模型 API 的 401 分类为带恢复提示的认证失败，提示指向 `/login jcode`
  （`crates/jcode-base/src/auth/login_diagnostics.rs`）。
- RV-03（客户端）被撤销的 key 不得在未浮出认证失败的情况下静默回退到另一个 provider（`crates/jcode-base/src/provider/account_failover.rs` 中的账号故障转移测试）。
- RV-04（后端）撤销后重新登录签发 NEW key；旧 key 保持失效（无复活）。

## 7. 混合版本兼容矩阵

在 2x2 矩阵中运行 DL/ME 向量套件：

| | 旧向量（v1） | 新向量（v1.x） |
|---|---|---|
| 已发布客户端（stable 通道） | 必须通过 | 必须通过，忽略未知字段 |
| head 客户端 | 必须通过 | 必须通过 |

编码为测试的规则：未知 JSON 字段被忽略（serde 默认行为——绝不添加 `deny_unknown_fields`）；缺失可选字段有默认值（DL-02、ME-02）；新错误码落入"意外错误"分支并保留原始响应体（DL-11），而不是被误分类为待处理。

## 8. 安全负向测试

- SN-01 device_code 熵：后端测试断言 >= 128 位，不可猜测的顺序 ID；token 端点按代码和按 IP 限速（429 路径已被客户端处理：DL-05）。
- SN-02 邮箱枚举：`/v1/auth/device` 对已知和未知邮箱返回相同形态（后端）。
- SN-03 客户端绝不把 `api_key` 或完整 `device_code` 打印到 stdout/stderr 或日志（对登录流程捕获输出的 grep 式测试；见可观测性文档的永不记录清单）。
- SN-04 非测试环境下拒绝 HTTP（非 TLS）`auth_base`，除非 `127.0.0.1`/`localhost`（客户端变更 + 测试；今天接受任何 base）。
- SN-05 超大/恶意响应体：10 MB 响应体、错误 content-type、NUL 字节——客户端干净报错，不 panic（`token_poll/` 中的模糊式向量）。
- SN-06 env 文件权限：Unix 上持久化凭据文件为 0600（对 `persist_subscription_credentials` 的测试）。
- SN-07 自动打开浏览器前对 verify_url 的 scheme/host 白名单（BA-06）。
- SN-08 批准后轮询：复用已消费的 device_code 返回过期，绝不返回第二个 key（后端；客户端由 DL-07 语义覆盖）。

## 9. 时钟与竞争

- CR-01 `interval: 0` -> 钳制到 1s（单元测试已通过 `interval.max(1)` 隐式存在；使其显式）。
- CR-02 `expires_in: 0` -> 截止时间是 `max(expires_in, interval)`；循环以过期错误终止，不热旋转。
- CR-03 重复 `slow_down` 单调增长等待；总计在截止时间封顶。
- CR-04 批准落在截止时间检查和轮询之间：客户端接受已批准响应，即使截止时间检查只在下一迭代发生——向量：pending 直到 t=deadline-1，然后批准。
- CR-05 客户端计时使用 `Instant`（单调），因此墙钟偏移不应影响：用 mock 的大 `expires_in` 和手动结果注入测试。
- CR-06 同一邮箱的两次并发登录：env 文件上最后写入者胜；无交错/损坏文件（通过文件锁串行化，或接受并用测试记录最后写入者胜）。
- CR-07 后端：批准和过期在同一秒竞争——恰好一个结果被持久化。
