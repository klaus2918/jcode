# 交互机制

本文覆盖输入与消息注入的交互细节：软中断（消息注入）、Shift+Enter 与多行输入、
会话恢复行为、面向用户的消息语气。合并自原四篇小文档。

## 一、软中断：无缝消息注入

用户在 AI 正在生成时输入消息，**不取消当前生成**：消息进入队列，在提供商连接空闲的
安全点自然合入对话。

对比旧的硬中断（取消 → 等待 → 重新发送）：不丢部分工作、无取消延迟、
不用重发全文上下文、体验流畅。

### 安全注入点

唯一硬约束：**只能在未从提供商积极流式传输时注入**，并且
**Anthropic API 要求每个 `tool_use` 块紧跟其 `tool_result`**，因此不能在两者之间插入用户文本。

| 点 | 位置 | 时机 | 用途 |
|---|---|---|---|
| **B** | 回合完成（未请求工具） | 流结束且无工具调用 | 文本回复后的快速追问 |
| **C** | 工具循环内部 | 仅紧急中止 | 需先补齐被跳过工具的桩 `tool_result` |
| **D** | 所有工具完成之后、下次 API 调用之前 | 默认 | 最干净、最可预测 |

非紧急注入一律推迟到 D 点；只有在**紧急**（`urgent: true`）时才在 C 点中止剩余工具，
并为跳过的工具补 `[已跳过：用户中断]` 的桩结果。

```
loop {
    流式接收 → 加入助手消息
    if 无工具调用 { 注入(B) → 继续循环 }
    for 每个工具 {
        if i > 0 且 有紧急中断 { 补桩结果 → 注入(C) → 跳出 }
        执行工具 → 加入结果
    }
    注入(D)   // 默认路径
}
```

### 协议与实现

```rust
// crates/jcode-protocol/src/wire.rs
#[serde(rename = "soft_interrupt")]
SoftInterrupt { id: u64, content: String, urgent: bool }

ServerEvent::SoftInterruptInjected { content: String, point: String }
```

- 智能体侧维护 `soft_interrupt_queue`，在每个注入点 drain 并合并为一条用户消息
  （多条之间用空行分隔），随后落盘会话。
- 客户端侧不再 `cancel()` 后重发，而是 `soft_interrupt(message, urgent)`。
- 服务器回发 `SoftInterruptInjected` 事件，TUI 据此提示"消息已在工具 X 之后注入"。

### 用户可见行为

- **默认**（回车）：入队 → 状态提示"将在下一个安全点注入" → 注入后提示"已注入"。
- **紧急**（Shift+Enter 或显式标志）：状态提示"将尽快注入（可能跳过工具）"。

### 边界情况

多条软中断合并为一次注入；纯文本响应期间在 B 点注入；提供商内部处理工具（如 CLI 型）
仍然有效（注入发生在我们自己的循环）；无工具的紧急中断按普通处理；流错误时清空队列并正常报错。

## 二、Shift+Enter 与多行输入

### 问题

终端的 Enter 只发一个字节 `0x0d`，VT100 时代无从记录 Shift 是否按下，
因此 `Enter` / `Shift+Enter` / `Ctrl+Enter` 到达时完全一样。

### 解法

现代方案是 **kitty 键盘协议**：应用请求终端消歧，终端对 Shift+Enter 发 `ESC[13;2u`
（键码 13，修饰符 2 = 1 + shift 位）。jcode 启动时请求该协议
（`enable_keyboard_enhancement`），由 crossterm 解码，因此**在支持该协议的终端上零配置可用**：
kitty、Ghostty、WezTerm、Alacritty、foot、iTerm2 3.5+、Warp、VS Code 1.109+。

三种会失效的情况与处理：

| 情况 | 修复 |
|---|---|
| 终端忽略请求（Terminal.app） | 换终端，或把 Shift+Return 手动映射为 `\033[13;2u` |
| tmux 不转发扩展键 | 把 `extended-keys` 写入 `~/.tmux.conf` |
| WezTerm 需显式开启 | 设 `enable_kitty_keyboard = true` |

上表三种修复都由 `/terminal-setup` 处理：它会**实际查询终端能力**而不是假设
（`supports_modified_enter_reporting` 用 `CSI ? u` 后跟 `CSI c` 直接问），
然后要么确认已可用、要么应用配置、要么说明为何配置也解决不了。

### 回退方案（所有终端可用，不依赖修饰键上报）

- **行尾反斜杠 + Enter**：插入换行，与 shell 行续接一致；首次使用时 jcode 会引导运行 `/terminal-setup`。
- **Option/Alt+Enter**：终端发送 `ESC` + `CR` 的地方都可用（含把 Option 当 Meta 的 Terminal.app）。

### 相关测试

`shift_enter_csi_u_sequence_decodes_to_enter_plus_shift`（把精确字节序列送进真实 PTY，
断言解码为 Enter+SHIFT）、`bare_carriage_return_decodes_without_shift`、
`terminal_setup::tests::*`（配置生成、幂等、不覆盖用户配置）。

## 三、会话恢复行为

`/resume`、`/session`、`/sessions` 打开交互式会话选择器（本地 UI 命令，不能作为聊天提示词发送）。

| 按键 | 默认行为 |
|---|---|
| `Enter` | 在当前终端恢复高亮会话 |
| `Ctrl+Enter` | 在新终端打开高亮会话 |
| `Esc` / `q` / `Ctrl+C` | 关闭选择器，不切换会话 |

```toml
[keybindings]
session_picker_enter = "current-terminal"   # 改为 "new-terminal" 可交换两者行为
```

- **当前终端恢复**：把当前工作区/客户端切到该会话；可导入的外部会话先转换为 jcode 会话再就地恢复；
  多选时就地恢复第一个并在 UI 说明；恢复排队后选择器关闭。
- **新终端打开**：每个选中目标尽量在自己的终端打开；终端启动失败时打印手动
  `jcode --resume <id>` 命令；选择器保持打开并清空多选，便于继续打开。

`/save [label]` 把当前会话加入书签（出现在选择器的已保存部分），`/unsave` 移除书签。

选择器还会列出 Claude Code / Codex / pi / OpenCode / Cursor 的外部会话，可直接续接。

## 四、消息语气

面向用户的系统/状态消息（TUI 通知、CLI 输出、通知）的写法。目标：直接说明发生了什么、
我们为用户做了什么，而不是叙述内部机制。

公式：**[发生了什么。] [我们做了什么。] [如何改变这一行为。]**
（除第一部分外均可选，顺序不变。）

原则：

1. **先用用户的语言讲结果**，而不是机制名（不说"todo 完成门控""自动催促已武装""排队续作"）。
2. **用过去时说明我们代办了的事**："我们已为你催促它。"而不是"自动催促中……"。
3. **逃生出口放最后且简短**："。使用 /poke off 停止。"不要把标志或设置名放开头。
4. **面向用户的文本里不出现内部术语**：避免 gate / armed / dispatch / continuation /
   followup / queued dispatch / state / flag（这些词可以出现在日志、注释与代码里）。
5. **用完整句子而非标签**："你的智能体带着 5 个未完成的 todo 停止了。"
6. **警告先讲后果，再讲怎么做**："我们停止了催促，因为它没有取得进展。请检查剩余的 todo。"

示例：

| 之前 | 之后 |
|---|---|
| `Auto-poking: 5 incomplete todos. /poke off to stop.` | `5 个未完成 todo。我们已为你催促。使用 /poke off 停止。` |
| `Auto-poking: todos complete; sending confidence summary follow-up.` | `Todo 已完成。正在请智能体做最终信心确认。` |
| `Todo completion gate: validation still failing after repeated nudges.` | `我们催促了智能体几次，但它停止了进展。已放弃；请自行检查剩余 todo。` |

范围之外：日志/追踪/调试输出保留精确内部名称；面向开发者的 panic 与内部错误不在范围内。
