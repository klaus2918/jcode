# 不等体感出现就定位卡顿

UI 中性能问题的默认发现方式是有人使用它、注意到拖沓并说出来。这有三个失败模式，本仓库一次性全踩了：它只捕捉到人恰好碰到的东西，只在代码发布后才触发，而且它产出的是印象而不是明天可以依据或比较的数字。

这篇笔记描述 desktop2 现在使用的替代方案，以及如何把它应用到别处。

## 杠杆：对可枚举状态空间的纯渲染函数

`jcode-desktop2` 的 `build_scene` 是 `Model` 的纯函数。`states::NODES` 已经枚举了应用的视觉状态，因为同一列表驱动离屏捕获用于视觉审查。

这两个事实合在一起意味着帧成本不是必须在运行窗口里*观察*的东西。它是一个可以*求值*的函数，在已知空间上，不需要窗口、合成器、GPU 或时钟：

```
jcode-desktop2 --profile-states            # ranked table
jcode-desktop2 --profile-states 2000       # with a custom warm budget, in us
```

该命令只对无论什么机器都真实的问题非零退出：任何在未变化帧上重做布局的状态，或超过 40ms 失败阈值的状态。表中的 4ms 热预算只是*建议*。它是墙钟，因此未优化构建或正忙于编译其他东西的机器会标记健康状态，而狼来了的工具会被忽略。当行显示 SLOW 但 relayout 是 `0/n` 时，读 relayout 列继续前进。

测量位于 `crates/jcode-desktop2/src/profile.rs`，并作为 `scripts/check_guardrails.sh` 和 CI 中的门运行。

## 测量工作，而不只是时间

扫描每个状态报告两件事，第二件更重要。

**墙钟成本**（冷和热）是人类读的。冷是空缓存的第一个帧：一次调整大小、一次主题切换、第一次绘制。热是稳态，几乎是每帧的真实情况（一次光标闪烁、一个动画滴答、一次滚动、一个流式增量）。

单独的时间是糟糕的门。在测试套件其余部分共享核心时测量的数字价值是空闲值的数倍，而且 CI 运行器比开发者的机器更慢更不稳定。所以时间门必须携带足够的余量以避免 flake，而余量正是真实回归藏身的地方。会 flake 的门会被静音，被静音的门不是门。

**重排计数**是修复方案。记录布局缓存报告一帧必须从头布局多少条消息。稳态帧上答案必须是零，因为什么都没变。这是关于*工作*的陈述，因此它是精确的、可复现的，在最快的笔记本和最慢的共享运行器上完全相同。不需要余量。

这种区别不是学术性的。当动机这一切的回归被故意重新引入时，松散的时间门在一些状态上通过，而重排门抓住了每一个。

## 状态空间必须触及慢端

原来的 25 个节点都是小而漂亮的屏幕。这对视觉捕获是对的，对性能剖析无用：对它们的扫描报告应用很快，而真实会话却在卡顿，这正是记录重排悄悄发布的方式。

四个 `heavy_*` 节点现在覆盖 60 回合会话、一堵代码墙、一张宽表和数学重型输出。一个测试断言重端保持明显重于中位数，因此覆盖率不会随节点添加而悄悄侵蚀。

注意重端断言是对**冷**成本做的。热成本在缓存正常工作时刻意平坦，所以在那里断言差异等于断言缓存坏了。

## 证明工具框架确实能检测东西

总是打印 OK 的性能工具框架比没有更糟，因为它令人安心。唯一知道它有效的方法是把本该被抓住的东西弄坏并看着它失败。

对 desktop2 这是一行改动：让缓存总是未命中。

```rust
// crates/jcode-desktop2/src/paint.rs, in TranscriptCache::lay_out
let reusable = false && self.keys.get(index).is_some_and(...);
```

然后 `bash scripts/check_guardrails.sh --skip-slow` 必须变红并点名状态。回退后必须变绿。每当门以可能削弱它的方式更改时都做这件事。

## 应用到别处

这个模式泛化到任何具有这两个属性的渲染器：

1. 渲染是模型的纯（或纯可派生）函数。
2. 有趣的模型是可枚举的，而不是只能通过驱动真实 UI 到达。

如果两者都成立，添加扫描、添加重节点、对工作计数器设门而不是只对时间，并通过弄坏东西来证明它。

jcode TUI 满足两者（它有无头黄金渲染测试和 `ui_messages_cache.rs` 中成熟的渲染缓存），因此同样的工具框架可以迁移过去。这还没做，因为 TUI 的缓存目前不携带这类 bug；这篇笔记让这个选项在架上而不是被重新发现。

## 这不覆盖什么

扫描测量的是场景*构建*，在有人想到要枚举的状态上。它不测量 GPU 栅格化、合成器行为、输入延迟或没人写下来的状态。运行时插桩（从真实应用记录超预算帧，带产生它们的状态）是自然的补充：扫描防止已知回归，日志发现值得加入空间的新状态。单独日志是较弱的一半，因为它仍然需要有人先碰到慢路径。
