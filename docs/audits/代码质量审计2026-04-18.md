# 代码质量审计 - 2026-04-18

本报告清点了通过静态扫描和针对性结构启发式可检测的仓库级代码质量问题。它的定位是全面积压种子，而不仅仅是短清单。

## 范围与方法

- 扫描 `target`、`.git` 和 `node_modules` 之外的所有 Rust 文件
- 按 LOC 测量文件大小
- 用花括号平衡的 `fn` 块近似函数大小
- 统计易 panic 宏和方法，并基于路径做测试分类
- 清点 `allow(...)` 抑制和 TODO/FIXME/HACK/XXX 标记
- 注意：基于路径的生产 vs 测试分类是近似的，可能把生产文件内嵌的纯测试代码算多

## 当前积极面

- `cargo clippy --all-targets --all-features -- -D warnings` 干净通过
- Rust 源码中不再有 `#[allow(dead_code)]` 抑制
- 格式当前是干净的

## 最高价值改进主题

1. **在添加更多逻辑之前拆分巨型文件。** 仓库有大量远超文档化 1200 LOC 上限的生产文件，在 TUI、server、provider、session 和工具模块中尤其集中。
2. **拆解怪兽函数。** 最大的可维护性风险不只是文件大小，还有像 `handle_remote_key_internal`、`handle_client`、`handle_server_event`、`run_turn_interactive` 以及多个 markdown/渲染路径这样的巨大单函数。
3. **减少服务器控制/会话代码中的参数扇出。** server 模块中重复的 `#[allow(clippy::too_many_arguments)]` 表明缺少请求上下文结构或更窄的辅助函数边界。
4. **加固真实生产代码中的失败路径。** 即使 clippy 干净，`unwrap`/`expect`/`panic!` 仍然广泛存在，尤其是在工具执行、认证、服务器控制、构建和 provider 代码中。其中一些是生产文件内的纯测试代码，应移出或隔离。
5. **移动或隔离巨型生产文件中内嵌的内联测试。** 几个生产文件携带大量测试主体，抬高了文件大小和易 panic 调用计数。
6. **减少测试集中度。** `src/tui/app/tests.rs` 本身就是一个巨型热点，应按领域拆分，如认证、远程、命令、渲染和状态恢复。
7. **修剪抑制表面。** 大多数抑制是纯测试的 clippy 逃生口，但服务器代码中的 `too_many_arguments` 抑制是架构气味，不只是 lint 噪音。
8. **烧尽延迟工作标记。** TODO/FIXME 标记不多，这是好事，但剩余的仍应转化为 issue 或解决。

## 建议的执行顺序

1. 拆分 `src/server/comm_control.rs`、`src/server/client_lifecycle.rs`、`src/provider/mod.rs`、`src/provider/openai.rs` 和 TUI remote/input 模块

5. 继续把 TUI 渲染和事件处理函数拆分为领域聚焦的辅助函数
