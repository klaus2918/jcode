# 工程质量

本文汇总本仓库的工程质量体系：重构纪律、代码质量标准与门禁、编译与构建工作流、
留存就绪度评测、crate 拆分原则、Terminal-Bench 基准。合并自原六篇文档
（重构路线图、代码质量10-10计划、编译性能计划、留存就绪度、dev/crate拆分计划、Terminal-Bench测试）。

## 一、重构纪律

目标：重构期间保持现有会话与工作流稳定，尽早暴露回归，分阶段降低耦合（不做大爆炸重写）。

**不可妥协的规则**：

1. 优先**保持行为的变更**（提取/重命名/拆分），再做逻辑变更；
2. 合并前跑门禁：`scripts/check_guardrails.sh`（fmt、clippy `-D warnings`、
   以及警告/代码尺寸/测试尺寸/panic/吞错/依赖边界/通配再导出等 ratchet）；
3. 警告数不得高于基线：`scripts/check_warning_budget.sh`（预算见 `scripts/warning_budget.txt`）；
4. 合并前跑安全预检：`scripts/security_preflight.sh`；
5. 每个阶段结束都重新测量并追问：热 `check` 是否实质变快？热 `build` 是否实质变快？
   常见编辑的重建范围是否缩小？**答案是否就不要再以编译时间为由继续高变更重构。**

阶段划分（历史上按此推进，当前已完成到 CLI/服务器/智能体/状态拆分层面）：
安全与卫生 → CLI 分解 → 服务器分解 → 智能体回合循环统一 → TUI 状态/Reducer 拆分 → provider 状态隔离。

## 二、代码质量标准

目标是持续的 9+/10 工程标准，并且日常开发感受接近"10/10"——**不是完美**，而是：
缺陷更难引入、贡献者能快速判断代码归属、仓库抵抗架构漂移、风险区测试良好、质量不依赖记忆或英雄主义。

### 完成定义

| 维度 | 标准 |
|---|---|
| 构建与 lint | `cargo check --all-targets --all-features` 干净；clippy `-D warnings` 干净或仅有狭窄且有据的例外；`cargo fmt --check` 通过；警告数接近零并主动向下棘轮 |
| 结构 | 生产文件原则上不超过 1200 LOC（超出需记录理由），多数低于 800 LOC；多数函数低于 100 LOC；主要领域边界清晰 |
| 可靠性 | e2e 按功能拆分而非集中在巨型文件；关键状态转换有定向测试；重载/流式/工具执行/集群协调有显式失败模式覆盖；内存、socket 生命周期、重连重载有长期检查 |
| 安全 | 生产 `unwrap`/`expect` 显著减少且剩余有据；宽泛 `allow(dead_code)` 被消除或收窄；工具/shell/路径/凭据边界显式且已测试 |
| 贡献体验 | 贡献者能说出代码属于哪里；规则已文档化；CI 让回归难以合并；架构文档与现实一致 |

### 已落地的门禁与预算

```bash
scripts/check_guardrails.sh            # 所有门禁
scripts/check_guardrails.sh --skip-slow  # 跳过 cargo check/clippy 等慢项
```

预算文件：`code_size_budget.json`、`test_size_budget.json`、`panic_budget.json`、
`swallowed_error_budget.json`、`wildcard_reexport_budget.json`、`warning_budget.txt`，
检查脚本为 `scripts/check_*.py` / `check_warning_budget.sh`。

### 不可协商原则

无大爆炸重写（增量）；先做保持行为的变更；质量必须可强制（优先 CI 门禁而非非正式预期）；
激进删除死代码；整个过程中保持产品可发布。

### 要跟踪的指标

警告数与 clippy 违规、宽泛 `allow(dead_code)` 数、生产 `unwrap`/`expect` 数、
前 20 大 Rust 文件、测试运行时间与 flake 率、启动时间 / 内存 / 重载可靠性。

## 三、编译与构建工作流

### 目标与基线

保留全功能构建的同时，让常见的自研开发编辑显著更便宜地编译；每阶段后测量，
**停止没有回报的折腾**。

参考基线（2026-03-24，本机）：

- 热 `cargo check`：约 8.5s（冷些的样本 12.3s / 23.8s）
- 热 release 构建：约 47.3s

近期目标（不触碰广泛共享接口的常见编辑）：热 `check` < 5s，热构建 < 20–30s。

### 优先级（按杠杆排序）

1. **工作区 / crate 边界**——Rust 在 crate 边界缓存最好；
2. **好的边界设计**——高变更逻辑不要放在宽扇出 crate 或不稳定共享类型里；
3. **sccache**——对重复本地构建与 CI 有实际收益；
4. **快速可靠链接器配置**；
5. **重型子系统隔离**（嵌入、provider 实现、大型 TUI 渲染）；
6. **更窄的内循环构建目标**；
7. **让更多变更由配置/钩子/技能/数据驱动，而不是源码驱动**。

### 日常命令

```bash
scripts/dev_cargo.sh check --quiet
scripts/dev_cargo.sh build --profile selfdev -p jcode --bin jcode --quiet
scripts/dev_cargo.sh --print-setup          # 查看实际生效的缓存/链接器/jobs 设置

# 更窄特性集探针（避免拼 Cargo 标志）
JCODE_DEV_FEATURE_PROFILE=minimal scripts/dev_cargo.sh check -p jcode --lib --quiet
JCODE_DEV_FEATURE_PROFILE=full    scripts/dev_cargo.sh check -p jcode --lib --quiet

# 显式选择链接器
JCODE_FAST_LINKER=lld|mold|system scripts/dev_cargo.sh build --release -p jcode --bin jcode
```

包装脚本行为：可用时自动用 `sccache`（**仅非增量构建**）；Linux x86_64 优先 `lld`（可在
`dev_cargo.sh` 内切换为 mold 优先）；自研构建用 `selfdev` profile；
可用 `JCODE_DEV_FEATURE_PROFILE` 注入命名特性集；避免硬强制本机可能损坏的链接器模式。

**sccache 规则**：`sccache` **不能**缓存增量编译单元，而 `selfdev`/`dev`/`release`/`test`
都设置 `incremental = true`，所以在内循环里它是 0% 命中加包装开销。
`dev_cargo.sh` 因此自动判定：增量构建跳过 sccache；非增量构建（如 `release-lto`）才启用。
覆盖：`JCODE_SCCACHE=on|off`、`CARGO_INCREMENTAL=0`（使其可缓存）。

### 内存自适应任务数

多智能体并发构建时静态 `jobs` 会在两个方向都错（空闲浪费核、忙碌超订内存导致
`earlyoom` 杀构建）。`scripts/dev_cargo.sh` 每次运行按**当前可用内存**调整：

- `select_build_jobs()` 读 `MemAvailable` 除以每任务内存预算（默认 2048 MiB，
  `JCODE_BUILD_MIB_PER_JOB`），钳制在 `[1, nproc]`，导出 `CARGO_BUILD_JOBS`；
- 显式 `JCODE_BUILD_JOBS` / `CARGO_BUILD_JOBS` 总是优先；非 Linux 主机保持 cargo 默认。

### 远程构建主机

设置 `JCODE_REMOTE_CARGO=1`（通常在 `~/.config/jcode/remote-build.env`）时，构建会通过
`scripts/remote_build.sh` 卸载到 `JCODE_REMOTE_HOST`。预检先做廉价的 TCP 可达性探针，
离线主机约 1s 内故障转移到本地（而非等满 SSH `ConnectTimeout`）；最近失败后用更短恢复探针
（默认 0.3s）。可调：`JCODE_REMOTE_TCP_TIMEOUT`、`JCODE_REMOTE_RECOVERY_TCP_TIMEOUT`、
`JCODE_REMOTE_DOWN_TTL`、`JCODE_REMOTE_TCP_PROBE=0`。

### 目标目录清理

`target/` 会跨 profile 与交叉编译缓存无界增长（曾达约 84GB）。`scripts/clean_target.sh`
**在并行构建运行时安全**回收空间：绝不触碰有活跃 `rustc`/`cargo` 的目录，
也不碰近期（默认 20min，`JCODE_CLEAN_ACTIVE_WINDOW_MIN`）写入过的 profile 目录。

```bash
scripts/clean_target.sh                        # 干跑，报告可回收空间
scripts/clean_target.sh --apply                # 移除交叉编译/兼容缓存
scripts/clean_target.sh --apply --aggressive   # 额外 cargo clean 过期 profile
```

### 共享构建缓存的操作规则

多智能体共享同一个 `target/selfdev` 是**有意的**："一个智能体编译，人人受益"，
并且自研构建系统用 `build_dedupe_key = worktree_scope : source_fingerprint : command`
做跨会话去重（相同源码状态时后来者附加到进行中的构建）。

由于 `target/selfdev` 的指纹**包含 RUSTFLAGS**（`-Zthreads`、`-fuse-ld=...`），
只有每次构建都用相同标志时缓存才保持热。因此：

- **总是通过 `selfdev build` / `scripts/dev_cargo.sh` 构建**；裸
  `cargo build --profile selfdev` 使用不同标志，会触发整链重建并毒化共享缓存。
- rust-analyzer 用 `target/debug`（独立目录），不会污染 `target/selfdev`。

### 已被测量并否决的做法（不要重试）

| 尝试 | 结果 |
|---|---|
| cranelift 代码生成后端 | 更慢——瓶颈是前端不是代码生成 |
| 把 provider/auth 拆出 `jcode-base` | 无收益：rmeta 流水线让 `app-core` 在 `base` 完成前就开始编译，中间 crate 拆分只是把工作从已重叠的路径移走（**决定：回退**） |
| 把内联 `#[cfg(test)]` 测试移到独立目标 | 无帮助：普通 build/check 已用 cfg 门控掉（0 成本）；集成测试只能看 `pub` 项，破封装；`cargo test -p <crate>` 仍要编译整个测试 cfg |
| 开发二进制 `-C prefer-dynamic` | 链接时间与体积均无变化（只有 std 是 dylib），还给 reload 增加 `.so` 路径脆弱性 |

### 最终裁决（2026-06-08）

发布过的胜利：**nightly 并行前端**与**快速链接器**。热编辑循环已是均衡的约 10s 串行链
（前端约 3s → app-core 约 3s → tui 约 2.7s → bin 链接约 2s），没有单一主导阶段。
剩余唯一杠杆是**产品级**的（削减静态链接的依赖重量，例如把最重的栈特性门控在默认关闭之后），
以及删除真正的死代码。

## 四、留存就绪度

区分两个不应共享标签的问题：

1. **留存就绪度**：确定性的产品属性，让回访变得有用且便宜——是回归测试；
2. **观测到的留存**：真实隐私安全队列是否真的回访并完成有意义工作——是产品结果。

**确定性测试绝不能冒充 D1/D7/D30 用户留存。**

```bash
cargo test -p jcode-app-core --lib retention_readiness -- --nocapture
```

评估器驱动真实的 `Agent`、provider 接口、持久化 `Session` 与磁盘恢复路径，穿过标记的阶段边界
（D0 激活并持久化；D1 从持久化会话新建 Agent 与 provider 注册表、不重述上下文继续；
D7 注入一次 provider 中断后要求失败提示本身持久化、一次重试恢复，且只有前两阶段上下文都在才返回）。
D0/D1/D7 是**确定性阶段标签，不是墙钟睡眠**。

维度权重：激活/首个价值 25%、回访摩擦 20%、连续性 20%、持久性 15%、故障恢复 10%、复合价值 10%。
行为分是**加权几何平均**（`100 * Π(score/100)^weight`），因此零分维度会让总分崩溃而不是被掩盖。

证据覆盖：已评分 6 项（响应首个价值、回访摩擦、连续性、重启/故障持久性、恢复、复合上下文）、
延后 2 项（工具/文件编辑支撑的首个价值、按 provider-OS 矩阵的凭据重建）、
仅观测 1 项（真实 D1/D7/D30 留存，不计入确定性分母）。当前
`Behavioral 100/100`、`Evidence coverage 75/100 (6/8)`，**诚实的头条是 75/100 覆盖调整后就绪度**，
而不是"100% 留存"。

观测对应物（真实队列）应锚定到激活事件与有意义产出，例如
`D7 meaningful-work retention = 激活后 D7 窗口内至少一次成功助手/工具产出的用户数 ÷ D0 首次成功产出的用户数`；
至少报告首次成功响应后与首次成功工具/编辑后的 D1/D7/D30 回访、每活跃用户的重复成功工作流、
升级后回访、认证恢复后的后续工作。`active_days_7d/30d` 是参与信号，但**不是**队列留存
（未把分母锚定到激活事件，也不要求成功产出）。

校准循环：发现确定性因子弱点 → 改进并保持记分卡绿色 → 发布 → 对比隐私安全的真实队列 →
只有多次发布显示稳定关系才调整权重。**绝不为凑期望留存数字而调谐确定性测试。**

## 五、crate 拆分原则

目标：最小化迭代时必须重新检查/构建的代码量。根 `jcode` 仍是集成外壳，稳定叶子代码放在
具有单向依赖的小 crate 中。

原则：

1. **先提取稳定的叶子**：文件系统/存储、协议/类型、解析器、provider 请求/流编解码器、
   TUI 渲染原语；
2. **避免循环的领域 crate**：根可依赖叶子，但叶子不得直接回调根日志/配置/运行时——
   在边界处用数据类型、回调或显式事件；
3. **按重编译易变性拆分，而不是按目录名**；
4. **重型可选依赖放在 crate/feature 之后**（嵌入、PDF、图像/渲染流水线等保持隔离）；
5. **迁移期间保留兼容外观**（`crate::storage::*` 可再导出 `jcode-storage::*`），调用方逐步迁移。

反模式：提取依赖根 `jcode` 的 crate（保留瓶颈并产生循环）；为每个文件建微型 crate
（元数据开销与重构痛苦）；只移动类型别名而把实现留在原处（昂贵编译单元仍然昂贵）。

> 拆分决策的完整规则与当前分层见 [模块与依赖边界](模块与依赖边界.md)；
> 上述"已被测量并否决"的条目说明：**在并行前端与 rmeta 流水线生效后，
> 继续拆分现有巨石收益递减到负——杠杆是 crate 的内容与重量，不是数量。**

## 六、Terminal-Bench 2.0 基准

通过 Harbor 在 Terminal-Bench 2.0 上运行 jcode 的路径。

仓库内相关脚本：

- `scripts/jcode_harbor_agent.py`：jcode 的 Harbor 自定义智能体适配器；
- `scripts/build_linux_compat.sh`：为较旧 glibc 基线构建 Linux jcode 构件
  （许多任务容器比本机构建的二进制使用更旧的 glibc，**必须**用它产出兼容二进制）。

```bash
scripts/build_linux_compat.sh /tmp/jcode-compat-dist

# 让 Harbor 指向适配器运行单个任务（Terminal-Bench 位于 /tmp/terminal-bench-2 时）
# 也可用 --dataset terminal-bench@2.0 走远程数据集
```

**认证与模型假设**：适配器默认使用 `~/.jcode/openai-auth.json` 的 OpenAI OAuth、
模型 `gpt-5.4`、高推理努力、优先服务层级；均可用环境变量覆盖。

常用环境变量：`JCODE_HARBOR_BINARY`（上传到容器的 Linux 兼容二进制）、
`JCODE_HARBOR_BINARY_DIR`、`JCODE_HARBOR_OPENAI_AUTH`、`JCODE_HARBOR_CA_BUNDLE`、
`JCODE_TB_MODEL`（默认 `openai/gpt-5.4`）、`JCODE_TB_PATH`（默认 `/tmp/terminal-bench-2`）、
`JCODE_OPENAI_REASONING_EFFORT`（默认 `high`）、`JCODE_OPENAI_SERVICE_TIER`（默认 `priority`）。

**公平性与状态隔离**：适配器为每次试验提供容器内的全新 jcode 主目录（`/tmp/jcode-home`），
因此记忆与认证状态按试验隔离。

**验证状态**：该路径已用真实 Harbor 任务验证（`regex-log`、`largest-eigenval`、
`cancel-async-tasks`），初始试点三者均在容器内通过、验证器奖励 1.0。
