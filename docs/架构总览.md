# 架构总览

jcode 是**单服务器、多客户端**架构：一个常驻服务器进程管理全部会话与共享状态，
TUI 客户端通过本地套接字连接，断开或服务器重载后透明重连。

相关文档：[模块与依赖边界](模块与依赖边界.md)、[集群](集群.md)、
[Windows 平台](Windows平台.md)。

## 一、进程模型

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                             服务器（🔥 blazing）                              │
│                                                                             │
│  jcode serve                                                                │
│  ├── 主套接字：    <runtime-dir>/jcode.sock                                 │
│  ├── 调试套接字：  <runtime-dir>/jcode-debug.sock                           │
│  ├── 注册表：      ~/.jcode/servers.json                                    │
│  ├── provider（按配置装配：命名 provider / anthropic / openai / openrouter） │
│  ├── MCP 池（跨会话共享）                                                   │
│  └── 会话：                                                                  │
│        ├── 🦊 fox   (active)  → "🔥 blazing 🦊 fox"                         │
│        ├── 🐻 bear  (active)  → "🔥 blazing 🐻 bear"                        │
│        └── 🦉 owl   (idle)    → "🔥 blazing 🦉 owl"                         │
└─────────────────────────────────────────────────────────────────────────────┘
         │              │              │
         ▼              ▼              ▼
    ┌─────────┐   ┌─────────┐   ┌─────────┐
    │ 客户端 1 │   │ 客户端 2 │   │ 客户端 3 │
    │ 🦊 fox  │   │ 🐻 bear │   │ 🦉 owl  │
    └─────────┘   └─────────┘   └─────────┘
```

### 命名

```
服务器 = 形容词/动词             会话 = 动物名词
🔥 blazing  ❄️ frozen  ⚡ swift     🦊 fox  🐻 bear  🦉 owl
🌀 rising   🍂 falling 🌊 rushing   🌙 moon ⭐ star  🔥 fire
✨ bright   🌑 dark    💫 spinning  🐺 wolf 🦁 lion  🐋 whale

组合："🔥 blazing 🦊 fox" = 服务器 + 会话
```

服务器启动时获得随机修饰词，会话获得动物名。服务器名通过 `~/.jcode/servers.json`
在重载后持久；`/reload` 时新进程重新注册，过时条目自动清理。

长期部署可用 `jcode serve --server-name <name>` 或 `JCODE_SERVER_NAME`
（另接受 `JCODE_SERVER_DISPLAY_NAME`）给守护进程稳定身份；CLI 优先于环境变量。
名称会规范化为注册表安全的小写标签（`mount-cloud/fabian` → `mount-cloud-fabian`）。

### 生命周期

```
  启动                        连接                      重载
  ────                        ────                      ────
  jcode（首次）               jcode（后续）             /reload
     │                            │                        │
     ├─ 无服务器？派生守护进程     ├─ 服务器存在？直接连接   ├─ 服务器 exec 新二进制（同 PID）
     ├─ 等待套接字                │                        ├─ 所有客户端断开
     ├─ 作为客户端连接            └─ 创建/恢复会话          └─ 客户端自动重连
     └─ 创建会话
```

- **启动**：无服务器时以分离守护进程方式派生 `jcode serve`（`setsid`），等待套接字后连接。
  守护进程与客户端完全分离，杀掉任一客户端不影响服务器与其他客户端。
- **关闭**：空闲 5 分钟无客户端即退出；也可手动杀死，或由 `/reload` 走 exec 换二进制。
- **重连**：客户端带退避重试——前两次尝试（以及首次拉起服务器的前 20 次）间隔 100ms，
  之后按 `2^(n-2)` 秒指数增长并封顶 30s（`remote/reconnect.rs`）；恢复同一会话（会话状态落盘）；
  服务器重载后若客户端二进制较新，客户端自身也会 re-exec。
- **热重载 `/reload`**：客户端发 `Request::Reload` → 服务器回 `Reloading` 事件 →
  服务器 `exec()` 进入新二进制（同套接字路径）→ 所有客户端自动重连。

### 远程工作目录

客户端订阅时会把当前工作目录发给服务器作为会话工作目录。面向远程守护进程时可用
`--remote-working-dir` 把客户端与服务器路径分开：

```bash
jcode --socket /tmp/jcode.sock -C /local/checkout --remote-working-dir /remote/checkout
```

`-C` 在客户端生效；`--remote-working-dir` 必须是服务器上存在的绝对路径。

### 套接字位置

由 `jcode-storage` 的 `runtime_dir()` 决定（`crates/jcode-storage/src/lib.rs`）：

1. `$JCODE_RUNTIME_DIR`（显式覆盖）
2. `$XDG_RUNTIME_DIR`（Linux 通常 `/run/user/<uid>`）
3. macOS：`$TMPDIR`
4. 回退：`<temp>/jcode-<uid>`

```
<runtime-dir>/
├── jcode.sock          # 主通信套接字
└── jcode-debug.sock    # 调试/测试套接字
```

**Windows**：套接字路径映射为命名管道（`crates/jcode-base/src/transport/windows.rs`）。
管道名 = 文件名主干 + `-` + 规范化路径 SHA-256 的前 16 位十六进制，例如
`/run/user/1000/jcode.sock` → `\\.\pipe\jcode-<hash16>`；
`/run/user/1000/jcode/myserver.sock` → `\\.\pipe\myserver-<hash16>`。

## 二、协议

- 线格式：行分隔 JSON，`Request` / `ServerEvent` 定义在 `crates/jcode-protocol`。
- 传输：本地套接字（Unix domain socket / Windows 命名管道）；形态上传输无关，代码上尚未抽象。
- 调试面：`jcode debug <command>` 走独立的调试套接字，可 list / start / sessions / message /
  tool / state / history 等（`jcode debug help` 查看全部）。

## 三、客户端形态

今天是**每客户端单会话**：服务器拥有多个会话，每个客户端通常挂接一个会话，
每个终端窗口/进程托管一个客户端（`session ≈ client ≈ process`）。

已落地的多会话相关能力：

- **分屏视图**（`/split-view`，`crates/jcode-tui/src/tui/app/split_view.rs`）：在侧栏把
  另一个会话的内容以分屏形式呈现。
- **工作区地图**（`crates/jcode-tui-workspace`）：渲染会话/工作区位置关系的迷你地图。

**未落地**（保持为设计方向，不在本仓库实现）：`ClientShell` / `SessionController` /
`SessionSurfaceState` 分层、单进程托管多个会话表面、会话多路复用协议、pop-out / dock 工作流。

## 四、后台会话

会话切换时，**正在忙碌的旧会话不会被中断**：服务器继续执行其回合，把状态登记为后台会话，
完成后再通知客户端。已实现要点（`crates/jcode-app-core/src/server/background_session.rs`）：

- 切换时保留忙碌会话，而不是终止其回合。
- 后台会话完成时产生通知事件，TUI 以通知与列表标记呈现。
- 会话选择器区分「前台 / 后台运行中」状态；后台会话可被重新拉回前台接管。
- 客户端断连时不清除后台会话，重连后仍可观察其结果。

## 五、自研模式

自研（self-dev）不是独立守护进程，而是**共享服务器上的会话级能力**：

1. 进入方式：显式 `jcode self-dev`（别名 `selfdev`）、当前工作目录是仓库（自动检测）、
   或恢复的会话本身就是 canary。
2. 客户端连接**同一个共享服务器**，在订阅时带上 `selfdev: true`。
3. 服务器只把该会话标记为 canary：仅对该会话注册自研工具、注入自研提示词。
4. `/reload` 重载的是共享服务器（所有客户端重连）；重载选用哪个二进制由**触发会话**决定
   （普通会话 → stable/启动器候选，canary 会话 → 仓库构建候选）。

这样做的收益是显著的 RAM 节省：不再有第二套常驻服务器进程及其 Tokio 运行时、
MCP 池、嵌入模型生命周期、事件缓冲与会话/集群 map。

## 六、关键行为速查

| 场景 | 行为 |
|---|---|
| 首次 `jcode` | 派生服务器守护进程并连接 |
| 后续 `jcode` | 连接现有服务器 |
| 杀死客户端 | 服务器与其他客户端不受影响 |
| `/reload` | 服务器 exec 新二进制，客户端重连 |
| 所有客户端关闭 | 服务器 5 分钟后空闲退出 |
| 恢复会话 | `jcode --resume fox` 重连到既有会话 |
| 会话切换 | 忙碌的旧会话转入后台继续执行 |

## 七、未落地的方向（仅记录，勿当作现状）

- **远程交接**：把活动会话在主机间**迁移**（所有权转移）或**挂接**（远程客户端驱动，
  所有权不动）。已有基础：客户端间会话接管、SSH ControlMaster 复用、重载时的状态序列化。
  缺的是传输抽象（`Local` / `Ssh` / `Relay`）与回合中途断链的事件重放保证。
- **多会话客户端**：见第三节。
- **跨设备工作树同步**：让两台机器共享同一套 worktree/构建状态，用 `version_label`
  （提交哈希 + 状态 + `diff --binary HEAD` + 未跟踪内容的指纹）判断两端源码是否等价；
  未落地。
- **智能体原生 VCS**：面向多智能体协作的「通道优先」版本控制层（Git/jj 之上保留变更
  含义、归属与维护上下文），目前只有设计思路，无实现。
