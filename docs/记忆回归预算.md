# 记忆回归预算

状态：活动护栏
更新：2026-04-18

本文档定义 jcode 当前的记忆回归预算。

实时服务器分类和按原因修复，见 [Jcode 服务器记忆故障应急手册](./记忆事件处理手册.md)。

目标不是永远冻结记忆使用。目标是让记忆变化：
- 可测量
- 可审查
- 有意且有依据

在可能处，下面的预算绑定到代码库已暴露的计数器和上限，而不是猜测的 RSS 数字。

## 如何收集指标

使用现有调试面而不是临时插桩：

- TUI 聚合记忆画像：`:debug memory`
- TUI 记忆采样历史：`:debug memory-history`
- Markdown 缓存画像：`:debug markdown:memory`
- Mermaid 缓存画像：`:debug mermaid:memory`
- 通过调试套接字的智能体/会话记忆画像：`agent:memory`
- 快速服务器故障分类：`server:memory-incident`
- 完整服务器归因：`server:memory`
- 进程生命周期时间线：`python scripts/analyze_runtime_memory_log.py --days 1`

代码中的主要来源：
- `src/tui/app/debug_cmds.rs`
- `src/tui/memory_profile.rs`
- `src/session.rs`
- `src/tui/markdown.rs`
- `src/tui/mermaid.rs`
- `src/runtime_memory_log.rs`

## 预算模型

我们使用两类预算：

1. 硬上限
- 这些是缓存已执行的显式限制。
- 这里的回归意味着代码改变了其边界或绕过了它。

2. 棘轮期望
- 这些是记忆计数器之间的期望关系。
- 这里的回归只允许带解释和更新的文档/测试。

## 硬上限

### Markdown 缓存预算

来源：`src/tui/markdown.rs`

| 指标 | 预算 | 原因 |
|---|---:|---|
| `highlight_cache_entries` | `<= 256` | 显式缓存上限（`HIGHLIGHT_CACHE_LIMIT`） |

违反时要求的审查行动：
- 解释缓存限制为何变化
- 更新本文档
- 更新任何受影响的测试或基准

### Mermaid 缓存预算

来源：
- `src/tui/mermaid.rs`
- `src/tui/mermaid_cache_render.rs`

| 指标 | 预算 | 原因 |
|---|---:|---|
| `render_cache_entries` | `<= 64` | 显式渲染缓存上限（`RENDER_CACHE_MAX`） |
| `image_state_entries` | `<= 12` | 显式协议状态上限（`IMAGE_STATE_MAX`） |
| `source_cache_entries` | `<= 8` | 显式解码源上限（`SOURCE_CACHE_MAX`） |
| `active_diagrams` | `<= 128` | 显式活动图上限（`ACTIVE_DIAGRAMS_MAX`） |
| `cache_disk_png_bytes` | `<= 50 MiB` | 显式磁盘缓存上限（`CACHE_MAX_SIZE_BYTES`） |
| `cache_disk_max_age_secs` | `<= 259200` | 3 天过期（`CACHE_MAX_AGE_SECS`） |

违反时要求的审查行动：
- 记录新限制和原因
- 验证驱逐仍然有效
- 验证没有引入无界增长路径

## 棘轮期望

### 会话和记录记忆

来源：`src/session.rs`、`src/tui/memory_profile.rs`

这些还不是严格上限，但它们是期望关系。

| 指标关系 | 期望 |
|---|---|
| `provider_messages_cache.count` vs `messages.count` | 对单会话应保持在同一数量级，通常与记录紧密跟踪 |
| `session_provider_cache_json_bytes` vs `canonical_transcript_json_bytes` | 正常聊天流程应保持可比，不独立爆炸 |
| `transient_provider_materialization_json_bytes` | 应在活动物化重型路径之外回到零或接近零 |
| `display_large_tool_output_bytes` | 大值需要解释，因为它们通常意味着原始工具输出在 UI 中被过于激进地保留 |

违反时要求的审查行动：
- 显示前后记忆画像
- 解释哪个保留路径增长了
- 在提高任何预算之前优先修复重复

### 运行时记忆日志期望

来源：`src/runtime_memory_log.rs`

运行时记忆日志是回归检测机制，不只是调试功能。

期望行为：
- 服务器/客户端日志应足以解释以下方面的大变化：
  - 会话/记录总计
  - 提供商缓存总计
  - TUI 显示总计
  - 侧面板总计
- 新的大记忆所有者应发出可归因信号，而不是只表现为无法解释的 RSS 增长

违反时要求的审查行动：
- 在接受记忆增长之前添加或改进归因

## 影响记忆的变更的审查清单

更改记忆重型代码时，捕获并包含：

1. 哪些计数器变了？
- 聚合 `:debug memory`
- 定向 `:debug markdown:memory` / `:debug mermaid:memory`
- 会话/提供商缓存行为变化时的 `agent:memory`

2. 硬上限变了吗？
- 如果是，解释为什么旧上限不足

3. 重复增加了吗？
- 规范记录
- 提供商缓存
- 物化的提供商视图
- 显示副本
- 侧面板副本

4. 可观测性仍然充分吗？
- 如果记忆增长了，日志/画像能解释在哪里吗？

## 当前初始预算摘要

这些是今天实际强制执行的限制：

- Markdown 高亮缓存条目：256
- Mermaid 渲染缓存条目：64
- Mermaid 协议图像状态条目：12
- Mermaid 解码源缓存条目：8
- Mermaid 活动图：128
- Mermaid 磁盘 PNG 缓存：50 MiB，最长 3 天

对这些限制的任何有意更改必须在同一个 PR 中更新本文档。
