# 赞助发现：赞助方接入

本手册是向 jcode 的 `discover_tools` 目录添加工具赞助方的事实来源。它覆盖产品批准、目录数据、服务行为、客户端验证、发布和回滚。

赞助方为在发现分类中的位置付费，而不是为推荐付费。智能体仍必须为用户的任务选择最佳工具，并可以选择非赞助的替代品。不要接入其协议要求优先推荐、隐藏位置或削弱用户保障的赞助方。

## 通常改什么

向既有分类添加赞助方是发现服务的目录变更。它不应需要 jcode 发布。

当赞助方需要以下内容时，才需要 jcode 代码变更：

- `DISCOVERY_CATEGORIES` 中的新分类；
- 当前客户端不支持的响应字段；
- 新的设置或来源机制；或
- 不同的披露、隐私、遥测或安全行为。

托管目录和发现服务不存储在本仓库中。该变更与服��所有者协调。客户端契约位于：

- `crates/jcode-app-core/src/tool/discover.rs`；
- `crates/jcode-base/src/sponsors.rs`；
- `crates/jcode-base/src/sponsors/provenance.rs`；
- `crates/jcode-tui/src/tui/app/sponsor_disclosure.rs`；以及
- `TELEMETRY.md`。

## 1. 接收与批准

在编辑目录前记录以下内容：

- 赞助方的法律名称和公开产品名；
- 规范工具名称和 URL；
- 请求的分类；
- 简洁、事实性的产品描述；
- 支持的平台和前置条件；
- 确切的安装或连接步骤；
- 设置是否使用 MCP，若是，确切命令和参数；
- 工具接收的权限、凭据、网络访问和数据；
- 定价、试用、账户、支付和其他重大要求；
- 支持联系人、技术负责人、开始日期和结束或复审日期；以及
- 回滚联系人和最大可接受禁用时间。

发现负责人必须验证：

1. 产品真实、可达且与其分类相关。
2. 描述是事实性的，而不是比较性或促销性的。
3. 设置说明在可行时使用官方、带版本号或以其他方式可审计的分发渠道。
4. 目录数据中没有嵌入任何凭据、API key、推荐 secret、用户标识符或环境值。
5. 设置不绕过 jcode 的确认要求。注册、支付、破坏性操作和其他重大动作仍需要正常的用户确认和赞助披露。
6. 商业协议只购买可发现性。编辑排序和智能体选择保持独立。

如果任何一项无法验证，拒绝或暂停接入。

## 2. 选择或添加分类

当前分类由 `crates/jcode-base/src/sponsors.rs` 中的 `DISCOVERY_CATEGORIES` 定义。分类值是小写 slug。

只要现有分类能准确描述该能力就使用它。要添加分类：

1. 把 slug 添加到 `DISCOVERY_CATEGORIES`。
2. 把相同值添加到发现服务的分类白名单。
3. 更新任何公开分类文档。
4. 运行下面列出的客户端测试。
5. 先发布 jcode 变更，再发布依赖该分类的条目。

不要创建赞助方专属分类。分类描述用户需求，不是厂商。

## 3. 创建目录条目

`name` 使用稳定、小写的工具 slug。一个完整的内部目录条目应为两个 API 阶段都包含足够数据：

```json
{
  "name": "example-tool",
  "category": "databases",
  "blurb": "Managed PostgreSQL with branching and connection pooling",
  "url": "https://example.com/product",
  "setup": "Run `npx -y example-tool-mcp@1.2.3`, then connect the resulting MCP server.",
  "mcp": {
    "command": "npx",
    "args": ["-y", "example-tool-mcp@1.2.3"]
  },
  "active": true
}
```

客户端可见字段：

| 字段 | 必需 | 规则 |
|-------|----------|-------|
| `name` | 是 | 稳定的规范 slug。它也是粗粒度 MCP 用量计量使用的赞助方键。 |
| `blurb` | 是 | 简短、事实性的能力描述。不要声称"最好"或暗示背书。 |
| `url` | 推荐 | 厂商控制的 HTTPS 产品或设置页。 |
| `setup` | 选择性阶段 | 仅在智能体选择工具后返回的完整说明。绝不包含 secret。 |
| `mcp.command` | 用于 MCP 来源 | `mcp connect` 使用的可执行文件。必须与最终连接命令完全一致。 |
| `mcp.args` | 用于 MCP 来源 | 有序字符串数组。必须与最终连接参数完全一致。 |

服务可以保留 `category`、`active`、活动日期或排序元数据等运营字段，但绝不能向客户端暴露私有商业数据。

### 设置安全审阅

在发布前于干净测试环境中运行该设置。审阅包所有者、源码仓库、安装脚本、传递行为、所需权限和凭据流。目录设置说明中优先使用固定版本。如果刻意使用浮动版本，记录谁负责持续监控和紧急禁用。

对于 MCP 条目，`mcp.command` 和 `mcp.args` 对安全和测量敏感。jcode 仅当后来的 MCP 连接与两个值都完全匹配时才记录发现来源。单独的散文 `setup` 字符串不会启用来源标记或粗粒度用量计量。

## 4. 实现浏览、选择与目录建议

默认客户端发送 `GET https://api.jcode.sh/v1/discovery`，带三秒超时和 64 KiB 最大响应。它发送 `User-Agent: jcode/<version>` 头和随机的 `x-jcode-discovery-request-id` 关联头。

当前客户端还发送粗粒度来源头：随机的本地会话 ID、会话元数据是否可用、self-dev/debug/canary 标志、工具执行模式、构建通道、Git 检出/CI/Cargo 运行标志。服务用这些信号把维护者告警分类为疑似用户、self-dev、内部测试、canary、开发、遗留或未验证流量。这些值是客户端报告的证据，而非密码学证明。它们不包含任何记录内容、文件路径、账户身份、凭据或用户撰写的文本。

由 `scripts/benchmark_discovery.py` 启动的运行还发送 `x-jcode-discovery-benchmark: 1`。服务必须把该标记连同其请求日志保留，使基准流量可以从普通发现和赞助报告中被排除。

浏览和选择使用这些查询参数：

| 参数 | 阶段 | 含义 |
|-----------|-------|---------|
| `category` | 浏览/选择 | 必需的分类 slug。 |
| `q` | 浏览/选择 | 必需的能力摘要，20-500 字符。它必须足够具体以描述缺失能力，而不复制用户文本。 |
| `reason` | 浏览/选择 | 必需的理由，40-2,000 字符。浏览解释为什么需要该能力。选择解释为什么所选工具比列出的替代品更合适。 |
| `tool` | 选择 | 从先前浏览响应中选定的规范名称。它的存在选择第二阶段。 |

面向模型的 schema 明确说明浏览/选择的 `q` 和 `reason` 可能被发送给相关赞助方用于需求和选择报告。目录建议只发送给 Jcode 维护者。Schema 告诉模型写新鲜的摘要，而不是复制用户文本，并且绝不包含 secret、凭据、个人数据或私有内容。两个字段在所有三个动作中都保持必需并使用相同长度边界。

客户端在发起网络请求前拒绝缺失、空白、过短、过长、填充式低信息或可识别的敏感文本。服务在存储或交付给赞助方之前重复验证，使直接 HTTP 调用者无法绕过客户端。高置信度检测覆盖常见 API-key 和 access-token 格式、凭据赋值、bearer token、私钥、JWT、支付卡号、邮箱地址、SSN、带凭据的 URL 和国际电话号码。错误消息绝不回显被拒绝的值。这是纵深防御过滤器，不是把私有数据放进任一字段的许可。

对于普通非基准流量，服务把两个原始摘要存储在 `discovery_events` 中。当为列出的赞助方配置了已审阅接收者时，它也把与该条目相关的浏览或选择摘要发送给该赞助方。接收者配置是显式的，默认为空。标记为 `x-jcode-discovery-benchmark: 1` 的运行仍以 `benchmark_run = 1` 存储以供审计，但绝不被作为赞助报告交付。

### 浏览响应

浏览返回合格工具，不含设置说明或 MCP 启动数据：

```json
{
  "tools": [
    {
      "name": "example-tool",
      "blurb": "Managed PostgreSQL with branching and connection pooling",
      "url": "https://example.com/product"
    }
  ]
}
```

没有条目合格时返回 `{"tools": []}`。浏览期间绝不返回 `setup` 或 `mcp`。设置仍需要特定选择和理由。每个浏览响应必须暴露其请求 ID，使智能体在没有列出工具合适时可以引用它。

### 选择响应

选择在 `category` 内查找 `tool` 并返回一个规范条目：

```json
{
  "tool": {
    "name": "example-tool",
    "blurb": "Managed PostgreSQL with branching and connection pooling",
    "url": "https://example.com/product",
    "setup": "Run `npx -y example-tool-mcp@1.2.3`, then connect the resulting MCP server.",
    "mcp": {
      "command": "npx",
      "args": ["-y", "example-tool-mcp@1.2.3"]
    }
  }
}
```

对未知分类、未知工具、无效请���或服务失败使用非 2xx 响应。绝不静默替换另一个赞助方。保持总 JSON 低于 64 KiB 并避免重定向，因为重定向使行为更难审计。

### 目录建议响应

当浏览结果为空或不合适时，智能体可以发送 `POST /v1/discovery/suggestions`。JSON 体包含 `category`、`query`、`reason`、`prior_request_id` 和 `suggestion_kind`（`known_product` 或 `capability_gap`）。已知产品还需要 `product_name`，并且可以包含公开的 HTTPS `product_url`。两种类型都可以包含简明的 `gap_evidence` 和多达八个公开 `requirements`。

服务必须验证 `prior_request_id` 指向同一分类中的成功浏览，每个浏览最多允许一条建议，在确认前同步持久化该建议，并对每个文本字段应用相同的敏感数据验证。返回 `202` 与 `{"suggestion_id":"...","status":"received"}`。重复提交可以返回带 `status: "duplicate"` 的 `409`；客户端把它视为成功接收。建议只发送给 Jcode 维护者，绝不发送给赞助方。接收不意味着批准、赞助、实现或可用性。

## 5. 上线前验证

首先直接验证服务。使用通用测试文本，因为 `q` 和 `reason` 会被发送给发现服务并可能被其存储。

```bash
DISCOVERY_URL=https://staging.example.com/v1/discovery

curl --fail-with-body --get "$DISCOVERY_URL" \
  --data-urlencode 'category=databases' \
  --data-urlencode 'q=managed postgres for a test application' \
  --data-urlencode 'reason=validate the databases discovery listing'

curl --fail-with-body --get "$DISCOVERY_URL" \
  --data-urlencode 'category=databases' \
  --data-urlencode 'tool=example-tool' \
  --data-urlencode 'q=managed postgres for a disposable test application' \
  --data-urlencode 'reason=selected for staging validation after reviewing the listed database options'

curl --fail-with-body --request POST "$DISCOVERY_URL/suggestions" \
  --header 'content-type: application/json' \
  --data '{
    "category":"databases",
    "query":"managed postgres branching with scoped agent provisioning",
    "reason":"none of the current database entries satisfy the isolated branch requirement",
    "suggestion_kind":"capability_gap",
    "prior_request_id":"<browse request ID>",
    "requirements":["Create isolated branches without exposing administrator credentials"]
  }'
```

验证以下全部：

- 浏览在预期分类中恰好一次包含该赞助方；
- 浏览省略 `setup`、`mcp`、凭据和私有活动元数据；
- 选择返回相同的规范 `name`，外加已审阅的设置说明；
- 未知工具和分类失败而不是返回默认条目；
- 响应体保持在 64 KiB 以下；
- 记录的查询和理由文本遵循服务的保留与访问策略；
- 缺失、过短、过长和可识别的敏感查询或理由文本在原始事件存储前被拒绝；
- 已配置的赞助方接收者收到浏览和选择摘要，但带基准头的相同请求不产生赞助交付；
- suggest 需要同一分类中先前成功的浏览，每个浏览持久化一条可操作的提案，并且只发送给 Jcode 维护者；
- 建议接收明确说明提议的产品或能力尚未被批准或可用；
- 请求 ID 出现在服务日志中，可以在没有持久用户标识符的情况下关联以进行可靠性调试；以及
- 禁用目录条目使其从浏览移除并阻止选择。

然后通过指向 staging 的测试配置在 jcode 中验证：

```toml
[sponsors]
enabled = true
endpoint = "https://staging.example.com/v1/discovery"
```

在一次性 jcode 会话中，浏览该分类，选择赞助方或在没有条目合适时提交建议，并且在适用时连接宣传的 MCP 服务器。确认：

- 第一次发现使用显示 `(sponsored discovery)`；
- 浏览输出说明位置不意味着偏好；
- 设置只在选择后出现；
- 浏览、选择和建议渲染为不同的紧凑卡片，建议标出其类型、能力、缺口、要求、状态和维护者专用接收者策略；
- 重大后续动作仍请求确认并提及赞助；
- 使用确切结构化命令和参数的 MCP 连接显示发现来源；以及
- 工具无需未披露的权限或数据即可工作。

对于客户端侧变更，至少运行：

```bash
cargo test -p jcode-app-core tool::discover
cargo test -p jcode-base sponsors
cargo test -p jcode-base discovery_provenance
cargo test -p jcode-tui sponsor_disclosure
cargo check -p jcode
```

如果 Cargo 的过滤器发生变化，运行所在 crate 的测试而不是跳过检查。

## 6. 发布与监控

1. 发布到 staging 并完成验证清单。
2. 获得发现负责人和设置安全审阅人的签字。
3. 如果支持，以禁用状态或在其活动窗口之外发布条目。
4. 在生产启用它，不改变无关目录条目。
5. 对生产重复一次浏览和一次选择请求。
6. 监控发现成功/失败率、响应大小和延迟、浏览到选择行为，以及粗粒度来源使用。客户端遥测边界见 `TELEMETRY.md`。
7. 每当厂商改变其包、所有权、权限或认证流程时，重新审阅设置和目标 URL。

不要用选择或用量计数让智能体偏好赞助方。那些信号用于可靠性、汇总报告和目录质量。

## 7. 回滚

主要回滚是禁用或移除赞助方的服务侧目录条目。这必须同时停止浏览位置和直接选择查找。用于安全问题、误导性文案、坏掉的设置、过期协议、服务滥用或厂商请求。

禁用后：

1. 验证浏览不再返回该条目。
2. 验证直接选择其名称失败。
3. 只保留适用保留策略要求的日志和汇总记录。
4. 通知技术和商业负责人。
5. 如果用户可能安装了不安全���错误的软件，打开事后 issue。

只有当目录禁用无法遏制问题时才需要客户端发布，例如分类级响应被攻破或客户端设置处理有缺陷。

## 完成定义

只有当每个框都被勾选时，赞助方才算接入完成：

- [ ] 接收、所有权、活动日期和回滚联系人已记录。
- [ ] 在 `scripts/attribution_benchmark_sponsors.json` 中声明了归因机制，并且 `python scripts/benchmark_attribution.py --live --sponsor <tool>` 得分为 100。见 [赞助归因基准测试](赞助归因基准测试.md)。
- [ ] 接受仅位置策略和独立推荐。
- [ ] 分类和事实性文案已批准。
- [ ] 设置和目标 URL 在干净环境中通过安全审阅。
- [ ] 浏览和选择响应匹配文档化 schema。
- [ ] 两个阶段都拒绝缺失或不安全的 `q` 和 `reason` 值。
- [ ] 赞助报告接收者已审阅，基准排除已测试。
- [ ] 浏览不暴露设置或 MCP 启动数据。
- [ ] MCP 命令和参数（如使用）与测试的连接完全匹配。
- [ ] Staging jcode 验证通过，包括披露和确认。
- [ ] 未知和禁用条目失败关闭。
- [ ] 生产冒烟测试通过，监控有负责人。
- [ ] 回滚已通过禁用 staging 条目测试或演示。
