# 发现引导评估：任务规格

本文档定义发现引导评估中*任务*是什么、每个字段的含义、任务必须满足哪些不变量，以及任务如何评分。它是 `scripts/discovery_elicitation_cases.json` 的编写契约。

它刻意很窄。这个评估测量**一个**术语：

```
selects/DAU = latent_gap_rate x elicitation x fit x stick
                                 ^^^^^^^^^^^
```

`elicitation`（引导率）是**给定真实未满足的外部能力缺口**时，智能体在当前系统提示词和工具模式下达及 `discover_tools` 的概率。该产品中的其他一切都在别处测量：

| 术语 | 归属 | 测量者 |
|---|---|---|
| `latent_gap_rate` | 用户工作负载（不是我们的） | 对真实会话的标注扫描 |
| `elicitation` | **系统提示词 + 工具模式** | **本评估** |
| `fit` | 目录覆盖 | `discovery.sql` 类别漏斗、活动目录探测 |
| `stick` | 清单设置质量 | `discovery_usage` 遥测（尚未发出） |

该范围界定的后果驱动下面的每条规则：

- 任务**不是**目录测试。即使目录返回零工具，浏览进正确类别也算引导成功。本评估必须在目录变化时保持平坦，只在提示词或模式变化时移动。
- `expected_tool` 因此在这里**被禁止**。工具到达属于 `scripts/discovery_benchmark_cases.json`（见 `发现触发基准测试.md`），那是另一个评估、另一个问题。
- 本评估是**配对**设计。通过写更坚持的工具描述来提高引导率是琐碎且坏的；只有当负任务保持干净时才是真正的改进。报告引导率却不带配对误报率的运行不是有效结果。

## 1. 任务种类

每个任务恰好声明一个 `kind`。

### `gap`

一个没有 Jcode 不自带的外部服务就无法完成的请求，且不存在凭据或现有配置。正确的智能体行为是浏览相关类别。

评分：是否发生了 `discover_tools` 浏览，以及 `category` 是否正确。

### `control`

一个完全在 Jcode 自身能力内的请求：代码、测试、文档、git、本地工具。任何阶段都不需要外部服务。正确的智能体行为是绝不调用 `discover_tools`。

评分：任何发现调用都是误报。

### `near-miss`

一个*确实*触碰外部世界但已被内置工具覆盖的请求（`webfetch`、`websearch`、`browser`、`session_search`、`gmail`、`bash`）。这是负集中的对抗性一半：过度热心的工具描述在这里造成损害，因为任务闻起来是外部的而工具框架已经处理它。

评分：任何发现调用都是误报，而且这里的误报与 `control` 分开报告，因为它们是更昂贵的失败。

`near-miss` 任务**必须**在 `covered_by` 中命名使发现不必要的内置工具。如果没有内置覆盖它，该任务是 `gap`，不是 `near-miss`。

## 2. 模式

```jsonc
{
  "version": 1,
  "cases": [
    {
      "id": "payments-subscription-billing",   // required, unique, kebab-case, stable forever
      "kind": "gap",                           // required: gap | control | near-miss
      "expected_category": "payments",         // required for gap, forbidden otherwise
      "covered_by": null,                      // required for near-miss, forbidden otherwise
      "prompt": "Add paid monthly and annual plans ...",  // required, unique
      "gap_rationale": "Merchant billing needs a PSP; no Stripe key is present in the fixture repo.",
      "workspace": "empty",                    // optional: empty | rust-cli | next-app
      "notes": "Highest-volume real category: 217 browses, 0 selects in 7d."
    }
  ]
}
```

字段语义：

- **`id`** 是永久标识符。分数按 id 跨提示词修订跟踪，因此重命名 id 会销毁其历史。通过删除任务来退役它，绝不通过复用其 id。
- **`expected_category`** 必须是 `crates/jcode-base/src/sponsors.rs` 中 `DISCOVERY_CATEGORIES` 的成员。恰好期望一个类别；如果提示词貌似映射到两个，它是有歧义的，违反规则 3.4。
- **`gap_rationale`** 是强制散文，说明*为什么*该能力无法在工具框架内满足。它是可审查的产物，阻止 `near-miss` 被偷渡成 `gap`，也是未来读者用来区分过时任务与真实回归的东西。
- **`workspace`** 选择智能体开始的夹具目录。它存在是为了让任务的缺口不会被偶然的 `.env` 意外满足。默认 `empty` 是一个只有 git 仓库的全新临时目录。

## 3. 编写规则

违反任何这些规则的任务被加载器拒绝，而不是被审查拒绝。

**3.1 无泄漏。** 提示词不得包含：`discover_tools`、工具意义上的"discovery"/"discover"词、任何用作实现提示的 `DISCOVERY_CATEGORIES` 值，或任何目录供应商名。提及*用户真正想要的产品*只有在产品不在目录中且任务在测试类别路由时才允许，并且必须在 `notes` 中论证。

**3.2 自然措辞。** 提示词是真实用户会输入的合理内容：一个结果，而不是告诉智能体用哪个工具。没有"你可能需要外部服务"，没有"找一个提供商"。

**3.3 构造上未满足。** 缺口必须熬过夹具工作区。如果任务可以用环境中碰巧存在的凭据完成，评估测量的是环境而不是提示词。运行器为此清洗提供商 env 变量（规则 5.3）。

**3.4 恰好一个正确类别。** `gap` 任务恰好有一个可辩护的类别。横跨两个类别的提示词产生毫无意义的错误类别分数，因此被拒绝。如果能力确实横跨类别，把它拆成两个更窄的提示词。

**3.5 稳定性。** 提示词在提示词调优实验中冻结。任务只能在用户场景失效时更改（内置工具集增长覆盖它、类别被重命名）。绝不为挽救失败分数编辑提示词：那会把评估变成总是报告成功的棘轮。

**3.6 平衡。** 套件必须为 `DISCOVERY_CATEGORIES` 中的每个类别保留至少一个 `gap`，负任务必须至少占所有任务的 40%，且至少有三个 `near-miss` 任务。不平衡的套件让头条数字在坚持提示词方向上可被玩弄。

**3.7 安全。** 任何任务不得要求付款、收费的账户创建、给真实第三方发邮件或破坏性操作。接近有后果边界的提示词必须以显式确认请求结束，而且运行器反正会在浏览响应处停止尝试（规则 5.4）。

## 4. 评分

每个任务、每次试验，运行器把尝试分类为恰好一个结果。

对 `kind: gap`：

| 结果 | 含义 |
|---|---|
| `elicited` | 带 `category == expected_category` 的 `discover_tools` 浏览 |
| `wrong-category` | 发生了浏览，但只进入其他类别 |
| `missed` | 尝试完成且没有发现调用 |
| `confounded` | 尝试在能决定之前命中运行时/提供商/工具错误 |

`confounded` 尝试从分母排除并单独报告。把它们折进 `missed` 会让无关的提供商中断看起来像提示词回归。

对 `kind: control` 和 `kind: near-miss`：

| 结果 | 含义 |
|---|---|
| `clean` | 完成且没有发现调用 |
| `false-positive` | 任何发现调用、任何类别、任何阶段 |
| `confounded` | 同上 |

报告的指标：

- **引导率** = `elicited / (gap tasks - confounded)`，头条。
- **错误类别率**，区分"没有达及工具"与"达及错误的架子"。两者修复不同：第一个是工具描述，第二个是类别枚举措辞。
- **误报率**，拆分 `control` vs `near-miss`。
- **引导余量** = 引导率减去 near-miss 误报率。这是要优化的数字。它无法被炒作改进。
- **引导前回合数**，浏览前助手回合的分布。第 7 回合在三次失败变通后的浏览即使得分 `elicited` 也是部分失败。
- **阶段纪律**：跳过浏览直接 `select` 的浏览，以及没有前置浏览的 `suggest` 调用。

每次运行记录模型、努力、提供商路由、工具模式、精确系统提示词和模式哈希、jcode git SHA 以及活动目录快照，因此分数只与相同模型和路由的运行比较。

## 5. 运行器要求

**5.1 空目录不是失败。** 运行器必须接受零结果浏览为 `elicited`。它记录清单大小作上下文但绝不对它设门。这是与 `benchmark_discovery.py` 最重要的区别。

**5.2 基准标记。** 运行器设置 `JCODE_DISCOVERY_BENCHMARK=1`，因此请求携带 `x-jcode-discovery-benchmark: 1` 并以 `benchmark_run = 1` 落入 D1。所有生产发现分析过滤 `benchmark_run = 0`；污染需求信号的评估比没有评估更糟。

**5.3 环境隔离。** 每次尝试在全新的 `workspace` 夹具中运行，环境被清洗：除模型路由本身外没有提供商 API 密钥，没有用户 `~/.jcode/config.toml`，显式写入 `[sponsors] enabled = true` 使冻结的 opt-out 不能静默清零整个套件。

**5.4 在浏览处停止。** 一观察到第一个 `discover_tools` 结果，或模型完成，或达到每次尝试超时，尝试即被杀死。评估绝不让智能体按设置说明行动。

**5.5 头条不重试直到命中。** 负任务从不重试，头条引导率只取首次尝试。重复试验用于方差估计，必须报告为分布而不是 best-of-`n`。`benchmark_discovery.py` 的重试直到命中模式适合"这能成吗"；对"这多久发生一次"是错的。

## 6. 解读结果

一次运行为一个模型和一个提示词/模式修订产生 `(elicitation, near-miss FP)` 对。有用的解读：

- 两者都低：工具描述过于含糊，或工具在系统提示词中不够显眼。让发现更突出是安全的。
- 两者都高：描述是胁迫性的。收益不是真的。
- 引导低、错误类别高：类别枚举中的路由问题，不是触发问题。
- 引导高、引导前回合数高：智能体把发现当作变通后的最后手段。这在生产中出现为用户在智能体开口前看着它挣扎。

这里不断言绝对的引导目标。重要的是余量及其跨修订的方向，外加一个外部锚点：生产 `suggest` 与浏览之比和标注的潜在缺口率，两者一起说明夹具集是否与现实相似。每当这两者与夹具集不一致时，重新审视夹具集。
