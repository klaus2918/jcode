数据来源：

- `jcode-telemetry` D1（`discovery_details` 关联 `events`）用于客户端侧尝试，包括从未到达端点的尝试。
- `jcode-subscriptions` D1（`discovery_request_events`、`discovery_events`、`discovery_suggestions`）用于服务器侧漏斗、原始 `query`/`reason` 文本和来源分类。

## 2. 阻碍：168 个用户被硬禁用发现

`discovery_details` 记录了 168 次 `failure_reason = 'disabled'` 的失败，每个独立用户一次，即曾尝试发现的 625 个用户中的 27%。客户端版本大多是翻转后的（0.54.4：93，0.58.0：35），因此这些是 `~/.jcode/config.toml` 中持久化的 `[sponsors] enabled = false` 条目，不是当前默认值。

根因：发现以 `enabled = false` 的 opt-in 形式在 `203a3f3d3`（v0.36.x）发布，而 `Config::save()` 用 `toml::to_string_pretty` 序列化整个结构体。该窗口内的任何配置写入都把 `enabled = false` 冻结进用户文件。`e226b84c4` 的 opt-out 翻转只改了代码内默认值，因此那些文件永远禁用该工具，智能体根本看不到 `discover_tools`（`tool/mod.rs:293` 跳过注册）。

## 4. 为什么三个有货类别不转化

从 likely-user/unverified 浏览的原始 `query` 文本分桶（这三个类别 85 次浏览；其中 18 次返回零结果，因为早于清单存在）。

### payments（15 单位，1 select）

目录恰好一个条目：Agentcard，面向智能体的预付虚拟 Visa 卡。
实际需求：

- 9 个查询想要商户计费而不是智能体消费：托管结账、循环订阅、客户门户、签名 webhook、支付链接、Stripe 正式模式产品管理、带拆分付款的市场托管。
- 4 个查询想要区域或平台轨道：Razorpay 查询、微信支付 v3、Toss Payments 商户接入、Google Play 计费 / RevenueCat 订阅测试。
- 1 个查询想要提供商计费自省（"读取我的 API 额度/费用"）。
- 1 个查询是真正的虚拟卡匹配，它转化了。

payments 中的具名产品缺口建议：Stripe Billing、Stripe Connect、Stripe、Razorpay、Google Play Billing、Toss Payments。

### code-review（18 单位，3 selects）

目录：Greptile，仓库感知的 PR 审查，需要 Node 22、全局 npm 安装、交互式 `greptile login` 以及智能体无法完成的 `greptile onboard` 向导。

- 9 个查询实际上是 Git 主机认证而不是审查：推送到被拒绝的上游、fork 并开 PR、私有 Gitea 推送、GitLab MR 讨论和行内评论、GitHub issue 访问。
- 7 个查询想要一个独立的本地审查器来审查未提交 diff，通常因为集群审查器派生失败，或特别想要 SonarQube/Ponytail/OpenCode Orcal。
  Greptile 不能审查未提交的本地 diff，除非先接入仓库。
- 3 个 select 来自措辞匹配"仓库感知 PR 审查"的查询。

这里的主导模式是 jcode 功能失败（集群审查器不可用、递归派生被禁用）泄漏到发现中作为变通尝试。

### web-data（27 单位，2 selects）

目录：context.dev，抓取和结构化提取。需求：

- 12 个查询想要特定数据源而不是通用抓取器：YouTube/Bilibili 记录、丹麦土地登记、Google Merchant Center、按 DOI 的 ACM 全文、Polygon.io 股票、Figma 文件、Mobbin 截图、反向电话查询、ETF 历史、股票视频 API。
- 4 个查询想要搜索引擎 API，因为 `websearch` 被反机器人页面阻止。
- 2 个查询想要 GitHub MCP 仓库访问。
- 11 个是杂项一次性富集或提取请求。
- 两个 select 都来自措辞为通用抓取/提取的查询。

## 6. 可操作的结论

1. 修复 168 个卡住的配置。把 opt-out 翻转前写入的持久化 `sponsors.enabled = false` 视为未设置，或在加载时迁移一次。同时阻止 `Config::save()` 把默认值部分写回磁盘，那正是冻结该标志的原因。
2. 填满空类别或缩小类别列表。14 个空类别意味着大多数浏览注定未命中，智能体随后还要花第二次调用做 `suggest`。添加没有清单的类别只会让未命中率更糟：每个新空类别都是另一次保证零结果的浏览加上一次后续 `suggest`。
3. 把 payments 扩展到智能体发卡之外。商户计费占 payments 需求的 60%，目前完全没有清单。
4. 把 code-review 与 Git 主机访问分开。大多数 code-review 浏览是认证/访问请求；GitHub/GitLab 清单可以服务它们，而 Greptile 的交互式接入是智能体完成设置的硬阻碍。
5. 修复产生发现流量的上游功能失败：集群审查器派生失败和被阻止的 `websearch` 占 code-review 和 web-data 浏览的很大份额。
6. 对设置完成插桩。`discovery_usage` 是空的，因此 `select` 之后没有任何可观察的东西。没有它，"select"是我们唯一的转化代理。
