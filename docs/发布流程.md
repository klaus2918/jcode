# 发布流程（本 fork）

本文件是本仓库（`klaus2918/jcode`，upstream `1jehuang/jcode` 的 fork）的发布规范。
上游的 `RELEASING.md` 描述的是 upstream 的发布假设（部署密钥、Azure 签名、七平台必达），
**本 fork 已按自身条件改造，以本文件为准**；两者冲突时以本文件为准。

## 1. 发布模型

- **版本线独立**：fork 不跟随 upstream 的版本号，只沿用 semver 语义。fork 是否合并 upstream 新版本，
  是发布内容的一部分，需要写进发行说明。
- **tag 驱动**：推送 `v*` tag 触发 `.github/workflows/release.yml`。这是唯一正式发布通道。
- **构建在 CI**：本地不做发布构建，避免“本地产物与 tag 内容不一致”。理由见 §6。
- **草稿门禁**：CI 先建 draft release，只有必达平台资产齐全才转为 public。

## 2. 版本号规范

| 变更性质 | 递增位 | 示例 |
|---|---|---|
| 修复缺陷、内部重构、依赖升级 | patch | `v0.65.0` → `v0.65.1` |
| 新增用户可见能力、新增斜杠命令、新增配置项 | minor | `v0.65.1` → `v0.66.0` |
| 破坏性变更（配置文件不再兼容、命令被移除） | major | `v0.66.0` → `v1.0.0` |

规则：

1. **一次发布一个 tag，tag 只增不改。** 已推送的 tag 绝不移动、绝不复用。
2. **`Cargo.toml` 的 `version` 是版本唯一真源。** 二进制版本、tag、changelog 文件名、发行说明
   四处必须一致；`Cargo.lock` 需一并刷新。
3. **首发版本**：fork 首个正式版本为 `v0.65.0`，之后按上表递增。
4. 预发布（如需）：用 `v0.66.0-rc.1` 这类带后缀的 tag，并在 GitHub release 上标记 pre-release。

## 3. 发布产物与平台策略

| 平台 | 资产名 | 策略 |
|---|---|---|
| Windows x86_64 | `jcode-windows-x86_64.exe` / `.tar.gz` | **必达**，缺失则发布停留在 draft |
| Linux x86_64 | `jcode-linux-x86_64.tar.gz` | best-effort |
| Linux aarch64 | `jcode-linux-aarch64.tar.gz` | best-effort |
| macOS Apple Silicon | `jcode-macos-aarch64.tar.gz` | best-effort |
| macOS Intel | `jcode-macos-x86_64.tar.gz` | best-effort |
| Windows ARM64 | `jcode-windows-aarch64.exe` / `.tar.gz` | best-effort |
| FreeBSD x86_64 | `jcode-freebsd-x86_64.tar.gz` | best-effort |
| 校验和 | `SHA256SUMS` | 必定生成，覆盖本次实际发布的全部资产 |

- best-effort 平台失败不会阻塞发布，但会在 CI 日志里产生 `::warning::` 注解，并写入发行说明的
  `Platform availability` 段落，不会静默丢失。
- **Windows 资产未做 Authenticode 签名**（本仓库未配置 Azure Artifact Signing）。
  首次运行会出现 SmartScreen 警告；CI 会把这个事实写进当次运行的 step summary。
  日后配齐 `AZURE_*` secrets 与 `WINDOWS_SIGNING_*` variables 后自动变为签名发布，无需改 workflow。

## 4. 一次性前置条件

发布前需确认下列配置已完成（这是 fork 相对 upstream 的最大差异，未配置时 CI 根本不会跑）：

- [x] 仓库 **Actions 已启用**（fork 默认关闭）—— 2026-09-12 已核实：5 个 workflow 均已注册且 `state: active`
- [ ] **Workflow 权限为读写**：`Settings → Actions → General → Workflow permissions → Read and write permissions`
      （release job 需要它创建/更新 release 并上传资产；这一项无法从外部核实，上线前需人工确认）
- [ ] 已移除对 `secrets.DEPLOY_KEY` 的依赖（本 fork 已改造完成，见 §7）
- [ ] 无需配置密钥：本 fork 依赖全部走 HTTPS 公共仓库
- [ ] 可选：Homebrew / AUR 发布需 `HOMEBREW_DEPLOY_KEY` / `AUR_SSH_KEY` secrets，
      未配置时对应步骤自动跳过，不影响主发布

## 5. 标准发布流程

```bash
# 0. 工作区干净，且已同步远端
git status --short          # 应为空（或只有本次要提交的内容）
git pull --ff-only origin master

# 1. 确认发布内容：列出上次发布以来的提交，逐条判断用户是否可见
git log --oneline v<PREV>..HEAD

# 2. 写 release metadata（见 §5.1），一次提交推上去
git add Cargo.toml Cargo.lock changelog/
git commit -m "release: v0.65.0"
git push origin master

# 3. 打 tag 并推送，触发 CI 发布
bash scripts/quick-release.sh --remote v0.65.0
```

Windows 环境说明：`quick-release.sh --remote` 只依赖 `git`，在 Git Bash 中可直接运行：

```bash
bash scripts/quick-release.sh --remote v0.65.0
```

### 5.1 release metadata 提交内容（三件套）

**硬规则：这个提交只允许包含 `Cargo.toml`、`Cargo.lock`、`changelog/` 三类文件。**

1. **`Cargo.toml`**：`version = "0.65.0"`（去掉 `v` 前缀）。
2. **`Cargo.lock`**：同步刷新，否则所有 `--locked` 构建失败。
   刷新方式（二选一，本地执行）：
   ```bash
   cargo check -p jcode            # 会按需更新 lock
   # 或
   cargo update -p jcode --precise 0.65.0
   ```
3. **`changelog/v0.65.0.json`**：按 `changelog/README.md` 的 schema 编写，面向用户描述效果。
   **首次发布必须有这个文件**，否则发行说明会退化成一份全量提交清单。

同时更新 **`changelog/index.json`**：在 `entries` 数组头部插入 `{"version": "0.65.0", "date": "YYYY-MM-DD"}`。

### 5.2 首发特例：没有上一个 tag

`scripts/generate_release_notes.sh` 在没有上一个 tag 时，把底部链接写成
`/commits/<tag>` 而不是 `/compare/<prev>...<tag>`，这是预期行为。

若希望首发也给出对照链接（例如相对 upstream `v0.84.0`），可手动指定：

```bash
bash scripts/generate_release_notes.sh v0.65.0 v0.84.0 > release_notes.md
```

从第二个 tag 开始，`git describe --tags` 能自动找到上一个 tag，无需手动干预。

### 5.3 替代流程：完全手动

`quick-release.sh` 不可用时，等价操作为：

```bash
git tag -a v0.65.0 -m "v0.65.0"
git push origin v0.65.0
```

CI 的 `create-release` job 会自行创建 draft release、生成发行说明，无需本地 `gh`。

## 6. 为什么不用本地产物发布

`quick-release.sh` 还有 `--fast-local`（本地构建 Linux 资产并立即公开）与 `--prepare-fast` 两种模式。
本 fork **不使用**，原因：

- `--fast-local` 要求 Linux x86_64 主机，并且要求发行提交不含任何代码文件
  （脚本会用 `git diff-tree` 校验，见 `scripts/quick-release.sh`）。
- 本 fork 的发布主机是 Windows，`--fast-local` 的组合校验没有实际收益，却引入了
  “本地产物与 tag 指向的源码不一致”的风险面。
- `--remote` 把构建、签名、校验全部交给 CI，产物与 tag 的对应关系由 CI 自己保证。

如确需本地快速路径，须在 Linux x86_64 主机上运行，并遵守脚本的前置校验。

## 7. 本 fork 对 workflow 的改造（相对 upstream）

改动集中在 `.github/workflows/`，目的是让上游为 upstream 基础设施编写的流水线能在 fork 跑通。
每处改动都带 `# fork:` 注释，便于日后 rebase upstream 时识别与重放。

| 文件 | 改动 | 原因 |
|---|---|---|
| `ci.yml` | 移除 4 处 `secrets.DEPLOY_KEY` 与 `ssh-agent` 步骤 | fork 无部署密钥；依赖全是 HTTPS |
| `ci.yml` | 去掉 `push` 触发，改为 `pull_request` + `workflow_dispatch` | 上游每次 push 跑 9 个重型 job，fork 上没有必要 |
| `release.yml` | 移除 `build-linux-macos` 的 `DEPLOY_KEY` / `ssh-agent` | 同上 |
| `release.yml` | Windows 签名由“必需”改为“可选增强” | fork 无 Azure Artifact Signing 账号 |
| `release.yml` | 资产完整性校验改为“Windows x86_64 必达 + 其余 best-effort” | 上游的七平台全齐门禁会让 release 永久卡在 draft |
| `release.yml` | 移除 `Close issues included in the published release` | 本仓库已关闭 Issues，该步骤必然报错 |
| `ci.yml` | `Run Windows hotkey and power tests` 改名并移除 `-p jcode-setup-hints` 调用 | 该 crate 已随 macOS 菜单栏与热键功能删除（863cc9b04），上游调用会让 job 失败 |
| `scripts/build_linux_compat.sh` | 移除 `--features linux-compat-vendored-openssl` | 该 feature 随 `523acc50a` 一同被删，而 fork 已无 OpenSSL 依赖，保留会让 Linux 便携构建报错 |

### 已随 `523acc50a` 一并移除、但当时被漏掉的引用

`523acc50a`（feature-simplification）删掉了 `linux-compat-vendored-openssl` feature，但其目的是摘除
azure/notify/overnight/doctor 与 Mermaid 渲染面——该 feature 当时是顺带掉落的。
它原本的链条是：

```
jcode → jcode-tui → jcode-app-core → jcode-notify-email（dep:native-tls + native-tls/vendored）
```

而 `jcode-notify-email` 也已在同一提交中被删除，Cargo.lock 里已无 `openssl-sys` / `native-tls` /
`openssl-src`，即本 fork 确实不再需要 vendored OpenSSL。因此修法是把脚本里这个已不存在的
feature 标志删掉，而不是把 feature 恢复回来（恢复反而会引用已删除的 crate）。

影响面：`scripts/build_linux_compat.sh` 是 Linux x86_64 便携产物的唯一构建入口
（`release.yml` 的 x86_64 job 与 `quick-release.sh` 标准模式都用它）。修复前它会在
`cargo build --features` 阶段直接报错，导致每次发布的 Linux x86_64 都缺失。

**未改动**：`install.sh` / `install.ps1` 仍指向 upstream 的 `REPO` 与 `jcode.sh` 元数据服务。
因此 fork 的 Release 产物**不要**用 upstream 的在线安装脚本安装，请用 §9 的本地方式。

### rebase upstream 时的核对清单

1. 上述 7 处 `# fork:` 改动是否被 upstream 版本覆盖；若被覆盖，重新施加。
2. `RELEASING.md` 若被 upstream 更新，核对 §1–§3 的平台策略与签名假设是否仍与本 fork 一致。
3. 上游若新增消费 `secrets.*` 的步骤，确认在 fork 上缺失时是「跳过」而不是「失败」。
4. 上游若新增对 workspace crate 的 `-p <crate>` 调用，核对该 crate 在本 fork 是否仍存在。
   本 fork 已删除若干 crate，上游引用会让对应 job 直接失败（已修过 `jcode-setup-hints` 一例）。
5. 上游若改回由 `native-tls` / `openssl-sys` 承担某条链路，需重新评估是否要恢复
   `linux-compat-vendored-openssl`（本 fork 当前无 OpenSSL 依赖，故该 feature 已删）。

### 已知的既有不一致（不影响发布，但影响手工安装体验）

fork 在 `863cc9b04` 移除了 macOS 菜单栏与全局热键能力，`setup-hotkey` CLI 子命令已不存在，
但 `scripts/install.ps1` 仍保留 `-ConfigureHotkey`：它会创建一个启动快捷方式，
指向 `jcode setup-hotkey --listen-windows-hotkey`，而该子命令已经不存在，所以手动带
`-ConfigureHotkey` 安装后热键不会工作。

**为什么不阻塞发布**：`.github/scripts/verify_windows_install.ps1` 会设置
`JCODE_WINDOWS_SETUP_SKIP_PROCESS_LIFECYCLE=1`，install.ps1 据此跳过监听器启动。
真正被断言的只是快捷方式的 TargetPath 与参数文本，而这些仍与 install.ps1 一致，
所以必达平台安装验证仍会通过。

**处理选项**（需要产品决策，本 fork 暂未动）：

1. 保留现状，但不在安装提示里推荐热键；
2. 从 `install.ps1` / `install.sh` / `install_release.sh` 与其测试中移除 `-ConfigureHotkey`；
3. 重新实现 `setup-hotkey` 子命令。

另：`docs/Windows平台.md` 与 `docs/键位冲突检测.md` 仍引用已删除的
`crates/jcode-setup-hints/src/...` 路径，属同一批删除后的文档残留。

### PR 流程上的一个限制

`.github/workflows/require-issue.yml`（上游的贡献策略）要求每个 PR 关联一个**本仓库**的
issue，但本 fork 的 Issues 是关闭的，因此向本 fork 提 PR 时该检查会一直显示 ❌。
它不影响合并（除非另配了分支保护），但会让 PR 页面看起来是红的。

处理选项：

1. 接受现状，把 PR 当作代码评审载体，忽略该 ❌；
2. 删除 `require-issue.yml`（本 fork 不需要上游的 issue 关联策略）；
3. 在本 fork 开启 Issues，使该 workflow 可用。

另：`windows-smoke.yml` 与 `freebsd-smoke.yml` 都是 `workflow_dispatch` 手动触发
（freebsd 另有周一定时），不会在 push 时自动跑，所以不影响日常提交。

## 9. 使用发布产物

本 fork 的产物不提供在线安装脚本，使用本地装包方式：

```powershell
# 下载 release 资产后，安装或更新本机 jcode
jcode update --local C:\dist\jcode-windows-x86_64.tar.gz
# 或直接用单文件 exe
jcode update --local C:\dist\jcode-windows-x86_64.exe
```

校验下载完整性：

```powershell
# 与 release 的 SHA256SUMS 对照
(Get-FileHash C:\dist\jcode-windows-x86_64.exe -Algorithm SHA256).Hash
```

本 fork 已移除 `jcode update` 的在线自更新（仅保留本地装包与 git 源码重建），
所以不存在“自动拉到 upstream 版本”的风险。

## 10. 异常处置

### 10.1 部分平台失败，release 卡在 draft

1. 打开 Actions 里失败 job 的日志，确认失败平台与原因。
2. 若失败的是 best-effort 平台：脚本不会因它阻塞发布；先确认 `release` job 本身是否因
   **Windows x86_64 缺失** 而退出。若是 Windows 缺失，按 10.2 处理。
3. 若仅是偶发失败（网络、runner 配额），重跑失败 job：
   `Actions → Release → 对应 run → Re-run failed jobs`。
4. 重跑后 `release` job 会重新校验并尝试发布，无需重新打 tag。

### 10.2 Windows x86_64 构建失败

Windows 是唯一必达平台，失败即发布不出去。

1. 在 Actions 中重跑 `Build (x86_64-pc-windows-msvc)` job。
2. 若持续失败，先在本地复现：`cargo build --locked --profile release-lto --target x86_64-pc-windows-msvc`。
3. 修复后：**不要移动已有 tag**。tag 已指向的提交不可变。正确处理是修一个 patch 版本
   （`v0.65.1`），并在发行说明里说明 `v0.65.0` 未发布。

### 10.3 tag 推错了 / 需要撤回一次发布

- tag 已推送且 release 已 public：**不能删除后重推同名 tag**（会破坏消费者与校验和的可追溯性）。
  正确做法是发一个新的 patch 版本。
- 只有确属事故（误推了完全无关的提交、tag 上什么都没有）时，才在维护者确认后删除远端 tag，
  并在本地同步删除：`git tag -d vX.Y.Z` + `git push origin :refs/tags/vX.Y.Z`。
  这是不可逆操作，必须经 `safe-git-write` 确认。
- 仅想把已发布的 release 撤下：在 GitHub 上把它改回 draft 或标记为 pre-release，
  **保留 tag**，避免版本号空洞。

### 10.4 发布后才发现必须回滚

发布资产是二进制，不能原地替换（消费者可能已下载并校验过）。

1. 保留问题版本的 release 与 tag，在其发行说明顶部追加醒目的已知问题说明。
2. 修复后发一个更高版本（patch）。
3. 若问题版本危害较大，把该 release 标记为 pre-release，让 `/releases/latest` 回退到上一个正常版本。

## 11. 与其他协作者并行

- 工作区可能有其他 agent 在改代码。发布前必须确认工作区只剩 release metadata 变更。
- release metadata 提交只包含 §5.1 的三类文件；发现混入代码文件时，拆开重新提交。
- 所有 git 写操作（含打 tag、推 tag）统一走 `safe-git-write` 流程确认后执行。
