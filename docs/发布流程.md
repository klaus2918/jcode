# 发布流程（本 fork）

本文件是本仓库（`klaus2918/jcode`，upstream `1jehuang/jcode` 的 fork）的发布规范。
上游的 `RELEASING.md` 描述的是 upstream 的发布假设（部署密钥、Azure 签名、七平台必达），
**本 fork 已按自身条件改造，以本文件为准**；两者冲突时以本文件为准。

## 1. 发布模型

- **版本线独立**：fork 不跟随 upstream 的版本号，只沿用 semver 语义。fork 是否合并 upstream 新版本，
  是发布内容的一部分，需要写进发行说明。
- **tag 驱动**：推送 `v*` tag 触发 `.github/workflows/release.yml`。这是唯一正式发布通道。
- **构建在 CI**：本地不做发布构建，避免“本地产物与 tag 内容不一致”。理由见 §6。
- **草稿门禁**：CI 先建 draft release，只有必达平台资产齐全才转为 public。

## 2. 版本号规范

| 变更性质 | 递增位 | 示例 |
|---|---|---|
| 修复缺陷、内部重构、依赖升级 | patch | `v0.65.0` → `v0.65.1` |
| 新增用户可见能力、新增斜杠命令、新增配置项 | minor | `v0.65.1` → `v0.66.0` |
| 破坏性变更（配置文件不再兼容、命令被移除） | major | `v0.66.0` → `v1.0.0` |

规则：

1. **一次发布一个 tag，tag 只增不改。** 已推送的 tag 绝不移动、绝不复用。
2. **`Cargo.toml` 的 `version` 是版本唯一真源。** 二进制版本、tag、changelog 文件名、发行说明
   四处必须一致；`Cargo.lock` 需一并刷新。
3. **首发版本**：fork 首个正式版本为 `v0.65.0`，之后按上表递增。
4. 预发布（如需）：用 `v0.66.0-rc.1` 这类带后缀的 tag，并在 GitHub release 上标记 pre-release。

## 3. 发布产物与平台策略

**本 fork 只发布 Windows x86_64。** 这是个刻意的取舍，不是遗漏：

- 本 fork 的使用场景就是 Windows。构建其他平台没有消费者，却要付真金白银的代价。
- 原先跟随上游构建 7 个平台时，FreeBSD 走 QEMU 虚拟机（超时上限 180 分钟），
  而最终 `release` 作业必须等它结束才会把 release 转正——
  结果是“只要一个 Windows 包”也要等最坏 3 小时，还可能被无关平台的偶发失败拖成永久 draft。
- 裁剪后只有一条链路：构建 → 签名（可选）→ 校验和 → 发布，预期端到端 15–20 分钟。

| 平台 | 资产名 | 策略 |
|---|---|---|
| Windows x86_64 | `jcode-windows-x86_64.exe` / `.tar.gz` | **唯一产物**，缺失则发布停留在 draft |
| 校验和 | `SHA256SUMS` | 必定生成，覆盖本次实际发布的全部资产 |

- **Windows 资产未做 Authenticode 签名**（本仓库未配置 Azure Artifact Signing）。
  首次运行会出现 SmartScreen 警告；CI 会把这个事实写进当次运行的 step summary。
  日后配齐 `AZURE_*` secrets 与 `WINDOWS_SIGNING_*` variables 后自动变为签名发布，无需改 workflow。
- 发行说明末尾的 `Platform availability` 会明写“仅发布 Windows x86_64”，
  避免使用者以为是构建失败而缺失其他平台。
- 如需恢复某个平台：从上游 `release.yml` 取回对应作业，并在 `release` 作业的 `needs`
  与必达资产列表里加回（见 §7 的裁剪说明）。

## 4. 一次性前置条件

发布前必须确认下列配置。这是 fork 相对 upstream 的最大差异：**未配置时 push 与 tag 都不会产生任何运行，而且 GitHub 不报错、不提示。**

- [ ] **fork 的 Actions 必须由仓库所有者手动启用**（最关键的一项，见下方判别方法）
      路径：仓库页 `Actions` 标签 → 黄色横幅 `Workflows aren't being run on this forked repository` →
      点 `I understand my workflows, go ahead and enable them`
- [ ] **Workflow 权限为读写**：`Settings → Actions → General → Workflow permissions → Read and write permissions`
      （release job 需要它创建/更新 release 并上传资产）
- [ ] 已移除对 `secrets.DEPLOY_KEY` 的依赖（本 fork 已改造完成，见 §7）
- [ ] 无需配置密钥：本 fork 依赖全部走 HTTPS 公共仓库
- [ ] 无需 Homebrew / AUR 的 `HOMEBREW_DEPLOY_KEY` / `AUR_SSH_KEY`：
      `release.yml` 已移除这两个发布步骤（见 §7 的裁剪表），
      `scripts/update_packages.sh` 仍在仓库里，但已无任何 CI 调用

### 4.1 如何判别「已注册」与「已启用」（排障必读）

**`GET /repos/{owner}/{repo}/actions/workflows` 返回 `state: active` 只说明 workflow 文件存在，
并不代表事件会触发它。** fork 默认处于「不运行工作流」状态，此时：

- workflow 列表里**能看到**该 workflow（因为文件已经存在）
- Actions 页显示 `0 workflow runs`，单个 workflow 页显示 `This workflow has no runs yet.`
- push 与 tag 推送**静默丢弃**，不产生运行、不报错（因为本来就一个都没跑过，无法从历史看出漏跑）

判别方法（四步，依次加强）：

1. `GET /repos/{owner}/{repo}/actions/runs?per_page=1` —— `total_count` 为 `0` 即「从未跑过」。
   若仓库已有大量 push 但仍为 0，基本可判定 Actions 未启用。
2. `GET /repos/{owner}/{repo}/actions/workflows` —— 看各 workflow 的 `updated_at`。
   如果**刚刚改过某个 workflow 文件却仍停留在 fork 创建日**，说明 GitHub 根本没在追踪这些
   定义（未启用时不解析），这是很硬的信号。
3. 打开 `https://github.com/{owner}/{repo}/actions`，看是否有黄色横幅
   `Workflows aren't being run on this forked repository`。
4. 推一个 tag 后等 1–2 分钟再看 `actions/runs`。仍为 0 且 workflow 文件里 `on: push: tags` 正确，
   即可确认是启用问题而非配置问题。

本 fork 首次排查时（2026-09-12）同时命中了以上 1、2、4：零运行、`updated_at` 冻结在 fork 创建日、
标签推送无反应。

### 4.2 启用后不补跑历史事件，需重新触发

启用开关**不会**回放已丢弃的事件。已推送的 tag 不会自动补跑，必须重新触发。

**推荐：用脚本，它会先强制检查安全前提**（无法使用脚本时见下方「手动等价操作」）：

```bash
scripts/retrigger-release.sh --dry-run vX.Y.Z   # 只检查前提，不动任何东西
scripts/retrigger-release.sh vX.Y.Z            # 删除 + 同名重建 + 推送
```

两个常用变体：

- `--at <ref>`：把 tag 重建到指定提交。**发布链路本身刚改过时必须用**，否则重跑的还是
  旧 workflow（tag 仍指旧提交）。例：`scripts/retrigger-release.sh --at HEAD v0.65.0`。
- `--assume-no-release`：跳过 release 查询（见下）。

若该 tag 已存在一个**草稿** release（异常中止的旧运行会留下），重建 tag 前先清理：

```bash
scripts/delete-draft-release.sh --dry-run vX.Y.Z   # 先看资产清单
scripts/delete-draft-release.sh vX.Y.Z             # 真删
```

它只删草稿；已公开的 release 一律拒绝删除（那种情况必须发新版本，见 §10.3）。

脚本会拒绝以下情况：

1. tag 本地与远端指向不同 commit
2. 该 tag 已有 release（含草稿；§10.3 的硬禁区，草稿需先用 §4.2 的脚本清理）
3. release 元数据（Cargo.toml / Cargo.lock / changelog/）有未提交改动
4. 目标 commit 不在 `origin/master` 上
5. tag 名与目标提交的 `Cargo.toml` 版本不一致（防止「tag 是 v0.65.0 但产物报 0.64.x」）
6. 目标提交缺少 `changelog/v<version>.json`（否则发行说明会退化成提交清单）
7. 目标提交缺少 `.github/workflows/release.yml`（推了也不会有构建）

第 5、6 条对应 §5.1 的「先提交版本元数据、再打 tag」纪律，第 7 条则拦住“流水线文件本身缺失”
这种一眼看得出、却很容易在执行时被忽略的情况。

它还会拒绝在**查不到 release 列表**时放行（受限网络下 curl 可能被拦，脚本会依次尝试
curl / python3 / PowerShell；三者都不通才要求你先在网页上确认无 release，再加 `--assume-no-release`）。

手动等价操作：

```bash
# 仅当该 tag 尚未产生任何 release / 资产时可用（见 §10.3 的硬条件）
git push origin :refs/tags/vX.Y.Z     # 删除远端 tag
git tag -d vX.Y.Z                     # 删除本地 tag（若还在）
git tag -a vX.Y.Z -m "vX.Y.Z"         # 在同一个 commit 上重建
git push origin vX.Y.Z
```

若该 tag 已经产生过 release 或被人下载过，则不要重建同名 tag，改为发一个更高的 patch 版本（§10.3）。

### 4.3 只有 tag 能触发发布，但 CI 可手动跑

- `release.yml` **没有** `workflow_dispatch`，只能由 `v*` tag 触发。即：发布套路的唯一入口是 tag，
  这也是为什么启用 Actions 后必须重建 tag（§4.2）。
- `ci.yml` **有** `workflow_dispatch`，可在 Actions 页选 `CI` → `Run workflow` 手动跑。
  启用 Actions 后如果想先确认「工作流真的会跑了」而不动 tag，可以用这个做一次验证
  （代价是它会跑完整套守卫与构建，耗时较长）。
- 另两个 smoke workflow 也都是手动触发：`Windows Smoke`、`FreeBSD Smoke`
  （FreeBSD 另有一条周一定时）。日常 push 不会自动产生任何运行。

## 5. 标准发布流程

```bash
# 0. 工作区干净，且已同步远端
git status --short          # 应为空（或只有本次要提交的内容）
git pull --ff-only origin master

# 1. 确认发布内容：列出上次发布以来的提交，逐条判断用户是否可见
git log --oneline v<PREV>..HEAD

# 2. 写 release metadata（见 §5.1），一次提交推上去
git add Cargo.toml Cargo.lock changelog/
git commit -m "release: v0.65.0"
git push origin master

# 3. 打 tag 并推送，触发 CI 发布
bash scripts/quick-release.sh --remote v0.65.0
```

Windows 环境说明：`quick-release.sh --remote` 只依赖 `git`，在 Git Bash 中可直接运行：

```bash
bash scripts/quick-release.sh --remote v0.65.0
```

### 5.1 release metadata 提交内容（三件套）

**硬规则：这个提交只允许包含 `Cargo.toml`、`Cargo.lock`、`changelog/` 三类文件。**

1. **`Cargo.toml`**：`version = "0.65.0"`（去掉 `v` 前缀）。
2. **`Cargo.lock`**：同步刷新，否则所有 `--locked` 构建失败。
   刷新方式（二选一，本地执行）：
   ```bash
   cargo check -p jcode            # 会按需更新 lock
   # 或
   cargo update -p jcode --precise 0.65.0
   ```
3. **`changelog/v0.65.0.json`**：按 `changelog/README.md` 的 schema 编写，面向用户描述效果。
   **首次发布必须有这个文件**，否则发行说明会退化成一份全量提交清单。

同时更新 **`changelog/index.json`**：在 `entries` 数组头部插入 `{"version": "0.65.0", "date": "YYYY-MM-DD"}`。

### 5.2 首发特例：没有上一个 tag

`scripts/generate_release_notes.sh` 在没有上一个 tag 时，把底部链接写成
`/commits/<tag>` 而不是 `/compare/<prev>...<tag>`，这是预期行为。

若希望首发也给出对照链接（例如相对 upstream `v0.84.0`），可手动指定：

```bash
bash scripts/generate_release_notes.sh v0.65.0 v0.84.0 > release_notes.md
```

从第二个 tag 开始，`git describe --tags` 能自动找到上一个 tag，无需手动干预。

### 5.3 替代流程：完全手动

`quick-release.sh` 不可用时，等价操作为：

```bash
git tag -a v0.65.0 -m "v0.65.0"
git push origin v0.65.0
```

CI 的 `create-release` job 会自行创建 draft release、生成发行说明，无需本地 `gh`。

## 6. 为什么不用本地产物发布

`quick-release.sh` 还有 `--fast-local`（本地构建 Linux 资产并立即公开）与 `--prepare-fast` 两种模式。
本 fork **不使用**，原因：

- `--fast-local` 要求 Linux x86_64 主机，并且要求发行提交不含任何代码文件
  （脚本会用 `git diff-tree` 校验，见 `scripts/quick-release.sh`）。
- 本 fork 的发布主机是 Windows，`--fast-local` 的组合校验没有实际收益，却引入了
  “本地产物与 tag 指向的源码不一致”的风险面。
- `--remote` 把构建、签名、校验全部交给 CI，产物与 tag 的对应关系由 CI 自己保证。

如确需本地快速路径，须在 Linux x86_64 主机上运行，并遵守脚本的前置校验。

## 7. 本 fork 对 workflow 的改造（相对 upstream）

改动集中在 `.github/workflows/`，目的是让上游为 upstream 基础设施编写的流水线能在 fork 跑通，
并按本 fork 的“只发 Windows”取向做减法。每处改动都带 `# fork` 注释，便于日后 rebase 时识别与重放。

| 文件 | 改动 | 原因 |
|---|---|---|
| `ci.yml` | 移除 4 处 `secrets.DEPLOY_KEY` 与 `ssh-agent` 步骤 | fork 无部署密钥；依赖全是 HTTPS |
| `ci.yml` | 去掉 `push` 触发，改为 `pull_request` + `workflow_dispatch` | 上游每次 push 跑 9 个重型 job，fork 上没有必要 |
| `release.yml` | **裁剪为 Windows x86_64 专用**（删除 `build-linux-macos`、`build-freebsd`，Windows 去掉 ARM64） | 本 fork 只面向 Windows；上游的 FreeBSD QEMU 构建超时上限 180 分钟，而 `release` 必须等它结束，于是“只要一个 Windows 包”也要等最坏 3 小时 |
| `release.yml` | Windows 签名由“必需”改为“可选增强” | fork 无 Azure Artifact Signing 账号 |
| `release.yml` | 必达资产收紧为 Windows 双资产（`.exe` + `.tar.gz`） | 缺一不可，避免发布半套产物 |
| `release.yml` | 移除 `Close issues included in the published release` | 本仓库已关闭 Issues，该步骤必然报错 |
| `release.yml` | 移除 Homebrew / AUR 更新步骤 | 它们依赖 Linux/macOS 资产，Windows 专用后已是死代码 |
| `release.yml` | 顺带：移除 Windows 发布路径里的 advisory 冒烟测试 | 它们编译整个 e2e 测试集会增加关键路径耗时；同类信号由 `windows-smoke.yml` 承载 |
| `ci.yml` | `Run Windows hotkey and power tests` 改名并移除 `-p jcode-setup-hints` 调用 | 该 crate 已随 macOS 菜单栏与热键功能删除（863cc9b04），上游调用会让 job 失败 |
| `scripts/build_linux_compat.sh` | 移除 `--features linux-compat-vendored-openssl` | 该 feature 随 `523acc50a` 一同被删，而 fork 已无 OpenSSL 依赖，保留会让 Linux 便携构建报错 |

| `scripts/install.ps1` | 嵌套调用改为 `-EncodedCommand`（两处） | `powershell -Command <多行脚本>` 会把参数重拼成命令行，带引号/多行的 payload 会被拆坏，导致嵌套进程以 -1 退出、快捷方式静默建不出来（详见下方“安装器嵌套调用”一节） |

### 安装器嵌套调用：一个只在真机上暴露的缺陷（已修）

`scripts/install.ps1` 原本用 `& powershell -NoProfile -Command $shortcutScript` 创建启动快捷方式。
该写法把一段多行脚本当作 `-Command` 的参数传递，PowerShell 会把参数重新拼成命令行，
带双引号与多行的 payload 会被拆坏：**嵌套进程以退出码 -1 终止，且不产生任何输出**。

后果：验证脚本 `verify_windows_install.ps1` 的 `-ConfigureHotkey` 断言失败，报
“Explicit hotkey setup did not create the Startup shortcut”。

实测对照（同一段脚本、同一台机器）：

| 传递方式 | 退出码 | 快捷方式 |
|---|---|---|
| `-Command <多行脚本>` | **-1** | 未创建 |
| `-EncodedCommand <base64>` | **0** | 已创建 |

**为什么值得记一笔**：该缺陷在 CI 上没有暴露（CI 环境的 PowerShell 恰好容忍了坏调用，
同一个断言在那里是绿的），只在真机上失败。所以“CI 绿”不能当成安装路径已验证。
修复后本地用**已发布产物**跑完整安装流程，验证器退出码为 0、
输出 `Windows install verification passed for v0.65.0`，且用户 PATH 未被改动。

### 已随 `523acc50a` 一并移除、但当时被漏掉的引用

`523acc50a`（feature-simplification）删掉了 `linux-compat-vendored-openssl` feature，但其目的是摘除
azure/notify/overnight/doctor 与 Mermaid 渲染面——该 feature 当时是顺带掉落的。
它原本的链条是：

```
jcode → jcode-tui → jcode-app-core → jcode-notify-email（dep:native-tls + native-tls/vendored）
```

而 `jcode-notify-email` 也已在同一提交中被删除，Cargo.lock 里已无 `openssl-sys` / `native-tls` /
`openssl-src`，即本 fork 确实不再需要 vendored OpenSSL。因此修法是把脚本里这个已不存在的
feature 标志删掉，而不是把 feature 恢复回来（恢复反而会引用已删除的 crate）。

影响面：`scripts/build_linux_compat.sh` 是 Linux x86_64 便携产物的唯一构建入口
（`release.yml` 的 x86_64 job 与 `quick-release.sh` 标准模式都用它）。修复前它会在
`cargo build --features` 阶段直接报错，导致每次发布的 Linux x86_64 都缺失。

**未改动**：`install.sh` / `install.ps1` 仍指向 upstream 的 `REPO` 与 `jcode.sh` 元数据服务。
因此 fork 的 Release 产物**不要**用 upstream 的在线安装脚本安装，请用 §9 的本地方式。

### rebase upstream 时的核对清单

1. 上表中 11 处改动是否被 upstream 版本覆盖；若被覆盖，重新施加。
   工作流里共有 9 处 `# fork` 标注（6 处写作 `# fork:`，`release.yml` 的 Windows 专用
   头部、签名可选、必达资产三处写作 `# fork 策略：`），可用
   `grep -rn '# fork' .github/workflows/` 定位。
2. `RELEASING.md` 若被 upstream 更新，核对 §1–§3 的平台策略与签名假设是否仍与本 fork 一致。
3. 上游若新增消费 `secrets.*` 的步骤，确认在 fork 上缺失时是「跳过」而不是「失败」。
4. 上游若新增对 workspace crate 的 `-p <crate>` 调用，核对该 crate 在本 fork 是否仍存在。
   本 fork 已删除若干 crate，上游引用会让对应 job 直接失败（已修过 `jcode-setup-hints` 一例）。
5. 上游若改回由 `native-tls` / `openssl-sys` 承担某条链路，需重新评估是否要恢复
   `linux-compat-vendored-openssl`（本 fork 当前无 OpenSSL 依赖，故该 feature 已删）。

### 已知的既有不一致（不影响发布，但影响手工安装体验）

fork 在 `863cc9b04` 移除了 macOS 菜单栏与全局热键能力，`setup-hotkey` CLI 子命令已不存在，
但两个安装器都还留着它的痕迹：

| 位置 | 残留行为 | 影响 |
|---|---|---|
| `scripts/install.ps1` 的 `-ConfigureHotkey` | 创建启动快捷方式，指向 `jcode setup-hotkey --listen-windows-hotkey` | 手动带该参数安装后热键不会工作 |
| `scripts/install.sh` 的热键探测 | 探测失败（子命令不存在）→ 仅打印一条提示 | 无功能影响；但该提示仅 macOS 分支出现，会推荐一个不存在的命令 |

两者都是**探测/开关式**写法，失败不报错、不影响安装与发布。

**为什么不阻塞发布**：`.github/scripts/verify_windows_install.ps1` 会设置
`JCODE_WINDOWS_SETUP_SKIP_PROCESS_LIFECYCLE=1`，install.ps1 据此跳过监听器启动。
真正被断言的只是快捷方式的 TargetPath 与参数文本，而这些仍与 install.ps1 一致，
所以必达平台安装验证仍会通过。`scripts/test_install_conversion.sh` 也不受影响：
它用的是自带 `setup-hotkey` 响应的**桩二进制**，不依赖真实的 jcode 拥有该子命令。

**处理选项**（需要产品决策，本 fork 暂未动）：

1. 保留现状，但不在安装提示里推荐热键；
2. 从 `install.ps1` / `install.sh` / `install_release.sh` 与其测试中移除 `-ConfigureHotkey`；
3. 重新实现 `setup-hotkey` 子命令。

另：仓库里还有其他针对已删 crate 的文档残留（同一批功能删除的遗留）。
它们不影响发布，需要时用以下命令自查并清理：

```bash
# 查找引用了本 fork 已删除 crate 的文档
grep -rn "crates/jcode-setup-hints\|jcode-desktop2\|jcode-notify-email" docs/ README.md
```

### PR 流程上的一个限制

`.github/workflows/require-issue.yml`（上游的贡献策略）要求每个 PR 关联一个**本仓库**的
issue，但本 fork 的 Issues 是关闭的，因此向本 fork 提 PR 时该检查会一直显示 ❌。
它不影响合并（除非另配了分支保护），但会让 PR 页面看起来是红的。

处理选项：

1. 接受现状，把 PR 当作代码评审载体，忽略该 ❌；
2. 删除 `require-issue.yml`（本 fork 不需要上游的 issue 关联策略）；
3. 在本 fork 开启 Issues，使该 workflow 可用。

## 8. 发布后验证

**推荐：直接跑核对脚本**，它把下面的清单全部自动化（含下载真实资产、校验哈希、运行产物）：

```bash
scripts/verify-release.sh              # 核对 latest
scripts/verify-release.sh v0.65.0      # 核对指定 tag
```

输出逐项 PASS/FAIL 并以退出码反映结果，可直接用于 CI 或发布后的自检。
注意：`--version` 与解包运行两项只能在 Windows 上执行（产物是 Windows 二进制），
其他平台会自动跳过并提示，仍完成元数据、哈希与发行说明核对。

手动核对清单：

- [ ] release 已从 draft 变为 public，且被标记为 latest
- [ ] 两个资产存在：`jcode-windows-x86_64.exe`、`jcode-windows-x86_64.tar.gz`（且**仅此两项**）
- [ ] `SHA256SUMS` 存在，覆盖且仅覆盖上面两个资产
- [ ] 发行说明正文是 changelog 渲染结果（不是提交清单回退），底部有 changelog 链接
- [ ] 发行说明末尾的 `Platform availability` 写明“仅发布 Windows x86_64”
- [ ] 下载 `jcode-windows-x86_64.exe` 并执行 `--version`，版本号与 tag 一致
- [ ] 下载 `jcode-windows-x86_64.tar.gz`，解包后同样验证 `--version`
- [ ] 对照 `SHA256SUMS` 校验下载文件（`Get-FileHash -Algorithm SHA256`）

## 9. 使用发布产物

本 fork 的产物不提供在线安装脚本，使用本地装包方式：

```powershell
# 下载 release 资产后，安装或更新本机 jcode
jcode update --local C:\dist\jcode-windows-x86_64.tar.gz
# 或直接用单文件 exe
jcode update --local C:\dist\jcode-windows-x86_64.exe
```

校验下载完整性：

```powershell
# 与 release 的 SHA256SUMS 对照
(Get-FileHash C:\dist\jcode-windows-x86_64.exe -Algorithm SHA256).Hash
```

本 fork 已移除 `jcode update` 的在线自更新（仅保留本地装包与 git 源码重建），
所以不存在“自动拉到 upstream 版本”的风险。

## 10. 异常处置

### 10.1 构建失败，release 卡在 draft

Windows x86_64 是唯一构件，所以“卡在 draft”几乎总是这一条链路出了问题。

1. 打开 Actions 里失败 job 的日志，确认是哪个 job。
2. 若是 `Build (x86_64-pc-windows-msvc)` 或 `Sign and publish Windows asset`，按 10.2 处理。
3. 若是 `Create release` 作业失败（例如权限不足导致 `gh release create` 报 403），
   先检查 §4 的 Workflow permissions 是否为 `Read and write`，修正后重跑该 job。
4. 若仅是偶发失败（网络、runner 配额），重跑失败 job：
   `Actions → Release → 对应 run → Re-run failed jobs`。
5. 重跑后 `release` 作业会重新校验并尝试发布，无需重新打 tag。

### 10.2 Windows x86_64 构建失败

Windows x86_64 是唯一产物，失败即发布不出去。

1. 在 Actions 中重跑 `Build (x86_64-pc-windows-msvc)` job。
2. 若持续失败，先在本地复现：`cargo build --locked --profile release-lto --target x86_64-pc-windows-msvc`。
3. 修复后：**不要移动已有 tag**。tag 已指向的提交不可变。正确处理是修一个 patch 版本
   （`v0.65.1`），并在发行说明里说明 `v0.65.0` 未发布。

### 10.3 tag 推错了 / 需要撤回一次发布

- tag 已推送且 release 已 public：**不能删除后重推同名 tag**（会破坏消费者与校验和的可追溯性）。
  正确做法是发一个新的 patch 版本。
- **tag 上什么都没有（无 release、无资产、无人下载）：可以安全重建同名 tag** 来重新触发事件。
  这是最轻的情形，但仍需维护者确认，因为它会删除并重建一个远端 ref。
  典型场景：fork 的 Actions 刚被启用，在此之前推送的 tag 事件已被静默丢弃（§4.2）。
- 只有确属事故（误推了完全无关的提交、tag 上什么都没有）时，才在维护者确认后删除远端 tag，
  并在本地同步删除：`git tag -d vX.Y.Z` + `git push origin :refs/tags/vX.Y.Z`。
  这是不可逆操作，必须经 `safe-git-write` 确认。
- 仅想把已发布的 release 撤下：在 GitHub 上把它改回 draft 或标记为 pre-release，
  **保留 tag**，避免版本号空洞。

### 10.4 发布后才发现必须回滚

发布资产是二进制，不能原地替换（消费者可能已下载并校验过）。

1. 保留问题版本的 release 与 tag，在其发行说明顶部追加醒目的已知问题说明。
2. 修复后发一个更高版本（patch）。
3. 若问题版本危害较大，把该 release 标记为 pre-release，让 `/releases/latest` 回退到上一个正常版本。

## 11. 与其他协作者并行

- 工作区可能有其他 agent 在改代码。发布前必须确认工作区只剩 release metadata 变更。
- release metadata 提交只包含 §5.1 的三类文件；发现混入代码文件时，拆开重新提交。
- 所有 git 写操作（含打 tag、推 tag）统一走 `safe-git-write` 流程确认后执行。
