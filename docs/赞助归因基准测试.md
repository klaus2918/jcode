# 赞助归因基准测试

`scripts/benchmark_attribution.py` 按赞助商评分：智能体代表用户执行的注册或安装是否可归因于 jcode。它补充 `scripts/benchmark_discovery.py`：那个套件测量 Discovery 是否触发；这个测量我们驱动的获取是否真的记在我们名下。

## 为什么存在

今天的目录归因大多是基于 cookie 的推荐链接（`?via=jcode-discovery`）。当人类在浏览器中点击清单 URL 时这有效。大多数 jcode 驱动的注册反而发生在智能体在 CLI 中遵循选择阶段 `setup` 说明时，那时从未设置过浏览器 cookie。每个赞助商的流程不同，因此每个赞助商都有自己的期望条目和 0-100 分。

## 检查与评分

每个赞助商按适用的检查评分（跳过项排除）：

| 检查 | 含义 |
|-------|---------|
| `catalog_entry_present` | 赞助商在活动（或保存的）目录中。 |
| `listing_url_marked` | 浏览 URL 携带推荐标记。 |
| `setup_preserves_marker` | 设置从不把用户送到供应商自己域上未标记的浏览器注册页。文档和 API 端点豁免。 |
| `cli_flow_attributable` | 如果设置以 CLI 为先，归因不能只依赖浏览器 cookie：要么设置通过带标记的 URL 路由账户创建，要么赞助商声明非 cookie 机制。 |
| `live_url_resolves` | （`--live-web`）带标记的 URL 有响应且重定向不丢失标记。 |

`cli_flow_attributable` 是**主要检查**。几乎每个 jcode 驱动的注册都发生在智能体 CLI 流程内，因此归因只在人类点击浏览器链接时才有效的赞助商实际上等于没有归因。因此：

- 它在分数中加权 `CRITICAL_CHECK_WEIGHT`（3 倍）；
- 每次运行都会打印每个赞助商显式的 CLI 归因裁决（`attributed` / `NOT-ATTRIBUTED` / `unknown`），外加一行 `N/M sponsors credit agent-driven CLI signups to jcode` 摘要；
- 报告 JSON 携带 `primary_check`、顶层 `cli_attribution` 映射，以及每个赞助商的 `cli_attribution` + `cli_attribution_detail`；
- 无论 `--min-score` 如何，`NOT-ATTRIBUTED` 裁决都使运行失败。

`skip` 显示为 `unknown` 而不是通过，因为缺少设置文本意味着 CLI 归因从未被验证。

分数 = 100 x 加权通过 / 加权适用。当任何赞助商分数低于 `--min-score`（默认 100）或任何 CLI 归因裁决不是 `attributed` 时，运行以非零退出。

## 赞助商期望

`scripts/attribution_benchmark_sponsors.json` 按赞助商声明归因 `mechanism` 和 `marker`。支持的机制：

- `referral-link`：基于 cookie 的联盟链接（对 CLI 流程最弱）；
- `signup-code`：注册期间智能体提供的代码；
- `utm-forwarding`：赞助商在注册时在服务端摄取查询参数；
- `api-partner-id`：嵌入 API/MCP 设置中的合作伙伴标识符。

单元测试强制要求 `scripts/discovery_benchmark_cases.json` 中有正用例的每个工具都有归因期望，因此新赞助商不声明归因如何工作就无法接入。

## 运行

```bash
# 离线逻辑测试
python scripts/test_benchmark_attribution.py

# 对发现服务实时运行，外加公共网页 URL 验证
python scripts/benchmark_attribution.py --live --live-web

# 单个赞助商
python scripts/benchmark_attribution.py --live --sponsor greptile

# 针对带完整条目（url/setup）的保存目录离线运行
python scripts/benchmark_attribution.py --catalog-file catalog.json
```

报告写入 `target/attribution-benchmark/latest.json`。对发现服务的实时请求携带 `x-jcode-discovery-benchmark: 1`，因此它们被排除在赞助商报告之外。

## 已知缺口（截至首次运行）

当前所有赞助商都得 80 分：它们的设置以 CLI 为先（MCP/API 密钥），但声明的机制是基于 cookie 的 `referral-link`，因此纯智能体驱动的注册没有归因。要弥合这一缺口，每个赞助商需要在设置说明中放入带标记的注册 URL，或声明非 cookie 机制（注册码或合作伙伴 ID），然后更新期望文件。
