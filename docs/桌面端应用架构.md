# Jcode 桌面端架构方向

> **历史说明：** 本文档描述已移除的旧版 `crates/jcode-desktop` 应用。当前桌面应用是 `crates/jcode-desktop2`。

状态：已提议
更新日期：2026-04-25

本文档记录 Jcode 桌面应用在这些约束下的初始方向：

- 无 Electron/Tauri/网页应用外壳
- 无通用 UI 框架
- 非常高性能
- 低空闲资源使用
- 非常定制的产品 UI
- 主要开发机器可能是 Linux
- 预计大多数早期用户在 macOS 上

目标是让桌面客户端成为一等 Jcode 面，而不分叉 Jcode 运行时或把应用变成重型 IDE 克隆。

## 执行摘要

把 Jcode 桌面端构建为带自定义 GPU 渲染 UI 的小型 Rust 桌面客户端。应用应连接到拥有会话、工具、智能体执行、持久化和权限的本地 Jcode 服务器/守护进程。

前端应优化为渲染/输入面：

- Linux 应是一等开发平台。
- macOS 应是一等产品/分发平台。
- UI 不应依赖仅 Linux 的桌面概念。
- UI 不应是网页视图。
- UI 不应直接嵌入智能体运行时。
- 渲染应从一开始就按需、虚拟化且可测量。

推荐的初始技术栈：

| 领域 | 决定 |
|---|---|
| 前端语言 | Rust |
| 后端/运行时 | 现有 Rust Jcode 服务器/会话运行时 |
| 进程模型 | 桌面前端 + 本地 Jcode 守护进程/服务器 |
| 窗口/输入层 | 薄平台层，初始可能用 `winit` |
| 渲染 | 带自定义 2D 渲染器的 `wgpu` |
| UI 架构 | 带脏跟踪的保留 UI 树 |
| 布局 | 小型自定义布局系统，非 CSS/DOM |
| 文本 | 专用文本布局/光栅缓存，可能用 `cosmic-text`/`swash` 或稍后平台支持文本 |
| 协议 | 带版本的类型化本地事件协议 |
| 持久化 | 服务器拥有的会话/事件持久化 |
| 产品身份 | 智能体操作控制台 / 任务控制中心 |

## 产品立场

Jcode 桌面端不应从完整 IDE 开始，也不应看起来像传统聊天机器人。

差异化产品是面向本地开发的**键盘驱动、类 Niri 的智能体工作区超级应用**。一等对象不是聊天窗口，而是包含许多可导航表面的工作区：

- 智能体会话
- 活动/任务视图
- 差异和变更文件
- 文件/差异/工具表面
- 可选未来表面
- 设置/调试/工具表面

应用应帮助用户：

- 监督自主编码工作
- 检查工具活动
- 管理后台任务
- 审阅变更文件
- 响应权限提示
- 恢复和协调会话
- 空间导航许多相关表面

桌面客户端应补充 TUI/CLI，而不是取代它。

## 平台策略

### 开发宿主：Linux

Linux 应支持最快的内环：

- 本地启动桌面客户端
- 运行渲染器压力测试
- 运行协议集成测试
- 基准测试内存/帧/布局/文本性能
- 无需 Mac 参与即可调试 UI 引擎

Linux 构建应是真实的，不是假模拟器。它应通过相同的 UI 引擎渲染，并练习与 macOS 相同的协议/视图模型路径。

### 产品目标：macOS 优先

预计大多数早期用户在 macOS 上，因此即使日常开发在 Linux 进行，macOS 打磨也应是产品要求。

不应推迟太久的 Mac 专属工作：

- 原生 `.app` 包
- 应用图标和菜单栏集成
- Command 键快捷键
- 系统浅色/深色外观
- Retina 渲染正确性
- 触控板滚动质量
- 原生剪贴板行为
- 文件/打开方式集成
- 代码签名和公证路径
- 在 Mission Control、Spaces 和全屏窗口下的良好行为

### 避免 Linux 形态的产品假设

由于开发者可能使用 Linux，架构应显式避免烘焙只对 Linux 窗口管理器有效的假设。

不要把这些做成硬依赖：

- Niri 式外部空间窗口管理
- X11 专属 API
- 仅 Wayland 行为
- 终端优先的会话工作流
- Linux 通知语义
- 在 macOS 上不可用或不友好的全局快捷键

现有的 Linux/Niri 工作流应保持优秀，但桌面产品质量应主要对照 macOS 预期评判。

## 进程架构

使用分离进程架构：

```text
Jcode 桌面端前端
  - 窗口/输入
  - 自定义渲染
  - 本地视图模型
  - 瞬态 UI 状态
  - 表面本地状态
  - 协议客户端

Jcode 服务器/守护进程
  - 会话
  - 智能体运行时
  - 工具运行时
  - 后台任务
  - 持久化
  - 权限
  - 模型/提供商配置
```

服务器保持以下内容的事实来源：

- 规范会话历史
- 流式事件
- 工具执行
- 文件编辑
- 后台任务
- 权限状态
- 持久化配置

桌面前端只拥有表面本地状态：

- 选中的会话/表面
- 草稿输入
- 光标和文本选择
- 滚动偏移
- 窗格大小
- 聚焦面板
- 本地命令面板状态
- 渲染缓存

这与服务器拥有的会话随时间可被不同客户端或表面显示的多会话模型对齐。

## 本地协议方向

桌面应用应消费带版本、类型化的事件流，而不是周期性地获取完整会话快照。

早期协议属性：

- 本地优先传输
- 显式协议版本
- 能力协商
- 仅追加的会话事件
- 助手/工具输出的流式增量
- 按事件游标可恢复的订阅
- 高音量工具输出的紧凑事件
- 服务器拥有的权限请求

可能的传输：

1. 现有 Jcode 服务器通道（如果与桌面需求兼容）。
2. Linux/macOS 上的 Unix 域套接字和 Windows 上的命名管道。
3. 早期原型和测试工具的 stdio JSON 协议。

除非有强理由，避免把 localhost HTTP 作为默认。它比用户拥有的套接字/管道制造更大的本地安全面。

示例事件族：

```text
session.created
session.updated
surface.attached
message.created
message.delta
message.completed
tool.started
tool.output.delta
tool.completed
task.started
task.progress
task.completed
workspace.changed
git.changed
permission.requested
permission.resolved
error
```

## 渲染架构

使用自定义渲染器，而不是原生组件层级或网页视图。

推荐层：

```text
平台窗口/输入
  -> 输入规范化器
  -> 应用状态/视图模型
  -> 保留 UI 树
  -> 布局
  -> 文本布局/缓存
  -> 显示列表
  -> GPU 渲染器
```

核心规则：

- 空闲时无连续渲染循环
- 只在输入、数据事件、动画或显式失效时渲染
- 虚拟化每个无界列表
- 分离布局成本与绘制成本
- 按内容/字体/宽度缓存成形文本
- 用稳定 ID 做脏跟踪
- 让调试/性能计数器在应用内可见

渲染器初始应支持：

- 矩形
- 圆角矩形
- 边框
- 实心填充
- 裁剪
- 滚动容器
- 文本运行
- 等宽块
- 简单图标或向量式原语
- 稍后图像支持

推迟：

- 模糊效果
- 复杂阴影
- 动画框架
- SVG 重型渲染
- 完整 Markdown 渲染器
- 完整终端模拟器
- 嵌入式代码编辑器

## UI 架构

使用带即时式构建器人体工学的保留 UI 树。

理由：

- 会话记录长生命周期且增量流式
- 工具输出可能很大
- 窗格需要稳定焦点/选择状态
- 脏跟踪对资源使用很重要
- 可访问性最终需要稳定语义节点
- 多会话表面需要稳定身份

模型不应模仿 DOM/CSS 栈。小型产品专属布局系统就够：

- 行
- 列
- 堆栈
- 拆分窗格
- 固定大小
- 弹性填充
- 滚动容器
- 虚拟列表
- 覆盖层/模态
- 固有文本测量

## 文本策略

文本是这个项目最难的部分之一，应作为核心系统对待，而不是细节。

桌面客户端需要：

- Unicode 成形
- 字体回退
- 等宽代码/工具输出
- 换行
- 增量追加布局
- 选择/复制
- 输入光标行为
- 命令面板文本输入
- 类 Markdown 会话记录样式
- 最终类 ANSI 工具输出样式

初始推荐：

- 依赖审阅可接受时使用 `cosmic-text`/`swash` 等 Rust 文本栈
- 维护 GPU 字形图集
- 按稳定块 ID 和可用宽度缓存成形行/运行
- 专化流式追加路径，使新输出不重新布局整个会话记录

Mac 专属文本质量应尽早评估。如果 Rust 文本渲染在 macOS 上不够好，考虑 macOS 用平台支持文本，同时保留相同的高层文本布局 API。

## 性能与资源预算

初始预算应在 Linux 开发机器和有代表性的 macOS 硬件上测量。

| 指标 | MVP 目标 | 长期目标 |
|---|---:|---:|
| 冷启动到可见窗口 | < 500 毫秒 | < 150 毫秒 |
| 前端空闲 CPU | 约 0% | 约 0% |
| 前端空闲 RSS | < 100 MiB | < 50 MiB |
| 输入到绘制延迟 | < 32 毫秒 | < 16 毫秒 |
| 滚动 | 60 fps | 可 120 fps |
| 假会话记录压力用例 | 10 万块可用 | 10 万块流畅 |
| 追加时完整会话记录重新布局 | 禁止 | 禁止 |
| 无界保留可见节点 | 禁止 | 禁止 |
| 空闲时渲染器帧 | 禁止 | 禁止 |

必需的早期仪器：

- 帧时间
- 布局时间
- 文本成形时间
- 显示列表构建时间
- GPU 提交时间
- 可见节点数
- 总保留节点数
- 字形图集大小
- 文本缓存大小
- 协议事件积压
- 守护进程往返延迟
- 前端 RSS（如可用）

在真实 Jcode 集成被认为完成之前，原型中应存在调试 HUD。

示例 HUD：

```text
frame 1.8ms | layout 0.3ms | text 0.6ms | gpu 0.4ms
nodes 812 | visible 47 | glyph atlas 12.4 MiB | events 0 | daemon 2ms
```

## MVP 范围

第一个 UI 里程碑应在证明每个产品工作流之前证明引擎。

### 里程碑 1：带假数据的自定义外壳

成功标准：

- 从 Linux 启动原生桌面窗口
- 通过自定义 GPU 流水线渲染
- 显示会话侧边栏、会话记录、编辑器框和活动面板
- 处理鼠标、键盘、焦点和滚动
- 渲染假流式会话记录数据
- 虚拟化 10 万块会话记录
- 近零 CPU 空闲
- 暴露性能/调试 HUD
- 在实用处有截图或金态测试

### 里程碑 2：协议连接

成功标准：

- 连接到本地 Jcode 服务器/守护进程
- 列出会话
- 挂接到会话/表面
- 订阅事件流
- 发送用户提示词
- 将助手/工具事件流式送入会话记录
- 可以停止/取消活动运行
- 在守护进程重启或断开后优雅恢复到足以供开发使用

### 里程碑 3：有用的智能体控制台

成功标准：

- 后台任务/工具调用的活动中心
- 权限请求覆盖层
- 工作区/git 状态面板
- 变更文件列表
- 打开外部编辑器/差异操作
- 会话搜索/过滤
- macOS 应用包原型

## Crate 布局提议

不要把整个桌面应用放在根 crate 中。

建议结构：

```text
crates/
  jcode-desktop-protocol/   # 共享协议/事件类型（如果服务器类型尚未覆盖）
  jcode-desktop-ui/         # UI 树、布局、文本/缓存抽象、渲染器无关部分
  jcode-desktop-renderer/   # wgpu 渲染器和 GPU 资源
  jcode-desktop/            # 应用外壳、平台窗口、协议客户端、产品 UI
```

如果编译时间成为问题，保持协议/UI crate 轻量，并把 GPU/窗口依赖门控在最终应用 crate 后面。

## 依赖策略

"无框架"不一定意味着"无库"。它应意味着无重量级应用框架和无网页外壳产品架构。

可能可接受的依赖：

- 渲染抽象的 `wgpu`
- 引导用的非常薄的窗口/输入层，如 `winit`
- 文本成形/光栅化的 `cosmic-text`/`swash` 或等价物
- 与 Jcode 已一致的小型序列化/协议 crate

避免：

- Electron
- Tauri
- Qt
- Flutter
- 作为应用框架的 GTK
- WebView UI 外壳
- React/Vue/Svelte 式 UI 栈
- 基于 CSS/DOM 的架构

如果 `winit` 对 macOS 打磨有限制，平台层可以增长直接 AppKit 支持，同时保留渲染器和 UI 模型。

## macOS 验证检查清单

由于 macOS 是主要用户目标，即使开发在 Linux 进行也要尽早验证这些：

- Retina 缩放因子正确性
- 触控板惯性滚动
- 与原生应用相比的文本清晰度
- 键盘快捷键在适当处用 Command 而非 Control
- 系统深色/浅色模式跟随用户偏好
- 窗口调整大小和全屏行为感觉原生
- 应用菜单和关闭/最小化/退出语义正确
- 剪贴板往返对代码和会话记录足够丰富
- 本地套接字权限安全
- 应用包可以可靠启动/找到守护进程

## 开放决定

这些应在实现越过假数据原型之前解决：

1. 初始用 `winit` 还是从一开始写直接平台外壳？
2. 用 `wgpu` 还是直接 Metal 优先渲染？
3. 用 `cosmic-text`/`swash` 还是平台文本 API？
4. 复用现有 Jcode 服务器协议还是引入桌面专属事件协议 crate？
5. 第一个桌面二进制应支持多表面模式还是只有一个活动表面？
6. 支持的最低 macOS 版本是多少？
7. 第一个分发路径：本地 `.app`、Homebrew cask，还是签名/公证的 DMG？

## 推荐的立即下一步

创建在 Linux 上运行但测量最终 macOS 产品所需确切性能特征的假数据桌面原型。

原型不应等待完美的守护进程 API。它应先验证昂贵的 UI 系统：

- 窗口创建
- 渲染器启动
- 保留树
- 布局
- 文本缓存
- 虚拟化会话记录
- 按需重绘
- 调试 HUD

只有在那之后才连接真实 Jcode 事件流。
