# 模型接入

本仓库的模型接入是**纯配置驱动**：没有交互式登录，没有内置第三方厂商预设，
所有端点通过配置声明，密钥集中在统一文件里。

```text
配置层      config.toml 的 [providers.<name>] / [[providers]]（含按模型能力字段）
   │
能力层      jcode-provider-core::capability（ModelCapability + 内嵌注册表 + 合并管线）
   │        优先级：显式配置 > 内嵌注册表 > 启发式 > 保守默认
解析层      jcode-base 的 provider/models 与 catalog_routes（路由能力投影）
   │
适配层      jcode-provider-*-runtime（Provider trait + 可选能力接口）
   │
运行时      jcode-app-core agent（工具门控、视觉门控、effort、压缩、错误恢复）
```

## 一、添加一个 provider

三条命令即可（密钥永不写进 `config.toml`）：

```bash
# 托管端点，密钥从 stdin 安全读入并写入统一 .env
printf '%s' "$MY_API_KEY" | jcode provider add my-api \
  --base-url https://llm.example.com/v1 --model my-model-id --api-key-stdin --set-default

# 引用已有环境变量，不落盘
jcode provider add openrouter --base-url https://openrouter.ai/api/v1 \
  --model deepseek/deepseek-chat --api-key-env OPENROUTER_API_KEY

# 本地无鉴权端点
jcode provider add ollama-local --base-url http://localhost:11434/v1 \
  --model llama3.2 --no-api-key
```

验证：

```bash
jcode provider list                                  # 已配置的 provider
jcode provider current                               # 当前请求与最终解析结果
jcode --provider-profile my-api run 'hello'
```

常用参数：`--api-key-env`、`--api-key-stdin`、`--api-key`、`--no-api-key`、`--auth`
（`bearer` / `api-key` / `none`）、`--auth-header`、`--api`（`openai-compatible` / `anthropic`）、
`--context-window`、`--model-catalog`、`--provider-routing`、`--proxy`、`--env-file`、
`--overwrite`、`--set-default`、`--json`。

`http://` 仅允许 localhost 与私有 LAN 地址，公网明文 HTTP 被拒绝。

## 二、配置写法

两种风格等价，jcode 保存时**保持你写的风格**（手写的 `[[providers]]` 数组不会被改写成表）。

经典表风格：

```toml
[provider]
default_provider = "my-api"
default_model = "my-model-id"

[providers.my-api]
type = "openai-compatible"       # 或 "open-router"
base_url = "https://llm.example.com/v1"
api_key_env = "JCODE_PROVIDER_MY_API_API_KEY"
env_file = "provider-my-api.env" # 可选，默认写到统一 .env
default_model = "my-model-id"
context_window = 128000

[[providers.my-api.models]]
id = "my-model-id"
```

resonix 风格数组：

```toml
[[providers]]
name = "my-api"
type = "openai-compatible"
kind = "openai"                  # 或 "anthropic"
base_url = "https://llm.example.com/v1"
model = "my-model-id"
models = ["my-model-id"]
api_key_env = "JCODE_PROVIDER_MY_API_API_KEY"
context_window = 128000
```

> **注意**：同一文件里不要混用 `[[providers]]` 数组条目与 `[providers.<name>]` 表格，
> 混用会让整个 `config.toml` 解析失败。

## 三、本地运行时

Ollama 与 LM Studio 都提供 OpenAI 兼容的 `/v1/models` 与 `/v1/chat/completions`；
jcode 使用流式对话、函数/工具调用与 OpenAI 风格图像内容。

```bash
ollama pull llama3.2
jcode provider add ollama-local --base-url http://localhost:11434/v1 --model llama3.2 --no-api-key

jcode provider add lmstudio --base-url http://localhost:1234/v1 --model '<model-id>' --no-api-key
jcode --provider lmstudio run 'hello'
```

自建 vLLM（无鉴权）：

```bash
jcode provider add local-vllm --base-url http://localhost:8000/v1 \
  --model Qwen/Qwen3-Coder-30B-A3B-Instruct --no-api-key --set-default
```

## 四、CC Switch 本地网关

[CC Switch](https://github.com/farion1231/cc-switch) 统一管理多路 API，并在本地起代理
（默认 `127.0.0.1:15721`，端口可在面板修改），按应用类型路由到当前启用的 provider，
转发时注入真实 key。jcode 以 **Anthropic Messages 格式**接入，等价于一个「Claude 通道」客户端。

```toml
[provider]
default_provider = "cc-switch"
# default_model 留空 → 自动跟随面板当前启用的 provider

[[providers]]
name = "cc-switch"
kind = "anthropic"
base_url = "http://127.0.0.1:15721"   # 以面板显示的"服务地址"为准
auth = "none"                         # 真实 key 由代理注入
# default / models 可留空（自动发现并跟随），也可填模型名固定
```

| 项 | 结论 | 说明 |
|---|---|---|
| 模型 | **可留空，自动跟随；也可固定** | 留空时 jcode 从代理 `/v1/models` 拉目录，自动选当前启用 provider 的第一个模型；面板切换 provider 后 jcode 刷新跟随（请求遇模型不可用也会自动回退）。用 `default_model` 或 `--model` 显式指定后不会被自动覆盖。 |
| key | **不需要** | 真实 key 在 cc-switch 侧，jcode 用 `auth = "none"` 即可 |

注意：代理必须保持运行；provider 切换在面板操作，jcode 侧不改配置；
故障转移、请求日志、用量统计都在面板查看。DeepSeek 风格网关若返回无签名 thinking，
需在该 profile 上设 `replay_reasoning_content = true`（官方 Anthropic API 相反，保持关闭）。

## 五、模型能力（config 声明）

`[[providers.<name>.models]]` 下所有字段可选且带别名（`context_limit`、`supports_vision`、
`efforts`、`reasoning-protocol` 等），旧配置原样解析：

```toml
[[providers.my-gateway.models]]
id                    = "custom-vlm"
context_window        = 128000
input                 = ["text", "image"]
vision                = true            # 显式视觉能力
tools                 = false           # 永不发送工具定义
reasoning_protocol    = "openai"        # auto|deepseek|openai|thinking_type|anthropic|none
supported_efforts     = ["low", "high"] # /effort 阶梯
default_effort        = "high"
output_window         = 16384
temperature_supported = false           # 固定采样后端
fixed_sampling        = true
output_limit_field    = "max_completion_tokens"
```

解析优先级（`ResolvedModelCapability` 带 `CapabilityTrace`，记录每个字段的获胜来源）：

1. 显式配置：`NamedProviderModelConfig` 字段 / 输入模态；
2. 内嵌注册表：`EMBEDDED_REGISTRY` 精确匹配优先于前缀，可按 provider 限定；
3. 启发式：开放权重上下文族、推理阶梯、视觉命名约定；
4. 保守默认：纯文本、工具可用、无推理控制。

门控行为：

- **工具门控**：模型解析为 `tools == false` 时，该回合工具集清空；未知模型保留工具。
- **视觉门控**：`capabilities.modalities` 含 `image` 的模型才走图像处理路径。
- **采样**：`temperature_supported` / `fixed_sampling` / `output_limit_field` 泛化固定采样后端。

`jcode model list --json` 输出含能力视图的路由；`--verbose` 打印人类可读能力块。
凭据、端点、代理信息**永不**进入能力视图，因此该视图可安全发给远程客户端。

## 六、凭据来源（排查"有没有 key"）

Anthropic 与 OpenAI 各支持**两条独立凭据路径**，作为不同 provider 呈现：

| provider id | 认证类型 | 凭据位置 |
|---|---|---|
| `claude` | OAuth（订阅） | `~/.jcode/auth.json` 的 `anthropic_accounts[].access`（`sk-ant-oat...`） |
| `anthropic-api` | API 密钥 | `ANTHROPIC_API_KEY` 环境变量 **或** `~/.jcode/.env` |
| `openai` | OAuth | `~/.jcode/openai-auth.json` |
| `openai-api` | API 密钥 | `OPENAI_API_KEY` 环境变量 **或** `~/.jcode/.env` |

要点：

- **OAuth 令牌不是 API 密钥**：`sk-ant-oat01-...`（OAuth）vs `sk-ant-api03-...`（直连密钥），
  grep 一种会漏掉另一种。
- **密钥通常在统一文件里**：`<jcode home>/.env`（默认 `~/.jcode/.env`，由 `jcode-provider-env`
  的 `unified_env_file_path()` 决定）。`printenv ANTHROPIC_API_KEY` 为空**不代表**没有密钥。
  旧式分散文件（`~/.config/jcode/*.env`）仍可读，启动时自动迁移。
- `auth.json` 只存 OAuth 账户，绝不存 API 密钥。
- 解析顺序：进程环境变量 → 统一 `.env` → 配置指定 `env_file` → 启动时注册的 OAuth 回退解析器。

检查（别靠猜）：

```bash
jcode auth status --json
```

编程上的单一事实来源是 `crates/jcode-base/src/auth/mod.rs` 的
`AuthStatus::assessment_for_provider(descriptor)`（返回 `ProviderAuthAssessment`）。

### 从其他工具导入凭据

首次运行会检测其他编码智能体留下的登录，**同意门控**读取（列出来源，逐个批准后才读；
外部文件就地读取，不复制进 jcode 存储）。

| 工具 | 路径 | 形态 |
|---|---|---|
| OpenCode | `~/.local/share/opencode/auth.json` | 扁平 `{ provider: { type: "oauth" \| "api", ... } }` |
| pi | `~/.pi/agent/auth.json` | 扁平（key 可为 `$ENV` 引用） |
| OpenClaw | `~/.openclaw/**/auth*.json`、`credentials/oauth.json` | 旧版扁平形态或 `{ profiles: {...} }` |
| Hermes | `~/.hermes/auth.json` | 嵌套 `credential_pool` + `providers` |
| Claude Code / Codex | 各自的凭据文件 | 见 `crates/jcode-base/src/auth/claude.rs`、`codex.rs` |

以 `!`（shell 命令）开头的值**绝不执行**，直接跳过。
Gemini / GitHub Copilot / Cursor 的专用导入器已随功能减法移除，这些厂商请用配置接入。

### "已过期"为何有误导性

`~/.jcode/auth-validation.json` 是**历史记录**，不是当前状态：已自动刷新的令牌仍可能显示
几天前的失败条目。`crates/jcode-base/src/auth/validation.rs` 会把早于 7 天
（`doctor::VALIDATION_STALE_AFTER_MS`）的记录标记为 `stale`——当作"未知，重新检查"。

```bash
jcode auth doctor <provider> --validate
```

## 七、诊断

| 命令 | 回答什么 | 需要 key |
|---|---|---|
| `jcode auth doctor [PROVIDER]` | 凭据链路：有没有、从哪来、是否过期、能否刷新、上次校验 | 否（`--validate` 才联网） |
| `jcode provider-test-coverage [PROVIDER] [MODEL]` | 每个（provider，模型）对在 12 阶段流水线卡在哪一步 | 否（只读台账） |

`jcode auth doctor` 逐 provider 输出 `auth_kind`、`status`、`method`、`health`、
`credential_source(_detail)`、`expiry_confidence`、`refresh`、`validation_method`、
`last_refresh`、`validation(_run)`、`needs_attention`、`diagnostics`。
`needs_attention` 判据（`crates/jcode-base/src/auth/doctor.rs`）：凭据不可用、上次刷新失败、
校验失败、或校验记录超 7 天未更新。

`jcode provider-test-coverage` 把台账渲染成流水线，每行 `READY`（12/12）或 `N/12` 加第一个阻塞点，
末列是新鲜度与来源（`user (release build)` / `developer (dev build)`，由构建标志推导）。
12 个严格检查点：`auth_credential_loaded`、`model_catalog_live_endpoint`、
`catalog_hot_reload_current_session`、`picker_live_models`、`picker_fallback_labeling`、
`model_switch_route`、`non_streaming_chat_completion`、`streaming_chat_completion`、
`tool_call_parse`、`tool_execution_loop`、`tool_result_followup`、`real_jcode_tool_smoke`。

### 典型排查

1. **选择器显示错误模型**：`jcode provider current` 看解析结果 → `jcode model list --verbose`
   看模型来源 → 检查配置里的 `[providers.<name>]` 与 `model` 字段。
2. **连不上 / 认证失败**：`jcode auth doctor <provider>`，看 `credential_source` 与
   `needs_attention`；必要时用 `--api-key-stdin` 重新写入统一 `.env`。
3. **能连但行为糟糕**：`jcode provider-test-coverage <provider> <model>` 看卡在哪个阶段；
   若卡在流式或工具调用，多半是模型/网关能力问题，换模型验证。

## 九、OpenAI 兼容 profile 运行时的设计要点

同一套 HTTP 传输被两类东西复用：标准 OpenRouter（带 provider 固定、端点元数据、
`openrouter` 目录命名空间）与直连的 OpenAI 兼容 provider（NVIDIA NIM、Groq、Cerebras、
Chutes、自建端点等，各有自己的凭据、API base、目录与模型 id）。

早期实现把两者塞进同一个 `openrouter` 运行时槽，导致切换 provider 会替换活动目录视图
（例如从 `openrouter/owl-alpha` 切到 NVIDIA NIM 后，`/model` 里再看不到标准 OpenRouter，
甚至把 OpenRouter 的模型错标成 NVIDIA）。当前设计把**传输、profile 身份、路由聚合**分开：

- 每个配置化的 OpenAI 兼容 profile 是一个独立运行时（`profile_id` / `display_name` /
  `cache_namespace` / `default_model` / 是否启用 provider-routing），存放在
  以 profile id 为键的 map 中；
- 切换活动 profile 只更新"当前选择"，**不移除也不重贴**其他 profile 的路由；
- `/model` 聚合所有已配置 profile 的路由，且静态与在线目录按 `cache_namespace` 限定作用域，
  避免陈旧缓存把模型挂到错误的 provider 名下；
- 面向用户的写法保持稳定：`openrouter:<model>`、`nvidia-nim:<model>`、
  `openai-compatible:<model>` 与 `--provider <name>` 语义不变，`ModelRoute` 的线上序列化不变。

回归重点：切换 profile 后未选中的 profile 仍可选；带斜杠的模型 id 不会被自动当成标准 OpenRouter；
一个 profile 的目录缓存不会污染另一个。

## 十、附录：Claude 能力实测（快照）

2026-07-24 用真实 API key 对 `claude-opus-5` 探测的结果（在线目录的 `max_input_tokens`
会过度宣传，所以以实测为准）：

| 能力 | 结果 |
|---|---|
| 最大输出 | `max_tokens: 128000` 通过；`128001` 返回 400 |
| 上下文窗口 | 目录 `max_input_tokens` = 1,000,000（`AnthropicContextMode::Native1M`） |
| 自适应思考 | `thinking: {type: adaptive}` 通过 |
| 手动思考 | `thinking: {type: enabled, budget_tokens}` 返回 400（该模型不支持） |
| 努力等级 | `output_config.effort` 的 `low/medium/high/xhigh/max` 全部通过 |
| 定价 | `$5 / MTok` 输入，`$25 / MTok` 输出 |

为什么输出上限重要：jcode 曾对所有 Claude 模型发固定 `max_tokens = 32768`，
而 Opus 5 允许 128K 且常开自适应思考，思考加工具调用常超 32K，导致回合在工具调用中途被
截断、智能体提前结束。现已按模型推导预算（Opus 4.6–4.8 / Sonnet 5/4.6 / Fable 5 为 128K，
Haiku 4.5 为 64K，未知与旧 id 保守用 32K）。
