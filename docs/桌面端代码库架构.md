# 从现有 TUI 出发的桌面端代码库架构

> 历史文档：本文描述已移除的旧版 `crates/jcode-desktop` 应用。当前桌面应用是 `crates/jcode-desktop2`。

状态：提案
更新：2026-04-25

本文把当前 Jcode TUI 架构转化为未来自定义桌面应用的具体代码库计划。

桌面应用预期具有与 TUI 大致相同的产品能力，但不应该是 TUI 实现的直接移植。TUI 面向终端/单元格，积累了大量的终端特定渲染、输入、布局、滚动和缓存逻辑。桌面应用应复用运行时/协议/会话概念和部分表现模型，但应有独立的自定义 UI 和渲染架构。

## 当前 TUI 观察

当前 TUI 功能丰富，应被视为产品参考实现。

大致当前规模：

```text
src/tui/*.rs 及子模块：144 个 Rust 文件，约 11.5 万行
src/tui/app.rs：            约 800 行
src/tui/ui.rs：             约 3.8 千行
src/tui/ui_prepare.rs：     约 1.6 千行
src/tui/ui_viewport.rs：    约 750 行
src/tui/ui_messages.rs：    约 2.4 千行
src/tui/markdown.rs：       约 1.4 千行
src/protocol.rs：           约 1.4 千行
```

重要的现有部分：

- `src/protocol.rs`
  - Unix socket 上的换行分隔 JSON
  - `Request`
  - `ServerEvent`
  - 会话订阅/恢复/历史/消息/取消/工具/状态事件
- `src/server/`
  - 多客户端服务器/会话运行时
  - 重连支持
  - 会话生命周期
  - 客户端事件
  - 后台任务/集群/comm 状态
- `src/tui/app.rs` 和 `src/tui/app/*`
  - TUI 应用状态根
  - 输入处理
  - 远程连接处理
  - 命令解析
  - 服务器事件 reducer
  - 本地模式支持
  - 复制/选择/导航/会话选择器/调试覆盖层
- `src/tui/ui.rs` 和 `src/tui/ui_*`
  - ratatui 渲染器
  - 终端/单元格布局
  - 视口和滚动行为
  - 侧面板
  - 覆盖层
  - 视觉调试捕获
- `src/tui/ui_prepare.rs`
  - 帧准备
  - 换行行映射
  - 完整准备缓存
  - 正文/流式/批量准备
- `src/tui/ui_messages.rs`
  - 消息到终端行的渲染
  - 工具/系统/后台/集群使用渲染
  - 行缓存
- `src/tui/markdown.rs`
  - 终端 markdown 渲染
  - 语法高亮缓存
  - mermaid 集成钩子

## 关键教训

TUI 已经拥有正确的**功能集**和许多正确的**领域概念**，但还没有为自定义桌面 UI 提供正确的边界。

桌面不应把 `ratatui::Line`、终端宽度换行、全局渲染器缓存或终端输入假设导入核心应用状态。

桌面应改用这种拆分：

```text
Jcode 服务器/运行时/协议
  -> client-core reducer 和视图模型
    -> 桌面产品视图
      -> 自定义 UI 树/布局
        -> 显示列表
          -> wgpu 渲染器
```

## 复用与不复用

### 直接或几乎直接复用

- 服务器进程架构
- 会话所有权模型
- 重连语义
- 请求/事件协议作为起点
- 服务器侧会话历史和工具执行
- 模型/provider/会话元数据
- 命令概念
- 后台任务概念
- 集群/目标/活动概念
- 权限概念
- 调试/诊断理念

### 抽取掉终端类型后复用

- 来自 `src/tui/app/remote/server_events.rs` 的服务器事件归约逻辑
- 消息显示块构建
- 工具调用摘要
- 活动/状态模型
- markdown 块解析决策
- 复制目标语义
- 会话选择器数据模型
- 登录/账户选择器数据模型
- 命令注册表和命令元数据
- info 部件数据模型
- 记忆/调试摘要模型

### 不直接复用

- 作为跨表面表示的 `ratatui::Line`
- 终端单元格布局
- 作为桌面主要模型的终端特定滚动偏移
- `LAST_MAX_SCROLL` 式全局渲染器状态
- 终端键协议代码
- 终端特定 markdown 换行
- 终端特定图像/mermaid 显示代码
- 作为桌面边界的巨型 `TuiState` trait
- 混合运行时、传输、UI 和渲染关注点的单体 `App` 状态

## 主要架构风险

如果桌面开发直接复制 TUI 结构，结果很可能是：

- 另一个非常庞大的 `DesktopApp` 状态对象
- 渲染缓存与领域状态混合
- 平台输入处理与会话 reducer 混合
- 重复的命令逻辑
- 重复的服务器事件处理
- 难以测试的 UI 行为
- TUI 和桌面之间共享行为困难

桌面应用应通过在实现太多功能之前创建真正的 client-core 边界来避免重蹈覆辙。

## 提议的 crate/模块架构

确切的 crate 名称可以改变，但依赖方向不应改变。

```text
crates/
  jcode-protocol/             # 最终从 src/protocol.rs 抽取
  jcode-client-core/          # 与表面无关的客户端状态/reducer/视图模型
  jcode-desktop-ui/           # 自定义 UI 树、布局、输入路由、风格令牌
  jcode-desktop-renderer/     # wgpu 渲染器、显示列表、字形/图像图集
  jcode-desktop-platform/     # winit/AppKit/Linux 外壳抽象、菜单、剪贴板
  jcode-desktop/              # 产品应用：窗口、面板、协议客户端、组合
```

初始实现可以把其中一些作为 `crates/jcode-desktop` 内的模块以减少早期摩擦，但边界应按独立 crate 设计。

## 依赖方向

允许的依赖流：

```text
jcode-desktop
  -> jcode-desktop-platform
  -> jcode-desktop-renderer
  -> jcode-desktop-ui
  -> jcode-client-core
  -> jcode-protocol
```

`jcode-client-core` 不得依赖：

- `wgpu`
- `winit`
- AppKit
- Wayland/X11
- `ratatui`
- `crossterm`
- 终端 markdown 渲染

`jcode-desktop-ui` 不应依赖 Jcode 服务器运行时。它可以依赖 client-core 视图模型和通用 UI 类型。

`jcode-desktop-renderer` 不应知道 Jcode 会话是什么。它渲染显示列表、文本 run、图像、裁剪和图元。

## `jcode-protocol`

现有 `src/protocol.rs` 已经是自然起点。

长期把它抽取为 crate，使 TUI 和桌面消费相同的线类型：

```text
crates/jcode-protocol/src/lib.rs
  Request
  ServerEvent
  HistoryMessage
  SessionActivitySnapshot
  FeatureToggle
  SwarmMemberStatus
  protocol version/capability handshake types
```

短期内桌面可以导入根 crate 类型，但协议应被视为共享 API。

桌面���定的协议需求可能包括：

- 针对侧边栏优化的带元数据会话列表
- 可恢复订阅的事件游标
- 更丰富的活动快照
- 工作区/git 摘要快照
- 权限请求快照
- 变更文件摘要
- 表面/窗口附着元数据

除非现有协议成为阻塞点，否则避免创建第二个无关的桌面协议。

## `jcode-client-core`

这是最重要的共享层。

它应拥有独立于终端和桌面渲染的行为和状态。

建议模块：

```text
jcode-client-core/
  src/
    lib.rs
    app_model.rs
    actions.rs
    reducer.rs
    protocol_reducer.rs
    command_registry.rs
    session_list.rs
    transcript.rs
    transcript_blocks.rs
    composer.rs
    activity.rs
    permissions.rs
    workspace.rs
    git.rs
    settings.rs
    overlays.rs
    selection.rs
    status.rs
    diagnostics.rs
    view_model.rs
```

### 核心状态切片

```rust
struct ClientCore {
    sessions: SessionListState,
    active_surface: Option<SurfaceId>,
    surfaces: SurfaceMap,
    connection: ConnectionState,
    commands: CommandRegistry,
    activity: ActivityState,
    permissions: PermissionState,
    workspace: WorkspaceState,
    diagnostics: DiagnosticsState,
}
```

每个表面拥有本地 UI 状态：

```rust
struct SurfaceState {
    session_id: SessionId,
    transcript: TranscriptState,
    composer: ComposerState,
    selection: SelectionState,
    scroll: ScrollState,
    focused_region: FocusRegion,
    overlays: OverlayStack,
    pane_layout: PaneLayoutState,
}
```

重要规则：

> 服务器拥有的会话状态和表面本地 UI 状态必须保持分离。

这与现有多会话架构文档一致，并使以后的桌面多窗口/多表面成为可能。

### 动作和 reducer

桌面和 TUI 最终应通过类型化动作共享 reducer 逻辑：

```rust
pub enum ClientAction {
    Platform(PlatformAction),
    User(UserAction),
    Protocol(ServerEvent),
    Tick(TickKind),
    Command(CommandId),
}
```

示例：

```rust
pub enum UserAction {
    SubmitPrompt,
    EditComposer(ComposerEdit),
    ScrollTranscript { delta_px: f32 },
    SelectSession(SessionId),
    CancelRun,
    ToggleActivityPanel,
    OpenCommandPalette,
}
```

Reducer 应返回效果而不是直接执行副作用：

```rust
pub enum ClientEffect {
    SendRequest(Request),
    StartDaemon,
    OpenExternalEditor(PathBuf),
    CopyToClipboard(String),
    ShowNotification(Notification),
    RequestRender,
}
```

这是当前 TUI 大多缺失的干净边界。

## 记录模型

TUI 当前把历史/事件归约为 `DisplayMessage` 然后终端行。桌面需要更丰富的块模型。

建议模型：

```rust
struct TranscriptState {
    blocks: Vec<TranscriptBlock>,
    block_index: HashMap<BlockId, usize>,
    streaming_block: Option<BlockId>,
    version: u64,
}

enum TranscriptBlock {
    User(UserBlock),
    Assistant(AssistantBlock),
    Tool(ToolBlock),
    System(SystemBlock),
    BackgroundTask(TaskBlock),
    Swarm(SwarmBlock),
    Usage(UsageBlock),
    Memory(MemoryBlock),
    Compaction(CompactionBlock),
}
```

这成为共同的语义表示。

TUI 以后可以继续从此模型渲染终端行。桌面将从中渲染自定义卡片/行。

### 桌面渲染路径

```text
TranscriptBlock
  -> DesktopTimelineItem
    -> UI 节点
      -> 布局盒
        -> 文本布局 run
          -> 显示列表
```

不要用终端换行行作为桌面的事实来源。

## TUI 到桌面的功能映射

| TUI 功能 | 当前 TUI 形态 | 桌面架构 |
|---|---|---|
| 聊天记录 | `DisplayMessage` + 换行 `Line` | `TranscriptBlock` + 虚拟化时间线 |
| 流式智能体文本 | `streaming_text` + 增量 markdown | 追加感知的块文本缓存 |
| 工具调用 | `ToolCall` 显示消息和流式工具调用 | 带紧凑/展开状态的工具卡片 |
| 批量进度 | 状态/消息准备中的 `BatchProgress` | 活动项 + 内联时间线块 |
| 组合器 | 终端输入字符串/光标 | 自定义文本输入模型，以后 IME 感知 |
| 排队消息 | 应用队列字段 | client-core 中的组合器/会话队列状态 |
| 软中断 | 协议事件和待处理队列 | 可见的中断横幅/队列芯片 |
| 头部/状态 | `ui_header`、`info_widget` | 顶栏 + 状态/活动区域 |
| 侧面板 | 固定 diff/内容/图表面板 | 带标签的检查器面板 |
| Mermaid/图表 | 终端/图像面板 | 图像/矢量表面，以后侧检查器 |
| Diff | 终端内联/固定/文件模式 | 变更文件面板、diff 卡片，以后 hunk UI |
| 会话选择器 | 模态覆盖层 | 命令面板/会话切换器模态 |
| 登录/账户选择器 | 终端覆盖层 | 设置/账户模态视图 |
| 命令 | 斜杠命令/键处理器 | 共享命令注册表 + 面板 + 菜单 |
| 复制选择 | 行/单元格范围 | 语义块/文本选择 |
| 工作区地图 | TUI 工作区部件 | 会话/工作区侧边栏，可选空间模式 |
| 调试覆盖层 | 视觉调试/帧捕获 | 性能 HUD + UI 树/渲染检查器 |
| 重连 | 远程循环状态机 | client-core/app 中的协议客户端状态机 |
| 重放 | 重放模式 | 桌面 UI 测试的事件日志重放装置 |

## 渲染/更新循环

TUI 使用重绘间隔和 `needs_redraw`。桌面应保持相同精神但更严格。

```text
等待平台/协议/计时器事件
  -> 规范化事件
  -> reducer 更新 client-core/app 状态
  -> 收集效果
  -> 标记脏 UI 节点
  -> 如果请求渲染：
       布局脏/可见节点
       整形脏文本
       构建显示列表
       提交 wgpu 帧
       发布调试统计
```

规则：

- 空闲时无连续渲染循环
- token 追加时不重新布局整个记录
- 可见节点数无界
- 协议事件在渲染前可以合并
- 动画必须显式调度下一帧
- 在真实功能集成被认为完成之前，帧统计应可用

## 现有 TUI 行为的复用路径

不要先停掉所有 TUI 工作来抽取一切。使用增量路线。

### 阶段 1：独立于 TUI 内部的桌面原型

构建：

- 桌面 crates/模块
- 假记录/活动数据
- 虚拟化时间线
- 调试 HUD
- 协议形态的假事件

避免依赖 `src/tui`。

### 阶段 2：协议复用

使用现有服务器协议：

- 连接 `jcode serve`
- 订阅/恢复会话
- 接收 `ServerEvent`
- 发送 `Request::Message`、`Request::Cancel` 等

实现一个桌面协议 reducer，镜像 `src/tui/app/remote/server_events.rs` 中的重要行为，但写入 `ClientCore`/`TranscriptBlock` 而不是 `DisplayMessage`。

### 阶段 3：抽取 client-core

一旦桌面 reducer 形态清晰，把 TUI 和桌面的共享部分抽取到 `jcode-client-core`：

- 记录块模型
- 服务器事件 reducer
- 命令注册表元数据
- 活动模型
- 状态模型
- 会话列表模型
- 权限模型

到那时 TUI 可以逐渐成为 `jcode-client-core` 的另一种表现，但不必一次性转换。

### 阶段 4：功能一致

按优先级顺序添加 TUI 功能的桌面版本：

1. 会话、记录、组合器、发送/取消
2. 工具卡片和流式输出
3. 活动面板和后台任务
4. 命令面板和核心斜杠命令
5. 权限提示
6. 会话选择器/恢复/搜索
7. 工作区/git/变更文件
8. 设置/登录/账户表面
9. diff/图表检查器
10. 调试/重放/剖析表面

## 桌面应服务器优先

TUI 仍支持本地模式和远程/服务器模式。桌面应从服务器优先开始。

推荐的桌面规则：

> 桌面始终连接本地 Jcode 服务器/守护进程。它不在进程内嵌入智能体运行时。

原因：

- 避免运行时工作导致 UI 冻结
- 让 CLI/TUI/桌面成为对等方
- 复用重连/会话生命周期
- 更简单的崩溃隔离
- 更容易的 macOS bundle 辅助模型
- 避免另一条本地模式运行时路径

## 与 TUI 模型的差异

### 滚动

TUI 滚动基于行/单元格。桌面滚动应基于像素并带小数偏移。

```rust
struct ScrollState {
    offset_px: f32,
    velocity_px: f32,
    anchor: Option<ScrollAnchor>,
    auto_scroll: bool,
}
```

虚拟化应按像素范围和估计/测量块高度进行。

### 文本

TUI 文本是终端 span 和显示宽度。桌面文本应是整形 run 和字形位置。

桌面文本缓存应按以下键控：

- 块 ID
- 内容版本/哈希
- 样式
- 可用宽度
- 字体缩放
- 平台缩放因子

### 选择

TUI 选择基于行/单元格。桌面应使用语义选择：

- 块 ID
- 块内文本范围
- 可选结构化复制目标

### 布局

TUI 布局是帧大小的终端矩形。桌面应使用带脏标志的保留布局树。

### 渲染缓存

TUI 有几个全局缓存。桌面缓存应是实例拥有且可归因的：

```rust
struct RenderCaches {
    text: TextLayoutCache,
    glyphs: GlyphAtlas,
    images: ImageAtlas,
    timeline_measurements: MeasurementCache,
}
```

除非显式不可变/静态，否则无进程全局渲染器状态。

## 测试策略

桌面应借鉴 TUI 的调试优先心态，但使用适合桌面的测试。

必需的早期测试：

- 从 `ServerEvent` 序列到 `TranscriptBlock` 状态的协议 reducer 测试
- 带 10 万个假块的记录虚拟化测试
- 流式追加期间的滚动锚点测试
- 拆分面板和时间线行的布局测试
- 文本缓存失效测试
- 命令注册表测试
- 稳定假 UI 状态的显示列表快照测试
- 使用捕获协议事件日志的重放测试

基本正确性避免依赖 GPU 测试。大多数 UI 行为应在 `wgpu` 提交前验证。

## 实现建议

开始添加桌面代码，而不太动 TUI：

```text
crates/jcode-desktop-ui       # 纯式 UI/布局模型
crates/jcode-desktop-renderer # wgpu 显示列表渲染器
crates/jcode-desktop          # 假数据应用外壳
```

然后连接服务器协议。

只有在桌面 reducer/视图模型形态被证明后，才应开始共享 `jcode-client-core` 抽取。这避免从当前 TUI 过早抽取错误的抽象。

## 总结决策

桌面应用应架构为共享客户端/运行时概念之上的新自定义表现栈，而不是 ratatui 移植。

TUI 仍是功能参考。服务器/协议仍是运行时基础。新的共享层应是 `client-core`，它拥有与表面无关的应用行为和视图模型。桌面特定代码应聚焦平台集成、保留式 UI、自定义布局、文本整形、虚拟化和 `wgpu` 渲染。
